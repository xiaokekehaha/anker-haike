# Anker 黑客松「智能服务」赛道说明

整理日期：2026 年 9 月 12 日。

本文根据赛事细则和预赛材料模板整理，分别说明官方要求与实现建议；后续调整以主办方最新通知为准。

## 1. 这个赛道要做什么

设计并实现一个面向真实售后场景的 **AI 智能客服 Agent 与高交互前端页面**，结合用户文本、故障图片、技术知识库和历史工单信息，帮助用户完成从描述问题到解决问题或升级处理的服务流程。

官方赛道主题是「真正听懂，真正解决」。作品需要体现 AI 能力、流程编排和业务规则的结合，并让服务效果可以被感知、演示和验证。

官方允许参赛者根据需求选择重点解决的售后难点，围绕具体场景组织能力与处理流程。

来源：[赛事细则 · 2.2.4 智能服务](https://anker-in.feishu.cn/wiki/LbG9wsb2ziX4gEkKCwAcgouknKc#Q7N1dVQM9odZQaxgFPvcGSXXnxd)。

## 2. 官方任务涉及的能力

| 能力 | 需要解决的问题 | 赛题示例或对应行为 |
| --- | --- | --- |
| 情绪识别与安抚 | 理解用户的焦虑、着急或愤怒，并调整沟通方式 | 用户明天要开派对，设备却突然无法工作，先安抚再协助排查 |
| 产品消歧 | 确认用户所说的产品类型和型号 | 用户说「S1 Pro 不吸了」，需要分清是吸奶器还是扫地机器人 |
| 故障定位 | 综合文字、故障图片、技术知识库和历史工单判断问题 | 理解用户上传的报错照片，并匹配相关故障信息 |
| 排障引导 | 将解决方案转化为用户能够执行的操作步骤 | 逐步引导操作，根据反馈继续判断，确认是否恢复 |
| 升级与后续处理 | 根据业务规则判断下一步处理路径 | 系统查不到订单时，识别经销商购买渠道，结合经销商名录判断质保路径 |

官方特别提到的复杂场景包括：产品名称有歧义、购买凭证来自不同渠道、故障描述含糊、用户带有明显情绪。

方案需要说明在这些情况下如何追问、判断、安抚、指导，以及何时升级处理。

## 3. 建议的实现范围

以下为实现建议，不属于官方指定的功能清单。

建议先选定一个具体场景，例如「扫地机器人吸力异常」，把完整处理流程做通，再考虑扩展产品和故障类型。

### 3.1 建议的用户流程

1. **描述问题**：用户输入故障描述，必要时上传图片。
2. **确认产品**：识别型号；存在歧义时，用简短问题确认产品类型。
3. **判断故障**：结合用户描述、图片和相关知识，定位可能原因。
4. **分步排障**：每次提供明确的操作步骤，让用户反馈执行结果。
5. **确认结果**：检查设备是否恢复，记录本次处理结果。
6. **升级处理**：仍未解决时，整理故障信息、已尝试步骤和结果，形成转人工摘要。

### 3.2 建议的前端页面

| 页面能力 | 作用 |
| --- | --- |
| 聊天与图片上传 | 接收故障描述、追问回答和现场照片 |
| 产品确认卡片 | 让用户快速确认设备类型和型号 |
| 排障步骤卡片 | 展示当前操作，并提供「已解决」「仍有问题」等反馈入口 |
| 处理进度 | 显示当前处于产品确认、故障判断、排障或升级阶段 |
| 转人工摘要 | 汇总产品、问题、已执行操作及结果，帮助后续接手 |

### 3.3 建议的演示案例

- **正常排障成功**：用户描述问题后，经过引导恢复使用。
- **产品存在歧义**：系统通过追问确认产品，再进入对应排障流程。
- **排障后仍未解决**：系统保留上下文，生成摘要并进入升级处理流程。

如果选择「购买凭证与质保判断」作为核心难点，可以围绕订单查询、渠道识别、规则判断和后续处理路径单独设计演示。

## 5. 编写方案前需要确定的事项

- 选择的具体售后场景和产品范围。
- 重点展示的 2–3 个功能，以及它们如何连接成完整流程。
- 知识库、历史工单、产品信息和业务规则的数据来源与可用范围。
- 问题解决与升级处理的判断条件。
- 用于演示和验证的案例，以及预期效果的衡量方式。

赛事细则提到了知识库、历史工单等输入，但本文所依据的内容未明确其具体开放清单、接口和获取方式，实现前需要进一步核实。
