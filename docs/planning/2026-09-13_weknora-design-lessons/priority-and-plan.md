# 多轮上下文与证据能力：优先级及实施方案

日期：2026-09-13。状态：建议方案，未实施。依据当前工作区静态核查；线上版本、质量和延迟未在本轮复测。

## 1. 决策与排序依据

建议首批交付“共享有效上下文 + 可追溯证据 + 最小真实多轮回答评测”。随后增加受控的追问补查，再根据数据优化流式体验和检索效果。保留 LangGraph、WeKnora 检索接口和业务事实 reducer。

排序依据依次是：答错的业务后果、影响范围、是否是其他工作的前置条件、已知缺口的证据强度、实施与验证成本。重要度描述价值；优先级描述实施顺序。P0 在本文件表示首批范围，不代表已确认生产紧急事故。

默认排期按暂不引入多 worker/多副本考虑；这是方案假设，非当前部署核查结论。如本次发布包含多副本，跨实例运行协调提升为发布前 P0。

| 工作项 | 优先级 | 重要度 | 主要收益/后果 | 工作量 | 依赖或触发条件 |
| --- | --- | --- | --- | --- | --- |
| 真实多轮回答评测基线 | P0-A，最先建立 | 极高 | 能识别“意图正确但回答无依据”；避免无效重构 | 小至中 | 复用现有 fixture、模型与检索评测 |
| 统一任务上下文与基本裁剪 | P0-B | 极高 | 诊断回复看见有效事实、步骤反馈及风险 | 中 | 基线；沿用 builder 和 router 窗口检查 |
| 证据正文与回答/步骤关联、受控回注 | P0-C | 极高 | 追问有出处，换设备/版本后不误用旧依据 | 中 | 上下文扩展与证据集合语义 |
| 追问时按需补查知识 | P1-A | 高 | 原证据无法回答新问题时能查证 | 中 | P0-C；严格限制只读且不推进步骤 |
| 首个有效文本增量提前发布 | P1-B | 高 | 降低用户等待完整 run 提交的时间 | 中至大 | 浏览器延迟基线、消息提交/作废语义 |
| FAQ/同义扩展/父块补全启用评估 | P1-C | 中至高 | 利用已经实现的能力改善证据覆盖 | 小至中，含标注 | 修正金标、对照结果支持 |
| 更复杂的长上下文恢复与摘要 | P2 | 中 | 改善长会话预算边界 | 中 | P0 基本裁剪后仍有实际失败数据 |
| rerank/grade/无命中改写扩大启用 | P2 | 条件性中等 | 噪声增多或召回失败时可能有益 | 代码增量小，评测成本中 | 有对应失败样本且质量收益抵消延迟 |
| 多副本运行协调 | 扩容前 P0；否则 P2 | 条件性极高 | 防止跨实例断流、取消失败和误判孤儿任务 | 大 | 部署计划包含多 worker/多副本 |
| 跨会话画像、开放 ReAct、替换编排框架 | P3 | 当前较低 | 当前尚无足够收益证据 | 大 | 独立业务需求与对照验证 |

## 2. 最新基线及前次结论修正

1. `conversation/summary_cache.py` 已实现带来源、revision 与过期约束的历史摘录缓存；`context/builder.py` 已接入。这修正 recommendations.md 早先“配置未发现使用”的时点观察。它按预算摘录完整历史，不等同于生成式滚动压缩。
2. `scripts/eval_conversation.py` 已真实调用 intake，检查意图及 reducer 结果；各案例重建预置历史，没有运行完整连续的检索—生成对话。因此本方案补的是端到端多轮回答依据评测，复用已有语义评测。
3. `context/budget.py` 已检查文本/schema/图片/输出窗口，不再新建重复的窗口检查器。当前 builder 将状态、摘录缓存放入历史裁剪前的预算，先减少可选状态与摘录比简单“删历史重试”更有效。
4. `effects.py` 捕获 message_start/message/message_end；`runner.py` 在 publish_commit 后发布 pending_effects。需要测量浏览器端首个 answer delta，模型首 token 指标不能代替体感延迟。
5. `current_evidence_ids` 是一轮诊断合成的候选输入集合；reply 还会裁剪、截取。它既不是精确 reply 输入集合，也不是答案实际引用集合。

## 3. 第一批：先交付一个能验证的正确性闭环

### P0-A：建立基线，实施全过程保留同一套验收

复用 `data/eval/conversation/`，增加独立的回答质量场景与 runner，保持原语义评测入口可用。

最小建议 16 个会话：8 类各 2 个变体，每个常规会话约 4–8 轮；长会话预算场景可更长。类别：步骤解释、已做无效反馈、指代问新知识、产品纠正、切回旧问题、取消/替代回复、原话回顾、失效/缺失证据。

- 使用合成会话和可核验知识版本；真实走语义理解、检索、回复与事件入口。
- 后续轮次读取前轮实际输出，不能每轮重置成预设正确历史。
- 同一组模型、知识库版本、配置对比基线/候选，各建议运行 3 次；固定外部因素仍不能保证模型确定性。
- 两层判定：确定性验证设备/issue、卡片、计数、事件、引用 ID；逐条对照原文审核答案中的产品断言与操作依据。模型评分只辅助，不单独作发布门槛。
- 输出逐案例成功/失败、失败原文及来源、token、模型调用数、浏览器首 delta/完成耗时。小样本报告分子分母，不冒充线上准确率。

建议首批门槛：回归用例中零跨设备误用、零擅自提交动作、零凭空新增危险操作；可核验的事实/步骤断言均有适用来源或明确说明无法确认。普通回答质量不得低于基线；语义一致性允许合理措辞差异。“不重复步骤”允许有明确证据和理由的复查。

### P0-B：扩展现有 ContextBundle，统一规则而非所有任务塞同样的数据

改动重点：`context/builder.py`、`prompts/reply.py`、`sessions/graph.py:reply`、`conversation/reply.py`。

建议增加任务投影参数/对象，由纯函数产出所需事实、步骤、历史范围及证据。沿用实际 human/ai 轮次消息：

- diagnose_reply：当前设备及有效症状、已做动作与反馈、适用风险、当前证据、必要问答。
- explain：被问步骤/回答、相关问答及其依据；不推进步骤。
- history_query：reader 定位到的原始记录；默认不塞知识库证据。
- 其他 issue 的内容只有在消解话题指代或明确回顾时带来源进入，不作为当前设备诊断依据。

预算顺序：必须保留当前输入、业务约束和必要事实；其余按任务选择相关证据、整轮历史和可选摘录。超预算先移除无关字段/重复摘录、缩减可选证据及旧轮次；不能截去来源或关键适用条件后把剩余片段当完整依据。必须内容本身过大时明确请求拆分，不无限重试。

trace 增加各区块 token 估计、裁剪理由与来源 ID，避免记录不必要的原始敏感内容。首批沿用现有模型窗口/输出校验，不引入新的 LLM 摘要调用，也不默认增加模型调用数。

### P0-C：保存生成所见证据，再关联答案与步骤

先明确三种集合：retrieved（召回候选）、presented（裁剪后实际给某次模型的证据）、cited（答案/步骤声明引用）。有合法 ID 不等于断言已获原文支持。

建议最小内部记录包含：

- 身份：evidence_id、知识条目/chunk ID、文档版本或可核验内容 hash。
- 适用范围：issue_id、产品范围，必要时 device_ref_id；检索时间和来源。
- 内容：该次生成实际看到的、受大小限制的原文快照；若为父块拼接，保存参与 chunk ID 与完整适用条件。
- 使用关联：run/input/message 或 plan/step ID、调用任务、presented IDs；有显式引用时另记 cited IDs。

现有 `Hit.full_text` 不会自动进入公开 evidence 累计状态，因此必须有明确的内部保存路径。首批可在现有 checkpoint 的 issue 状态中保存有界证据快照与消息关联，随当前提交语义一起发布；与会话保留期、大小上限保持一致。旧会话读不到新字段时，按“缺少可验证历史依据”降级，不猜测补齐。暂不为此单独建设向量记忆服务。

回注顺序：明确被问的步骤/回答关联 → 当前 issue 的相关生成依据 → 无可验证依据则澄清或进入 P1 补查。显式关联含糊时让用户指出目标。

校验产品/issue、适用条件、版本或来源可用性。事实纠正触发重新判断，不因无关偏好修改使全部证据失效；型号改变时不能直接沿用旧型号操作。历史原话仍可作为“当时回答”展示，必须与“当前有效操作依据”区分。无法确认最新版本时不能声称材料仍是最新。

证据条数及 token 上限可配置，初始可用最多 3 条作评测起点，不把它当已验证最优值；不对指代追问套统一 Jaccard 硬门槛。记录限制导致的信息不足。

## 4. 第二批：覆盖新知识追问，优化体验

### P1-A：有界、只读的追问补查

建议流程：理解本轮目标 → 读取关联依据 → 判断是否已有明确答案 → 按需检索一次 → 解释/明确未知。新增内部请求结构包括 question、target_message/step、issue、产品范围、reason；复用现有 interpret 提案，服务端验证范围，不再每轮额外加一个 LLM 意图调用。

追问 query 应包含明确产品/部件和当前问题，例如“已确认型号 + 滤网 + 是否可水洗”，不能继续仅用旧故障症状构造 query。证据缺失或新型号/新知识问题可以触发；纯原话回顾不触发。初版对明确的新产品知识追问宁可在预算内重查，不凭片段词面命中推断充分。

复用 search_round 与总 deadline，初版最多一轮检索、每库一次主 query，不自动串上 grade/改写/第二轮。预算不足、来源故障、无匹配分别记录；对用户明确无法确认对应事项。不改变 pending card、执行计数、反馈、风险限制；真正新增排障动作仍经既有业务流程。

验收：无证据的“能不能水洗”不能猜；回答解释不消耗步骤；目标含糊先澄清；已有可验证依据的简单解释不额外调用检索。

### P1-B：流式体验单独交付

先记录四个时间点：服务接收输入、模型首 token、业务提交、浏览器首次渲染有效 answer delta。对浏览器测量使用自身单调时钟或请求关联，避免服务器/浏览器时间直接相减。

方案方向：文本事件先可靠追加再推送，关联稳定 input/run/message ID，并显式区分生成中、已提交、已作废。生成完成不自动等于业务提交；只有提交完成后，消息才成为后续权威历史。取消/失败保留可见片段但标记中断或作废，禁止悄悄当成完整答复；恢复按 seq 去重。卡片和事实仍按现有提交后发布逻辑。

不能简单把 message 从 PERSISTED 中删除。需要同步修改事件契约、runner、history 折叠、snapshot 与前端 reducer，并验证生成完成但提交失败、首次增量后取消、进程崩溃及消息替代。

先考虑仅对不变更业务事实的解释回复试点；即使是解释消息，仍需取消和提交失败语义。若首批基线显示等待体验已阻碍主要任务，可提前此项，但不得绕过一致性验收。具体延迟目标在基线后冻结，不预先承诺秒数。

### P1-C/P2：既有检索增强按对照逐项启用

修正标注 → 固定基线 → 分别评测 FAQ、multi_query、parent_expand → 评测通过的组合 → 小范围启用。保留独立开关与版本化报告。优先看有依据的正确回答/计划和无效重复操作，延迟与调用成本作为约束。

已有初步对照只能指示实验顺序。rerank/grade/无命中改写需要对应的困难样本，不能因为技术更复杂就优先上线。parent_expand 的收益应同时验证 synthesize 与最终 reply 实际看到的正文，避免仅改善中间节点。

## 5. 扩容及远期工作

多副本前新增持久运行 owner/租约、原子认领及 fencing，防止旧 owner 在租约失效后继续提交。取消请求持久化，由实际 owner 观察并确认。跨实例事件读取以持久 seq 日志为事实源；通知只负责唤醒，丢通知仍能补拉。仅按本进程 _live 判孤儿的逻辑要改成租约/归属判断。

可优先复用 PostgreSQL，是否需要 Redis 按吞吐与通知延迟验证。必须测试跨实例重连/取消、owner 崩溃、租约过期后旧 owner 恢复、重复提交和启动时不误终止其他实例运行。若暂时不支持多实例，部署配置应明确约束单 worker，而非假定任意扩容都安全。

长上下文后续优化先看哪些内容导致溢出。当前已有摘录缓存与窗口检查；只在任务投影后仍存在真实失败时，考虑更细的摘要与供应商截断恢复。finish_reason=length 本身不能证明输入窗口不足；需要供应商语义、usage、错误码与剩余预算共同判定，确实缩减输入后最多一次恢复尝试。

## 6. 排期、发布及回退

建议拆成可独立审查的交付：A 评测基线 → B 上下文统一 → C 证据关联回注 → D 追问补查。流式 E、检索开关 F、多副本 G 分别独立。

粗估一名熟悉项目的工程师：A 约 1–2 人日，B 约 2–3 人日，C 约 2–4 人日；首批共约 5–9 人日，包含必要回归及一轮评测修正，不含等待模型/服务故障、线上验证与大幅返工。D 约 2–3 人日；E/G 牵涉跨层状态，需完成详细契约设计后再估，不能与首批混报承诺。

- 在途代码先固定版本作为比较点；本轮不自动提交、发布或修改其他任务。
- B/C/D 使用独立启用配置，默认保留兼容；可在测试会话里采集新旧上下文差异，不双跑业务动作。
- 证据字段采用向后兼容读取；回退不删除历史数据。某范围被确认错误时禁用该范围能力并明确澄清，不能静默退回已知错误答案。
- 发布前跑相关会话/证据/预算/恢复回归和端到端多轮质量集；不重复造已有测试。
- 对照报告同时提供模型/知识库/配置版本与失败案例。上线观察窗口内出现跨设备证据误用、误提交动作或消息重放不一致，应停止对应新路径并修复。

本轮只完成方案与评估文档，未实现上述变更，也未执行付费模型评测、数据库修改、配置开启或部署。
