# WeKnora 对当前项目的设计启示

日期：2026-09-13。WeKnora 对照以用户提供的 v0.8.0 源码分析为背景；项目判断基于当前工作区静态读取。工作区有其他任务在途修改，不代表线上已部署；本轮未重跑评测或访问数据库。

## 判断

保留自有 LangGraph 业务编排，继续把 WeKnora 作为知识服务。借鉴阶段职责、上下文装配、证据生命周期和运行事件设计。当前售后业务需要设备/问题隔离、事实纠正、步骤反馈、风险限制和凭证交互；直接切换知识聊天 API 会引入两个会话状态维护主体，且仍需自研业务约束。

## 当前基线修正

9 月 12 日 role-explanation.md 中“未使用 WeKnora 的聊天管线”仍成立；“本项目缺少同类能力”不能由此推导。

- `orchestrator/app/conversation/interpret.py`：已有统一语义入口、业务意图、带逐字来源的事实候选与纠正提案。
- `orchestrator/app/conversation/reduce.py`：已有 issue/device 隔离、事实版本与撤回、风险约束和诊断/对话路由。
- `orchestrator/app/context/builder.py`：已有按完整 run 装配的历史消息、token 估计及预算、来源序号和上下文版本。
- `orchestrator/app/knowledge/search.py`、`orchestrator/app/sessions/graph.py`：已有可选多查询、FAQ、rerank、父块补全、grade、一次受控补检索。
- `config/retrieval.yaml`：上述增强及 query_rewrite 默认关闭；实现存在、配置启用、生产生效与效果改善是不同判断。
- `orchestrator/app/sessions/router.py:125` 附近与 `manager.py:98`：已有按 seq 回放、Last-Event-ID 和实时订阅。

## 优先级与建议

### P1：让理解与生成共享同一份有效上下文

`conversation/interpret.py` 和 `conversation/reply.py` 使用 build_context，而 `sessions/graph.py:2013` 的诊断回复通过 `prompts/reply.py` 只接收本轮文本、简化状态、当轮证据与故障卡，没有直接纳入完整问答和已执行步骤。这是静态可见的输入差异，不是已经复现的用户故障。

建议在现有 ContextBundle 上统一装配规则，保留各任务自己的提示词与预算。诊断回复至少应看到当前 issue 的有效事实、当前待办、已做步骤及反馈、风险限制、相关历史问答和有效证据。来源原文与模型推断分开保存，用户说“清过了还是不行”不能被当成又一次首次报障。

不要复制 WeKnora 的 max_rounds 截断作为唯一策略。项目已有 token 预算，应继续按整轮裁剪，保留必要事实；历史原话回查走 reader。summary_after_turns / summary_max_tokens 配置存在，但本轮搜索未发现这两个参数被摘要生成逻辑使用，不应据此声称滚动摘要已实现。若加摘要，保留原文入口和来源引用，不覆盖事实账本。

### P1：用证据充分性决定追问是否检索

当前 reduce 将 explain / history_query 等路由到 dialogue，且 dialogue prompt 明确禁止新增排障动作。这是有价值的业务边界。

建议进一步区分“解释已给出的信息”和“补充新的产品知识”：

- “刚才那一步什么意思”：读取步骤与原证据，通常不需要新检索。
- “你说的滤网能不能水洗”：若已有证据没有明确说明，应在当前型号范围检索；缺证据就明确无法确认。
- “不是 A1，是 A2”：先更正设备/产品范围，再重新判断资料适用性。

业务事实变化继续由受控 reducer 生效；模型提出语义解释与检索需求，不能仅凭意图标签直接授予新操作权限。检索 query 继续优先由已确认产品与有效症状构造，仅在指代无法从结构化事实解决时考虑受控改写，避免每轮重复增加 LLM 调用。

### P1：补齐回答到证据的关联，再讨论历史证据回注

当前 graph 累积 evidence，但诊断生成选取 current_evidence_ids；conversation 的 ContextBundle 未直接装配这些检索片段。history.py 的 references 目前可见用途是消息替代关系，不能等同于回答使用过哪些知识证据。

建议显式保存回答/步骤与 evidence_id、chunk_id、文档版本、issue_id、产品范围、生成时上下文版本的关联。追问先按关联读取原证据，再校验当前范围、知识版本和事实是否发生相关变化；变化时重新验证，不能一律把所有变化都判为失效。

不直接复制 Jaccard ≥0.15、折扣 0.6、最多 3 条等常数。“它能水洗吗”与原文可能词面重合很低，但有明确上下文引用；旧型号的片段也可能词面非常接近却不适用。先保证关联与适用性，再评测相关性排序和 token 上限。

同时区分召回候选、进入生成的证据和答案实际引用：graph 的 evidence 事件还会包含 grade 剔除项，提前发来源列表并不证明生成内容被这些来源支持。

### P2：先证明检索增强有效，再逐项启用

复用已有 bounded-agentic-rag 实现与评测，不再开发重复管线。

现有 switches.md 的初步对照偏向 multi_query + FAQ + parent_expand；rerank / grade 未显示收益。标注仍未完成，不能将这些结果视为确定结论。该速查文档的 0/56 与 progress 后续两条示范标注存在时间差，避免传播固定过期计数。

先校正金标并重跑基线与候选方案，再决定启用。关注正确计划/答案、错误操作、引用支持程度和首条有效回复延迟；hit@5 高不能证明方案正确。不要复制上游复合评分权重或默认开启所有增强。

### 扩容前必做：跨实例运行协调

`manager.py:98` 的 subscribe 在当前进程没有 run handle 时只回放已有事件，然后返回；`manager.py:131` 的 cancel 也要求本地 handle。持久化事件提供回放基础，尚不能单独保证任意副本持续接收另一个副本的新事件或取消其任务。

若要部署多 worker/多副本，需要运行归属与租约、跨实例事件通知或持久日志轮询、可持久读取的取消请求、seq 去重和孤儿任务判定。启动时 reconcile_orphans 也需识别其他健康实例的任务。沿用现有事件契约即可，不必照搬 Redis 或 100ms 轮询实现；先明确故障语义。

## 暂不优先引入

- 自研 EventManager 替换 LangGraph：当前痛点可在已有节点与模块边界内解决，框架迁移本身无已证实收益。
- 开放式 ReAct 决定售后动作：当前受控计划、反馈与风险限制更贴合业务；若未来引入 Agent，先限定只读知识查询且设轮数、调用和时间预算。
- 泛化跨会话用户画像：优先完善设备/问题事实、已执行动作与失败结果。跨会话设备维修记录可在业务需求明确后单独设计，不能把模型推断自动升级成事实。
- 无证据时模型自由给新操作：保留受控标准流程、澄清与升级路径。

## 建议验收场景

以下是后续实施时的验收建议，本轮未新增或运行测试：

1. “清过滤网了，还是不行”：正确保留已做动作及结果，不无理由重复。
2. “它能不能水洗”：当前证据不足时补查，不能凭上一轮口吻继续猜。
3. “刚才说错了，是另一台 A2”：旧设备的证据和失败步骤不污染新设备。
4. 长对话后询问最初原话：能定位原始记录，缺失时明确说明。
5. 生成中断后续问：不把 aborted/replaced 答案视为完整事实。
6. 连接切到另一副本后继续收流、取消：无事件丢失/重复，不误判另一个实例的运行任务为孤儿。

建议实施顺序：统一诊断上下文 → 追问证据关联与按需检索 → 完善多轮评测 → 按评测启用已有检索增强；跨实例运行协调放在多副本上线前完成。

## 对后续五项提案的复核

再次核查当前工作区后，支持将最小多轮评测与证据回注合为 P0，但实施假设需修正：

1. `current_evidence_ids = list(round_evidence)` 是本轮进入诊断合成的证据集合，不等于上一条回答实际引用集合。选中计划/步骤的 evidence_ids 可以作为优先关联；无明确关联时只能称“前轮检索依据”。父块正文在 `Hit.full_text` / `as_internal_item()` 中，而累积 evidence 写入的是 `as_evidence_item()`；不能仅调用 `_evidence_text(state.evidence[id])` 就保证获得父块正文。
2. 证据注入应优先关联当前步骤/被追问回答并校验 issue、产品及版本；≤3 可作为初始可配置上限，但还要限制 token。Jaccard 不应直接作所有指代追问的硬过滤。history_query 主要回答历史原话，不必无条件注入知识库材料。
3. builder 在加入历史前就检查必需内容预算；因此必需内容已超限时“丢历史+一句摘要”不能解决问题。先将状态投影到当前任务，压缩可派生内容，保留必要事实、风险与当前输入；输入本身过大仍需明确请求拆分。`context/budget.py` 已有 input/schema/image/output 的绝对窗口校验，不能将绝对输出预留列作完全缺失。
4. 拟议 length/usage 条件应作为经供应商适配验证的候选恢复信号，不能仅凭当前代码断言必定是窗口不足。先收集和规范化 finish_reason / usage，并在确定减少输入、剩余时间允许时至多重试一次；不要直接复制 16384/4096 常数。
5. 当前已有 `test_conversation_original_case.py` 和 `test_conversation_flow.py` 等多轮回归测试，语义解释被替身替代。真正缺口是可重复的真实模型多轮 grounding 质量评测，而不是没有任何多轮测试。现有 query_rewrite 是无命中补救，不是每轮指代改写；0/56 触发不能单凭轮数归因，还需无命中口语表达、噪声命中和改写漂移等专项样本。
6. `conversation/effects.py` 将 message_start/message/message_end 捕获进 pending_effects，印证延迟发布假设。事件日志设计可降低传输耦合，但先发布再提交仍需未提交/完成/作废消息语义、取消及恢复一致性；不能把增量直接绕过捕获视为等价实现。测量用户输入到浏览器首个有效 answer delta（p50/p95），与模型首 token、业务提交耗时分别记录。

建议 P0 先复用已有会话 fixture，补少量真实模型多轮对照：步骤解释、指代追问、补查新知识、型号纠正、切换旧问题、取消回复、历史原话回顾、过期/缺失证据。评测实际断言来源适用与答案受支持，不只检查输出含有一个有效 evidence_id。

本次仍为方案复核，未修改业务代码或配置、未运行测试。
