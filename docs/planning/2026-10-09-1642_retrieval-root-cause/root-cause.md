# 知识检索相关错误：根因与修改位置

日期：2026-10-09。范围：官方首测 T18、T22、T30、T31、T34、T52、T61，T13 为对照。

结论：已确认的主要故障发生在事实入库、诊断输入、证据引用和失败分流。T18/T22/T30/T34 的目标资料都已进入模型候选上下文，增加召回数量不能解决这些案例的直接原因。建议先做这些接口的局部重构；本轮证据不支持更换知识库或重写整个系统。

本报告定位历史首测的失败机制。首测内部状态、模型语义日志与固定提交 `bf29496` 的校验/路由函数相互印证。当前共享工作区有另一会话正在修改应用，本文不代表那些修改完成后的验收；本轮只新增诊断文档和离线探针。

## 1. 事实抽到了，但原文引用不合格，被静默丢弃

完整链路：模型抽取症状 → 同时生成原文引用 → `quoted()` 校验引用是否存在 → `reduce_turn()` 丢弃无效引用的事实 → `symptoms=[]` → 检索使用原文回退，仍找到目标资料 → 诊断校验只能从空症状列表选择，所有 supported 方案必然失败。

| 案例 | 原文引用具体问题 | 目标资料 | 实际拒绝原因 |
|---|---|---|---|
| T18 | 模型在引用中插入 `...`，拼接了不连续的原文 | `rv-0147`，3212 | `no_supported_symptom:qa_rv_0147` |
| T22 | 将“问题描述”和“错误码”两段倒序拼接成一个引用；原文两段之间还有推送字段 | `rv-0106`，7002 | `no_supported_symptom:qa_rv_0106` |
| T34 | 第一条把原文 `siscovered` 改成 `discovered`；第二条把 `I` 改成 `i`，当前校验保留大小写 | `rv-0312`，地图丢失 | `no_supported_symptom:qa_rv_0312` |

这三例模型语义日志都存在症状候选，但入库 `patches=[]`，最终 `facts=[]`、`symptoms=[]`。模型并非完全不理解问题。知识选择日志的 `no_supported_symptom` 检查位于 `applicability == supported` 之后，说明对应候选已被模型判断为适用，再被程序拒绝。

离线对照：使用同一候选、同一知识引用和同一最小模型响应，仅把允许的症状集合从空集恢复为用户原文中的有效片段，三个候选均从拒绝变为保留。这是确定性校验机制的证明，不是重新调用模型得到的通过率。

修改位置与边界：

- `conversation/interpret.py`、`conversation/reduce.py`：保留来源校验。引用失败应返回结构化拒绝原因，并进行一次有界修复；不能静默把“事实抽取失败”当作“用户没描述问题”。
- `official/message.py` 与事实入库接口：表单中可直接定位的问题描述、设备提示、错误码，由程序保存带来源的字段。设备提示不能被当作用户主动要求转人工。
- `diagnose/query.py` 与 `diagnose/synthesize.py`：共用一份带来源的诊断输入，避免查询有原文回退、诊断却只能消费空症状。原文回退表示待分析材料，不代表整段话都是肯定症状或所有候选均适用。
- 后续可将模型复制长引文改为引用服务端生成的原文片段编号，支持一个事实对应多个原始片段。语义值允许归纳，来源文本由程序回填。仅修改大小写匹配无法解决省略号与不连续拼接。

## 2. 用户事实编号与知识证据编号混用

T30 的正确候选 `qa_rv_0443` 已在上下文中，模型也输出了 `supported`。但 `evidence_ids` 填入了用户的两条事实编号：

- `8abb61d9f499506db86872aa2ab6a62f`：E4、边刷异常、任务结束。
- `15bd1f003e13514089694f65f7251127`：两天前换过边刷。

合法知识引用是 `qa:rv-0443` 等本轮证据编号。程序因此记录 `evidence:qa_rv_0443:…` 和 `no_evidence:qa_rv_0443`，丢弃该方案。

`context/builder.py` 把用户事实及其 `fact_id` 放入通用上下文；诊断任务数据同时包含知识 `evidence_id`。两类编号进入同一模型上下文，输出字段又是宽松的字符串列表。当前校验能发现错误，但没有引用修复流程。

离线对照：保持方案和症状不变，只将错误的事实编号替换为已提供的 `qa:rv-0443`，原有校验即保留该候选。原始错误编号与事实表逐项相等，已排除单纯随机编造编号的解释。

修改位置：`diagnose/synthesize.py` 的输入结构、输出模型和 `filter_hypotheses()`；`sessions/graph.py::_synthesize_step()` 负责提供候选映射。

建议让模型返回一个候选编号，例如 `K1`，以及独立的用户事实编号 `F1/F2`。服务端维护 `K1 → plan_id + 可引用知识片段` 映射，避免模型重复生成多组长编号。候选引用、事实引用分别校验；出现无效引用时，在同一批候选内做一次输出修复。不能直接取消证据校验，或把任意无效引用静默补成合法引用。

## 3. 失败原因被合并，恢复动作没有针对原因

以上案例首轮没有方案后，`retrieve()` 都尝试了 `context_recovery`：只将首次被数量/字符预算排除的其他候选再交给模型。T18/T22/T34 的实际恢复集合与首轮集合不相交，T30 同样改看其他候选。

这种恢复能处理“相关资料被预算裁掉”，不能修复空事实或错误引用。最终 `_diagnose_outcome()` 主要按“有无方案/澄清”决定出口；T22/T30/T34 都出现 `knowledge_status=ok`，但最终走 R5 人工交接。R5 是业务出口，不能反推知识库真的没有答案。

应修改 `sessions/graph.py::retrieve()`、`_synthesize_step()`、`_diagnose_outcome()` 的结果传递，保留明确失败原因：

| 原因 | 对应恢复动作 |
|---|---|
| 有症状候选，但来源校验全部失败 | 修复事实引用；修复失败才向用户询问必要信息 |
| 正确候选存在，模型引用编号无效 | 保留原候选，修复输出 |
| 候选未进入上下文 | 使用现有候选恢复流程 |
| 必要前提未知 | 询问那个缺失前提 |
| 候选与已知事实冲突 | 拒绝候选，不把冲突改写成需要用户再次确认的事实 |
| 确实没有匹配知识或错误码未收录 | 如实说明缺口，按规则转人工 |

这只需要清晰的内部结果类型与对应分支，不需要引入一个新的总调度器。

## 4. 另两类问题应在各自边界处理

**T31：首次求助绕过检索。** 用户描述已擦过触点，`operation_changed=true` 使 `route_entry()` 直接进入 `reassess`（对已有排障方案重新决策），但当时没有方案，也没有检索记录。最小状态复现得到 `reassess`；只清除此标记即变为 `disambiguate`，继续产品确认和检索。应在 `route_entry()` 检查是否真的存在可重新决策的诊断状态；用户在来信前做过的动作应保存为已做操作。这不属于知识查询不准。

**T52/T61：主题相似被当成适用，错误也会出现在追问中。** T52 的事实和 query 都保留“充电盒本身不能充电”，但候选变成“充电盒给泵充电的磁吸对位”。T61 的事实和 query 都保留“提前两小时启动、清扫没有记录”，追问却预设为“定时清扫没启动”。已有数据不能把这两例归因于上游丢失整句。

应在 `diagnose/synthesize.py` 同时校验可执行方案和澄清问题：对象、动作方向、时间关系、肯定/否定是否与用户事实一致；未知与冲突要区分。候选条件应来自官方文档，不能只依赖模型自由生成的 `matched_subject` 或用字符串包含关系推断语义一致。T52 若原句仍存在歧义，应先区分盒子充不进电与盒子不能给泵充电。T61 的追问不能预设“从未启动”。

本轮尚未证明 T52/T61 的最佳资料是否在整个知识库中、换检索排序能改善多少。这部分需要单独标注期望文档并评估召回；不能从最终错答直接下结论。

**T13 对照：5116 未在当前官方错误码索引收录。** 当前记录为 `code_miss`，走人工核实有依据。不能为了减少人工率拿相近码 5112 替代，也不能把合理交接记成系统故障。

## 5. 实施顺序与回归要求

1. **先修事实传递**：来源校验失败可见且可恢复；查询、诊断、摘要使用同一份事实及原始材料。覆盖 T18/T22/T34，并泛化验证多语言、拼写错误、跨段引用。
2. **再修候选与证据绑定**：用户事实和知识引用分开建模；引用无效时修同批输出。覆盖 T30，并验证错误编号仍被拒绝、无关资料仍不能生成操作。
3. **同时修失败分流与首次路由**：空事实、错引用、未召回分开处理；没有旧方案就不能直接进入重新决策。覆盖 T31 及所有不恰当 R5。
4. **补齐适用性和追问校验**：验证对象、方向、时间、否定和并列问题，覆盖 T52/T61，以及描述相似但含义相反的对照样本。
5. **最后评估检索参数**：单独统计期望资料是否召回、是否进入模型上下文、是否被选中、为何被拒绝，再决定是否调整查询、重排和上下文预算。

这些规则按事实和状态生效，运行时代码不应判断 T 编号或完整案例原文。回归中保留 T13 的合理人工交接、真正无依据的事实拒绝、正常多轮继续排障、明确拒绝操作和已有人工审批边界。

当前并行修改中已看到首次路由保护、精确错误码直达、对象/时间字段等方向。精确错误码直达可以作为优化，可能绕过 T18/T22/T30 本次失败路径；它不能替代上述共用接口修复，尤其无法覆盖无错误码的 T34，也不自动修复事实在摘要等后续用途中的缺失。本轮未对并行修改做端到端验收。

## 证据与复现

- `checkpoint-evidence.json`：按首测 session_id 只读取得的 8 个会话诊断状态，包含被拒原因、事实、知识候选和流程结果。
- `intake-evidence.json`：从本地 `conversation_turn` 日志提取的三例语义输出及入库结果，证明事实因引用不合格而未入库。
- `reproduce.py`、`reproduction-results.json`：固定 `bf29496` 的实际函数，5 例机制对照全部通过；不调用真实模型或在线知识库。对照响应为最小构造，不冒充完整模型重放。
- 原始首测：`docs/planning/2026-10-09-1515_full-official-evaluation/T*.json`。

在仓库的 `orchestrator` 目录执行：

```bash
HAIKE_LLM=off HAIKE_KNOWLEDGE=off uv run --env-file ../.env python ../docs/planning/2026-10-09-1642_retrieval-root-cause/reproduce.py
```

默认模式检查“历史机制可复现、单变量对照可改变结果”，退出 0。加 `--expect-healthy` 检查基线业务结果是否正常，预期退出 1，明确暴露历史缺陷。脚本固定历史版本，因此未来修复验收需要针对修复代码新增相应回归；不能以该脚本默认通过宣称系统已修好。
