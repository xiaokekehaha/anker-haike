# 从方案转换的开发需求

依据：[design.md](design.md)。本轮实施 R1–R5；R6–R8 是方案阶段登记的下一批，R9 是开发复核新增的统计问题，均不能计入本轮完成率。状态和执行证据统一记录在 development.md。

## 本轮

| ID | 需求 | 可验收条件 | 回归与证据 |
| --- | --- | --- | --- |
| R1 | 未验证候选不能执行；按最终输入控制预算 | 模型关闭、无证据、调用失败及超预算均不产生 retrieval_order 可执行方案；预算裁剪有界，裁剪后只引用可见候选/证据；必要内容仍超限时返回失败原因；现有精确错误码路径不受影响 | T20/T53 失败路径；小预算、多候选、无法裁剪；T18/T30 精确码 |
| R2 | 关闭案件不显示等待，处理任务有终点 | closed_unresolved 进入 propose 后明确问题未解决且案件已关闭；当前处理任务不留 active；不新增免费服务/人工承诺；真实 awaiting_approval 保留人工边界；其他查询可按原队列推进 | T51/T53；单任务、多任务、真实人工等待 |
| R3 | 结构化故障表单不丢主诉 | 模型只返回 action_taken 时，原 Problem Description 可追溯地进入症状；已有有效症状不重复补入；自由邮件、没有问题描述、否定/不确定事实不被盲目改写为肯定故障；更正及其他设备事实不被覆盖 | T29；多语言字段；现有事实更正与来源校验 |
| R4 | 依据候选原文识别充电对象 | 候选实际讲内部设备充电时，即使模型 matched_subject 缺失、填写 charging case 或使用包含关系，也不能用来处理盒子自身不能充电；澄清对象为盒子自身；真实内部设备充电问题仍可进入对应方案；无充电关系的通用部件排查不受影响 | T52；真实 QA 和合成跨品类正反样本 |
| R5 | 通用澄清不夹带其他品类示例 | 摄像头或未知品类询问现象时，不出现扫地机专有代码；仍可询问用户实际看到的提示/代码 | T58；已有澄清测试 |

R1 的“无可执行方案”不等于“知识库没有命中”：日志应保留模型/预算失败原因。客户端是否展示技术异常不是本轮需求。

R2 的任务 done 表示当前处理环节已结束，不表示故障解决；案件保持 closed_unresolved，不能写成 closed 或 resolved。不新增“过保必须继续排障”的业务规则。

R3 保底是对官方结构化输入字段的保留，不允许用它取消事实极性检查或将整封自由邮件塞进症状。

## 下一批

| ID | 需求 | 开发前必须具备的样本与验收 |
| --- | --- | --- |
| R6 | 统一所有知识入口、拆分混合节点、保留说明终点 | FIRST_TRY、单段 answer、纯说明、尾部说明、条件操作、事实问句、材料上传、媒体及分支定位；用 T19/26/28/34/35/38/40/51 作回归，另加同结构反例；不按 T 编号分支 |
| R7 | 独立业务请求有独立证据 | T22/T38 不生成额外查询；订单号/登录国家字段不能证明客户请求物流；T9/T41/T63 等真实多诉求不得丢失；包括中文、英文、荷兰语和隐含但明确的请求 |
| R8 | 根据对象、动作和结果避免重复排查 | T27/T37 不重复已明确执行且失败的同一动作；部分执行的多动作段落保留未做动作；反证不当成已做动作；依赖 R6 的节点粒度，保留允许再次尝试的条件变化机制 |
| R9 | 统计区分未解决关闭和真实人工交接 | `analytics/l3.py` 的 SQL 与内存投影均不能仅因 closed_unresolved 就归为 escalated_human；先核对指标定义、数据契约和历史投影，再同时验证看板与留存快照；本轮只登记，未修改统计代码 |

## 交付约束

1. 生产代码不出现案例编号分支、订单白名单或按 QA 编号屏蔽错误候选。
2. 保持官方源文件和上一轮原始评测不变；口径修改写 addendum.md。
3. 新增/修改测试必须运行；后端运行 make lint 和相关测试文件。
4. 每项记录复现、变更文件、测试命令、结果、局限。没有真实模型复测不得声称线上或 63 单已全部修好。
5. 本轮不提交、不发布；后续 63 单复测须先证明运行版本对应修改后的代码。
