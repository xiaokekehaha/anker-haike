# T22 平地持续报错：两次结果不一致的原因

结论：复测版本 `0a2adde` 中，两层模型语义判定出现分叉，服务端将判定直接写成步骤执行记录和跳过条件，最终把一次条件误判放大为“排查耗尽 → 质保订单收集”。导致错误出口的直接原因是重启条件被误判为不成立；更早的入口误分类改变了候选范围，并记入了客户并未报告的操作执行。

分析对象是第二轮冻结的 B06-r1、B06-r2，实际运行时间为 2026-10-10 11:11–11:13（北京时间）。业务代码未由本分析修改。分析期间其他会话开始修改相关实现，因此下文引用保存的 `0a2adde` 源码，不能把后续工作区代码当作当时的实现。

## 相同客户输入，两个不同流转

两次首问和补充原文逐字相同。首问是 X10 Pro Omni / T2351 报错 7002，首张卡均为 s1：卡在楼梯或家具边缘时设置禁区。客户随后说：

> This happens continuously on an open, flat floor. It has not been stuck at stairs or furniture.

中文：在空旷、平坦的地面上持续报错，没有卡在楼梯或家具旁。

| 环节 | B06-r1，正确出口 | B06-r2，错误出口 |
| --- | --- | --- |
| 消息理解，Qwen | 故障场景补充；没有执行反馈 | 故障补充，同时给 `feedback=not_solved` |
| 所谓反馈的依据 | 无 | “It has not been stuck at stairs or furniture.” |
| 原 s1 卡 | 新事实使原卡失效 | 被保留，并记为已执行但未解决 |
| 条件判定候选 | s1 楼梯/家具条件 + s2 平地条件 | s1 已被消费，只剩 s2 平地条件 |
| 条件判定，DeepSeek | s1=`negated`，s2=`satisfied` | s2=`negated` |
| 服务端结果 | 跳过 s1，发 s2 重启 | 跳过 s2，计划耗尽，索要质保订单 |

`satisfied` 表示适用条件成立，`negated` 表示条件明确不成立。s2 的适用条件原文是：`the robot continues to display errors on flat ground`。

## 第一处分叉：把场景描述当成执行结果

失败轮的原始 Qwen 输出是：

```json
{
  "primary_intent": "report_problem",
  "secondary_intents": ["step_feedback"],
  "feedback": "not_solved",
  "feedback_quote": "It has not been stuck at stairs or furniture."
}
```

客户没有说“已设置禁区，仍报错”。这句只否定楼梯/家具场景，不能证明执行过设置禁区。

服务端 `answers_pending_step` 用“存在反馈值 + 引文来自本轮”决定是否保留原卡；`resolve_command` 同样核对引文、卡片类型和载荷格式，没有核实引文是否在描述该操作的执行效果。于是 `apply_feedback` 将 s1 记入 `steps_executed`，按 `next_on:s2` 推进。[原卡承接判断](/Users/xiaoke.zhou/Documents/workspace/anker-haike/orchestrator/app/conversation/reduce.py:116) · [文字命令校验](/Users/xiaoke.zhou/Documents/workspace/anker-haike/orchestrator/app/conversation/commands.py:27)

接着，`candidates` 排除已经消费的步骤。正确轮给模型两条条件对照，失败轮只给平地条件。与此同时，正确轮抽取了“没有卡在楼梯或家具旁”的独立观察事实，失败轮没有。这些是实际输入差异，不能把两次调用描述成“同一个完整模型输入”。[复测版本的候选筛选](/Users/xiaoke.zhou/Documents/workspace/anker-haike/docs/planning/2026-10-10-1102_post-makeup-multiturn-retest/t22-analysis/tested-source/fact_check.py:70)

## 直接失败点：重启条件被错误否定，校验没有挡住

失败轮的 DeepSeek 输出是：

```json
{
  "steps": [{
    "step_id": "s2",
    "status": "negated",
    "quote": "This happens continuously on an open, flat floor. It has not been stuck at stairs or furniture."
  }]
}
```

引文前半句明确符合 s2。后半句否定的是 s1 的场景。模型将 s2 判成不成立，属于条件与证据不一致。它是否受到孤立候选和后半句否定的影响，是与输入差异相符的推断；日志没有内部推理，尚不能证明具体的误判机制。

`accept` 只检查步骤 ID、步骤类型和引文是否来自用户；对条件步骤，只要状态是 `satisfied` 或 `negated` 且引文存在，就接受。它没有检查“这段引文是否支持该条件的成立或否定”。`_skips` 随后直接将 `negated` 标为 `skip=true`。[复测版本的接受函数](/Users/xiaoke.zhou/Documents/workspace/anker-haike/docs/planning/2026-10-10-1102_post-makeup-multiturn-retest/t22-analysis/tested-source/fact_check.py:87) · [复测版本的跳过规则](/Users/xiaoke.zhou/Documents/workspace/anker-haike/docs/planning/2026-10-10-1102_post-makeup-multiturn-retest/t22-analysis/tested-source/fact_check.py:108)

s2 是最后一步。`prepare_step` 按 `condition_not_met` 跳过后返回 exhausted；图中标记计划耗尽，再评估为 `handoff_offer / guide_exhausted`，进入质保信息收集。后续流转执行的是已写入的状态；不稳定点在前面的语义判定，以及服务端未拦住错误判定的边界。

## 离线重放确认了什么

从持久化日志取得两个会话全部 8 次模型调用的脱敏输入与输出，固定输出后经过真实的 `reduce_turn → resolve_command → apply_feedback → candidates → accept → _skips → prepare_step`。未调用真实模型或知识库。

| 消息理解输出 | 条件判定输出 | 实际选步结果 |
| --- | --- | --- |
| 正确轮 | 正确轮 | s2 重启 |
| 失败轮 | 失败轮 | 计划耗尽 |
| 失败轮 | 正确轮 | s2 重启 |
| 正确轮 | 失败轮 | s1 禁区卡 |

四个断言均通过，重放时相关 12 个源码/配置文件与 `0a2adde` 的哈希一致。第三行证明，入口误分类本身不足以导致本次质保出口；换正确条件结果，同一入口路径可以发重启。第四行证明，只处理入口分类也不足以保证选步正确：条件误判仍可能让系统回到不适用的禁区卡。

这是对保存输出的控制实验，证明输出被接受后的影响，不是在统计真实模型的失败概率。[重放证据](/Users/xiaoke.zhou/Documents/workspace/anker-haike/docs/planning/2026-10-10-1102_post-makeup-multiturn-retest/t22-analysis/replay-evidence.json) · [脱敏模型输入输出](/Users/xiaoke.zhou/Documents/workspace/anker-haike/docs/planning/2026-10-10-1102_post-makeup-multiturn-retest/t22-analysis/model-calls.json)

## 已排除和仍未证明的因素

- 复测期间容器、源码、配置指纹稳定；两次相同产品、错误码、`qa_rv_0106` 计划及证据版本，未出现召回差异。
- 两次都由 Qwen 做消息理解、DeepSeek 做条件判定，均一次成功，没有超时、重试或模型降级。
- 两次上下文指标都是 `truncated=false`、`omitted_entries=0`；原始客户全文仍在条件判定输入中，不能解释成消息被截断或丢失。
- 配置将消息理解温度设为 0.0，条件判定设为 0.2。温度影响尚未单独实验验证，而且完整上下文本身不同，不能把全部差异归因于温度。首轮输出就已出现不同的额外意图和助手文案，之后又产生不同事实、执行记录及候选范围。

## 必要的修复边界

1. 区分场景补充与操作执行反馈。“平地持续报错 / 没卡在楼梯旁”更新场景；缺少明确的本步骤操作结果时，不写成 `steps_executed`。
2. 对条件逐条绑定对象及支持原句，已处理的兄弟条件保留作对照。尤其不能将“没有发生场景 A”当作“场景 B 不成立”。
3. 跳过步骤需要有效的否定依据；与已知肯定事实冲突时保留为 unknown。仅因自动条件跳过导致计划耗尽，应复核或澄清，不能直接视为所有排障步骤已尝试后无效。
4. 回归验证要注入此次错误模型输出，检查下一张卡及执行历史。复测版本原 T22 首轮测试注入的是正确条件结果；两轮反馈测试只脚本化首轮空判定，未注入此次 s2 的错误否定。[复测版本的测试](/Users/xiaoke.zhou/Documents/workspace/anker-haike/docs/planning/2026-10-10-1102_post-makeup-multiturn-retest/t22-analysis/tested-source/test_step_fact_check.py:73)

降低条件判定温度、精简其任务上下文可以作为附加实验；它们不能替代反馈真实性和条件证据一致性的校验。以上为分析建议，本次未修改业务实现。
