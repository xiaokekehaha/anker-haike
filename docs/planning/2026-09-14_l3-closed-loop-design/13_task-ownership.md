# 多任务的对象归属与恢复

延续用户“第一性原理、功能开发为主”的要求，检查事实存储之外的任务执行链路。

## 根因

原队列只保存 intent、quote、status。恢复时仅替换意图，参数继续取当前聊天焦点；去重和完成只比较意图。这使同一种查询的 A、B 订单被视为同一任务，插话查询 B 可能消耗 A 的待办，稍后恢复 A 也可能继续使用 B。自动接续还会继承上一轮 answer_request / answer_scope，把上一问题的字段带到下一任务。

事实有独立寿命，任务也必须有独立归属。聊天焦点、任务对象、案件对象分别承担不同职责，不能互相代替。

## 实现

- BusinessContext 提供对象引用与按引用选择的接口。任务只保存引用，不复制事实；恢复后读取该对象的最新事实。无法解析的引用保留缺失或歧义。
- 队列按意图与对象共同去重，完成时匹配实际查询对象或显式任务 ID。不同订单的同类查询分别保留。
- 显式恢复与自动接续都使用原任务对象；显式切换暂停原任务，查询完成后恢复原排障卡片。
- 自动接续清除上一轮字段请求及回答范围，重新按当前任务读取；退款、换货、改地址分别设置对应办理类型。
- 活跃任务的缺失对象经用户补齐后更新引用。旧队列只从其原话的明确编号恢复，不能默认借用后来聊天的焦点。
- 多任务的顺序与进度由调度流程说明，排障阶段直接下发所选步骤卡片。停用该场景中重复回答整句多诉求的自由生成入口，避免排障回复擅自承诺其他待办的处理方式。

## 验证与边界

沿用已有 API 验证，扩展 A7 覆盖插话查询 B 后自动恢复 A，以及主动恢复 A 后继续原排障卡片。关联检查 52 项通过；后续两处收口再跑 3 项相关检查，Ruff 通过。没有扩展全量语义矩阵。

真实模型会话 `32727b310e91442795f442356cecbc27` 的五轮验证：建立 A 的排障与物流任务 → 查询 B 的订单、物流 → 恢复排队物流 → 追问单号和渠道，正确返回 A。首次排障自由回复出现虚构转人工安排，已据此收紧多任务输出入口；修复后的会话 `bec800d8941d4cb0b9b945d3dc3b3698` 仅输出任务顺序并正常下发排障卡片，未再声称转人工。证据：`reports/inspection/l3/task-ownership-validation.json`。

同一句提及多个对象但没有明确诉求归属时，当前解释契约仍保留歧义并澄清，不猜测每个子任务的参数。本文不声称覆盖所有自然语言表达，也不代表整个 P0 发布验收完成。
