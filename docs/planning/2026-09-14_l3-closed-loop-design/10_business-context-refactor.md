# 业务上下文与流程职责重构

2026-09-14：用户要求从架构和流程根因解决多轮业务对象丢失，授权修改与重构。此项是 L3 主计划的收口要求，不另开缩小范围的 goal。

## 已验证的根因

1. 缺少业务对象的唯一持久状态。订单号散落在 `consult_params`、`last_consult_params`、`receipt.fields`、`execution.receipt` 和原始历史中。不同节点采用不同优先级，字段清理意味着业务引用意外失效。
2. 把对话日志同时当作业务状态。历史窗口服务于语言理解，会裁剪；执行参数却要求跨闲聊、任务切换和进程重启保持稳定。两者生命周期不同，不能要求模型每轮重抽一次。
3. 理解和流程决定职责重叠。模型既给 `refund_request` 又自由生成「请提供订单号」；`reply_mode=clarify` 能绕过已有订单的业务解析，直接回显这句。模型建议不应决定哪些业务参数已经存在。
4. 结果与用户问题脱节。物流模板只输出 `status/updated_at`，没有展示回执里已有的 `tracking_no`。因此「物流 ID」收到「shipped」，外观像失忆，实际是结果投影不完整。
5. 原验收只验证单轮动作和短追问。没有同时覆盖业务切换、历史窗口外引用、含多个订单的歧义、重启、补充缺参后的接续，以及回复是否回答了所问字段。
6. 全量回归发现一次回顾选中的 `recall_entry_ids` 被作为下一轮解释器的必选上下文，导致 30 轮后的纠正请求在模型调用前超过预算。回顾原文是特定回复阶段的输入，不应跨轮强制绑定；现已在理解阶段去除旧 pin，保留之前回顾的选择元数据供 reader 处理明确 follow_up。

证据：会话 `4d21bcd669654f53afefcd4140c91873` 历史均完整传入；退货两轮模型分类为 refund_request 却要求补已知订单；末轮 logistics_query 确实执行但模板漏单号。两个覆盖该模式的 API 回归先红；临时修复后 20 项通过，但临时修复仍依赖分散状态，不能作为架构收口证据。

## 目标职责

- **历史**：保留原话、来源、时间，支持回顾；不充当每个业务节点的实时参数库。
- **业务上下文模块**：保存当前问题的业务对象、标识符来源与引用状态；统一处理明确切换、歧义、回执关联与旧状态迁移。对话间隔不清空对象。
- **解释器**：识别意图、引用建议和当前原话证据。不得通过自由文本澄清覆盖确定的业务状态。
- **编排图**：按意图进入对应能力；能力使用统一绑定结果决定执行、缺参或对象澄清。
- **业务动作**：输入来自绑定结果，输出可验证回执。只读观察不代表办理授权；写操作继续通过政策、凭证、风险、用户确认与幂等门。
- **回复**：面向所问业务信息投影工具回执；物流单号、订单号、服务单号分别标注，不把三者混为一类。

## 模块接口与不变量

`BusinessContext.restore(state)`：读取新持久状态；旧查询参数／凭证／回执／历史只在迁移入口归一化。

`accept(text, input_id, reference)`：校验本轮显式标识符或带原话证据的引用建议，返回新上下文；相同输入幂等。明确新对象无编号时标为待补，多个同类编号标为歧义。

`bind(action)`：输出 typed binding（ready／missing／ambiguous、params、missing_fields），所有查询与服务上下文共用。

`observe(action, params, receipt, input_id)`：只按本次实际请求与成功回执关联标识符；不同订单不拼接旧运单。回执归属按请求标识符匹配唯一对象，不依赖当前聊天焦点；办理 A 期间查询 B，A 的回执仍关联 A，聊天焦点仍为 B。

`projection()`：给解释器和回复一个小而完整的当前业务对象视图，不依赖历史窗口。

持久状态随 issue 进入 checkpoint；切换 issue 恢复其自身业务上下文。查询结果不会覆盖用户选定的另一笔订单，也不会转化为写操作同意。
