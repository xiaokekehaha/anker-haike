# 办理失败恢复与服务信息收集

本轮继续 P0 票 55、57，按用户要求以功能开发为主。

## 办理恢复

原执行器已经区分可恢复错误，但图节点把所有失败统一转人工，用户没有重试原申请的入口。现在：

- 可恢复失败进入 `executing_failed`，展示失败回执及重试原申请卡。
- 重试仍使用同一案件、动作、方案的幂等键。聊天查询另一订单不会更改办理对象。
- 重试重新检查授权门。政策输入、证据或政策版本导致判定 trace 改变时，先重新生成/确认方案；既有人工特批只在原依据未变时沿用。
- 不可恢复错误保留人工路径；选择“暂不办理”保留案件；重试卡可以直接选择人工协助。
- 新增图路由 execute → await_input 与 authorize → service_context，契约、快照、前端和案件筛选同步支持。

两个必要的接口验证覆盖：超时 → 插话查询另一订单 → 重试成功且只创建一次服务单；超时 → 使用地改变 → 重试被阻止并转重新审核。

## 服务信息卡

购买地、渠道等已知项只展示；只为 `fields` 中的缺项显示输入框。候选从 `config/policy/regions.yaml` 下发，快照保留 choices。表单提交已知项与用户填入项的合并结果，原有完整命令契约保持一致。

回放驱动器同步按真实表单合并 prefilled，修正 A5 仅传 region_use 而遗漏已知必填字段的模拟操作错误。尚未重新录制最新回放包。

## 验证

相关后端检查 50 passed，Ruff、契约生成一致性、前端类型检查与构建通过。最新版 8002 实际页面验证通过：已知项保持，刷新可恢复，确认使用地后正常进入人工审核。完整 P0 回放与发布仍是后续事项，不据此标记总目标完成。

## 统一命令分流

实际页面验证发现：`route_entry` 在处理已经接受的卡片命令之前，先按 `answer_pending` 和 `stage=context` 走服务上下文，从而跳过 `apply_action`。表现为提交成功但值没有保存，下一轮再次追问。已将所有通过校验的 action 入口统一优先交给 apply_action；自由文本仍按意图路由。新增一项接口验收覆盖完整“退款 → 补使用地 → 审核”链路；与凭证、受控命令相关检查 29 项通过。

A5 真实模型链路已完成换货、收货确认、结案和评分。离线回放定位到 ExecutedStep.ts 未归一化导致的记录未命中；回放格式升级为 3，区分运行时间与业务日期，A5 已按格式 3 重录并离线验证通过（模型命中 8，模型/知识未命中均为 0）。

进一步发现：办理完成后解释器的 issue_index 又携带一遍当前问题的完整事实，conversation_view 又携带一遍已做步骤，导致较长 A5 在收货确认时 context_budget，误要求重新说明问题。现在索引只包含其他问题的简要事实和未完成任务，当前问题从权威事实区读取；回答视图引用已有步骤而不复制。预算失败同时记录 required_tokens/max_tokens，避免再把内部状态过大归咎于本条用户消息。辅助 answer_request 只能在事实问答意图下触发咨询，不得覆盖 report_problem/confirm_received 等主流程意图。

最终证据：`replay/a5_replacement/manifest.json`（format 3）、`reports/inspection/l3/execution-recovery-validation.json`；真实模型录制与离线重放都经过脚本最终案件 closed 断言，包含执行回执和评分。
