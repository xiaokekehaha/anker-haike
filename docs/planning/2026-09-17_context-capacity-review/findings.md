# 核查发现

## 已确认

- 当前应用统一文本预算为 8000 token，估算器为 o200k_base，乘以 1.25 余量。
- domestic/intake 路由：qwen3.7-flash → deepseek-flash → glm-4.7；本地 context_window 分别声明 1000000、1000000、200000，尚待官方核对。
- 解释器预扣完整 TurnInterpretation JSON Schema 和 256 token，d524 案例只剩 4679 token。
- 最终调用还有第二道检查：文本和 schema 不超过应用预算；加图片估算与输出预留后不超过具体模型 context_window。
- 目前输入预算不是按 task 分档，模型窗口与应用预算是独立约束。

## 官方容量（2026-09-17 核对）

- Qwen3.7-Flash：上下文 1000000，非思考最大输入 991808，最大输出 131072。来源：https://help.aliyun.com/zh/model-studio/qwen3-7-flash 。
- deepseek-flash 当前对应 DeepSeek-V4.1-Flash，官方上下文 1M。来源：https://api-docs.deepseek.com/quick_start/pricing/ 。
- GLM-4.7：官方模型概览声明上下文 200K、最大输出 128K。来源：https://docs.bigmodel.cn/cn/guide/start/model-overview 。单模型猜测路径无法打开，采用已检索到的官方概览。
- 上述为厂商声明，不是本项目百万 token 容量实测；input/output 应共同受窗口约束，不能同时取各自最大值。

## 实现和测试初步发现

- Router 对 json_object 把 JSON Schema 注入 system，并通过 schema_in_messages 避免重复计算；没有发现本例的 schema 双算。
- 最近 6 轮按完整回合选择；可选历史放不下即停止加入。事实、待办、状态、系统提示超限先丢摘要，再尝试截断超长当前输入；当前输入已短时仍可直接失败。
- 摘要是满 12 轮后从早期完整问答抽取最多 1200 token 的缓存，不会压缩 facts / symptom_interview / turn_decision 等必需状态。
- test_conversation_long_flow 使用真实 HTTP/Router，但 FakeChatModel 的意图和回答由夹具指定，连续 30 轮主要为短闲聊。夹具 route 为 native、未显式设置生产 context_window，输出上限默认 2048；生产 domestic/intake 为 json_object、输出上限 512。
- 既有验收 A20/A23/A39 涉及长会话、超长输入、重试/备用模型预算；文档有要求，尚不能据此宣布当前生产形态全部达标。
- 历史 semantic-eval.json 为 75/75；需统计输入规模并区分旧版语义识别评测与长上下文容量评测。

## 本轮验证结果

运行命令：`cd orchestrator && uv run pytest -q tests/test_conversation_context.py tests/test_conversation_history.py tests/test_conversation_reader.py tests/test_conversation_summary_cache.py tests/test_conversation_long_flow.py`。

结果：15 passed in 1.35s。使用假模型与假知识库；摘要缓存的 PostgreSQL 测试使用现有隔离夹具。

覆盖：整轮历史裁剪、当前输入不重复、schema/重试提示/输出预算的函数检查、30 轮后首轮原文回查、长输入中间省略、跨问题事实可见、摘要缓存的修订失效和删除隔离。长会话测试验证 HTTP→Router→图→状态链，但使用固定意图，不能证明真实模型在长上下文里的理解正确率。

历史真实语义评测：`semantic-eval.json` 共 75 条、15 类、75/75 通过，模型为 qwen3.7-flash / deepseek-flash。记录的 `context_tokens` 范围 1854–1880；这是当时 ContextBundle 的估算，不应宣称是含 provider 包装与 schema 的全部输入。该旧版小上下文评测没有覆盖当前生产状态增长后的容量边界。

对 d524 第一次失败的原始 checkpoint 另做内存预算探测，保留当前生产 schema、json_object 模式、三模型路由和输出预算，只在探测进程替换应用输入预算，没有发起模型请求：

## 现有预期与缺口

既有 `2026-09-13_conversation-memory-v2-design/acceptance.md` 的 A20 要求 30 轮后回顾首轮，A23 要求长输入与主备切换保留必要信息，A39 要求最终 provider 输入和输出预算正确。语义门槛提议为普通意图/目标/变化联合正确率至少 95%，安全、纠正、跨问题隔离等关键案例全通过。设计文档明确区分预期与通过证据。

9 月 15 日 `docs/claude/spec_context_engineering_lessons.md` 已提出按任务预算和状态清单化，但实施记录明确暂缓。实际完成的是长输入省略、检索截断回执和跨问题索引下沉。d524 是状态连同固定提示已超限的新证据，不能由已完成的长文本截断保护解决。

当前没有找到与生产 schema、json_object 路径、真实密集业务状态相结合的容量分档验收。尤其缺少：短输入但必需状态超限、多设备/订单/步骤/事实同时增长、满输入预算时重试、长上下文主备语义质量、各长度档的延迟与成本。

## 建议的管理方式（待实施与验证）

1. **原始记录与模型输入分开**：事件、事实和业务状态按现有保留策略存库；每次模型调用只发送该任务所需视图。意图识别保留当前问题、聊天对象、待办和必要历史；诊断再带适用证据；回答只带已确认答案依据。跨对象索引用精简结构，按本轮引用回查明细。已知字段有唯一对象时可以确定性回答，不能因字段存在就忽略对象歧义。
2. **统一预算计算，按任务定额**：输入有效预算取任务配额、厂商最大输入、模型总窗口减输出/图片/预留三者的最小值。Schema、系统指令、消息包装、重试提示都计入。每个备用模型重新检查；模型真实 usage 用于校准当前跨厂商分词估算。
3. **初始预算建议**：意图解释 16000、诊断 32000、普通回答 16000。仅意图解释的 16000 在本事故上完成了离线容纳检查；其余是待评测起点，不能作为已验证容量或默认上线值。暂时提高全局值可缓解，但长期应按任务配置并控制状态体积。
4. **按占用压缩**：采用 token 压力触发，先去重复信息、无关对象明细、过期决策和可选历史，再生成带来源的结构化进展。保留安全约束、最新纠正、当前待办、对象身份以及已执行步骤结果。不能以盲目截断本轮中间内容替代这些约束。
5. **越界降级与观测**：返回可以确认的事实，必要时只针对缺失范围追问。内部记录任务、实际模型、总预算、各块占用、裁剪记录、估算与真实 usage 偏差、预算拒绝率；用户文案不能把内部装配失败笼统归因于其记录太多。

不需要先引入新的记忆数据库或无界的模型工具循环；已有 PostgreSQL、原文 reader 和结构化状态足以承载第一轮改造。
