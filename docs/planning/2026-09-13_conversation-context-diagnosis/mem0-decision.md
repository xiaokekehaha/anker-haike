# Mem0 是否需要现在引入

核对日期：2026-09-13。结论：**当前故障修复不依赖 Mem0，建议先完善现有 PostgreSQL/LangGraph 上的问答上下文与语义状态管理；把 Mem0 作为以后长期记忆检索的候选增强。**

## 官方能力与本项目的区别

Mem0 支持从用户/助手消息中抽取记忆，也支持 infer=False 保存原始内容。Platform 文档还描述了按一致用户/会话标识自动利用先前消息进行记忆抽取。这些能力有助于存储和组织上下文，但不等于自动把历史传入本项目的 intake 或改写业务路由。[Add Memory](https://docs.mem0.ai/core-concepts/memory-operations/add)

Mem0 search 提供语义检索、过滤及可选重排。检索结果是相关记忆的排序集合；本项目还需要严格按事件序号重建问答、按钮操作与当时摘要。因此建议将本地原始事件与业务状态保留为权威数据，Mem0 检索结果作为附加上下文。[Search Memory](https://docs.mem0.ai/core-concepts/memory-operations/search)

Mem0 Platform v3 官方文档有时间感知检索，官方说明也介绍了时间标注与时间敏感排序；不能声称它不支持时间。官方 Temporal Reasoning 页面明确该能力自动运行于 Platform v3，目前不适用于 OSS SDK；实际采用需锁定版本和验证。[Search Memory](https://docs.mem0.ai/core-concepts/memory-operations/search)、[Temporal Reasoning](https://docs.mem0.ai/platform/features/temporal-reasoning)

## 当前优先级

| 需求 | 当前选择 | 原因 |
| --- | --- | --- |
| 最近完整问答 + 时间戳 + 顺序 | PostgreSQL 事件与统一上下文构建 | 已有 seq/created_at，补齐输入事件、助手/动作视图；不必新增存储链路。 |
| 刚说错了、之前问什么、新问题 | 语义理解与事实/问题状态更新 | 缺少意图结构和对应流程；记忆库无法替代业务逻辑。 |
| 旧风险不串到新设备 | issue/device 归属与确定性策略 | 即使召回到新事实，旧 escalate_reason 仍会强制转人工。 |
| 跨会话设备背景、过去排障摘要、用户偏好 | 后续评估 Mem0 | 从大量历史中找到相关背景时更有引入价值。 |

本会话仅 7 轮，原始记录完整。新增记忆抽取/索引/检索目前没有证据能解决主要缺陷，还要处理本地状态与记忆索引的纠正一致性、额外请求和故障降级。这是项目判断，不是对 Mem0 性能的实测结论。

## 后续如果采用

建议流程：本地提交有序原始事件与有效事实 → 后台写入可检索记忆 → 下一轮按用户/设备/问题检索 → 校验来源及版本 → 合并到近期问答上下文。刚发生的问答和动作直接从本地读取，不能依赖后台索引完成才看得到。

- 用户身份、会话、问题、设备明确映射，不能把本项目每轮执行的 run_id 直接当成 Mem0 的持续会话分组。
- 记忆记录关联 source_event_ids、来源时间与事实版本。纠正同步到记忆检索层；当前有效事实与撤回关系优先。
- 助手推测不自动提升为用户事实。人工已接入、质保资格等仍以业务回执为准。
- Mem0 不可用时当前对话仍可继续。先通过相同多轮数据集比较召回正确性、错误归属、时间问题准确性、额外耗时和调用成本，再决定是否进入主链路。

当前不安装 Mem0、不调用其记忆 API、不将原始会话上传到第三方。本次只做选型判断。
