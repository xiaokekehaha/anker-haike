# 前端可视化重构：从客服助手出发的三套方案（2026-09-18）

用户要求：重新构思前端页面的可视化，从客服助手出发，样式与交互方式各给几套齐全、有依据的方案，次日选择决策。
本轮范围：**只出方案与可点击原型，不动生产代码**。现状证据与外部依据见 [findings.md](findings.md)。

## 1. 出发点：客服助手在做什么

把客户端当作**客服坐席工作台的客户侧投影**。一个真人客服在一次会话里同时维护三样东西：

| 客服手里的 | 现有界面 | 对应问题（findings §2） |
| --- | --- | --- |
| (a) 对话本身 | 有，且是唯一主体 | P3 噪音、P5 卡片不统一 |
| (b) 一张随时更新的工单：产品、问题、已做了什么、依据、状态 | 直到升级才以 `SummaryCard` 出现 | P2 |
| (c) 当前要客户做的一件事 | 混在 (a) 里，提示文字在别处 | P1、P8 |

三条设计原则，每条带依据：

1. **当前任务永远在手边**。待反馈卡与输入框同屏，不用滚动去找。依据：NN/g 启发式 #1（状态可见）、#6（识别优于回忆）；P1 的走查。
2. **记录随时可见、可复制**。产品、问题、已试步骤与结果、依据、案件状态在过程中就有形，转人工只是把它交出去。依据：官方受理条件「必须记录买家已执行的排障步骤及结果」；赛题要求五难点「可感知」。
3. **结构化优先，自由输入永不关闭**。选项贴着问题给，但输入框任何时刻可用。依据：NN/g 聊天机器人研究「按钮与自由文本两者都要有」；仓库既有约定 `OBSERVATION_HINT`。

附加约束：赛题交付是现场可交互演示，评委要能看见「看图 / 问清 / 分流 / 接稳 / 幻觉」的处理过程 → 需要一个对客户默认隐藏、对评委可开的「评审视图」层（§2.3）。

## 2. 三案共用底座

这部分无论选哪套都要做，是 P3 / P4 / P5 的解法。

### 2.1 样式系统

| 项 | 现状 | 改为 | 为什么 |
| --- | --- | --- | --- |
| 色彩 | 单一品牌绿承担品牌、成功、可交互、选中 | 保留品牌绿；新增 `--task`（蓝）专用于「当前待办」：卡片边框、光晕、进度当前段、跳转胶囊 | 绿已有三重语义，待办需要一眼区分；原型里对比可见 |
| 字号 | 正文 14 px，提示 10–12 px | 正文 15 px / 行高 1.7；卡片标题 16；系统行 12；不低于 11 | 中文在 14 px 以下与 1.6 行高下识读吃力；手机端首屏本来就少 |
| 时间戳 | 每条气泡一枚 | 分组时间分隔「今天 17:52」；间隔 ≥ 5 分钟或阶段切换才出现 | 时间戳对客户几乎无用，却在每条消息下占一行 |
| 助手消息 | 每条带头像 + 边框气泡 | 连续消息合并头像（首条显示）；A / B 保留浅底气泡，C 改无框正文 | 减少重复回复的视觉放大（P3） |
| 系统事件 | 工具行、`action`、`case_changed` 各自一套或无样式 | 统一为居中胶囊系统行；检索进行中为瞬态行（> 1 s 出现），完成后变「命中 n 条」 | NN/g 进度指示：> 1 s 要反馈；`action` 项现在是裸 `<div>` |
| 来源抽屉 | 独立时间线行「来源 23 条」 | 卡片右上「依据 n」芯片；点开在记录面板（A）/ 折叠区（B）/ 顶部抽屉（C）展开，主引用置顶 | 依据属于步骤，不属于对话流；保留 `primary_evidence_id` 置顶逻辑 |
| 头部 | 品牌 + 三组健康灯 + 刷新 | 品牌 + 会话切换 + 一个「服务正常」点（点开看组件明细）；回放徽标保留 | 健康灯是运维信息（P4）；回放徽标是演示合规要求 |
| 卡片解剖 | 各卡自定 | 统一：eyebrow（类型 · 序号）/ 标题 / 正文 / 预期结果 / 注意 / 动作行。待办态 = 任务蓝边 + 光晕；完成态 = 一行回执（序号 · 标题 · 依据 n · 结果） | P5 |
| 快捷回复 | 观察题独立卡 + 重复标题 | 选项 chip 紧贴提问消息；chip ≥ 36 px 高；选中高亮其余淡化；「答不上来」用虚线 chip；产品候选同理（带图） | WCAG 2.5.8 / HIG 44 pt；去掉重复标题 |
| 动作主次 | 每卡 3–4 个同级按钮 | 一张卡一个主动作；拒绝类降为文字按钮；步骤结果三选一用等宽分段按钮（≥ 44 px） | 减少误触与犹豫 |
| 会话与问题切换 | 原生 `<select>` | 头部胶囊 + 下拉菜单，标签「产品 · 阶段 · 时间」 | P7 |
| 品类图标 | emoji | 线性图标或产品图；产品候选卡用 `candidate.image` | 视觉一致，深色可控 |

### 2.2 输入区

- 单行胶囊输入，随内容自动增高到 5 行；照片按钮内置；发送键 36 px。凭证模式（`upload_receipt`）下展开为上传面板并保留三种「跳过」。
- 「请求人工」移出输入栏，常驻头部或记录面板；任何状态可点（现有约定）。
- 状态提示合并进 placeholder：待办卡在场时「也可以直接描述看到的情况…」；自由态「说说设备遇到了什么问题…」。`uiState` 那一行取消。
- 保留现有实现：IME 回车判定、粘贴截图、附件预览、失败保留草稿。

### 2.3 评审视图（可选层，三案通用）

- 开关：URL `?observe=1` 或头部菜单项；默认关闭。
- 显示：情绪等级与策略、规则码（`R1b` / `R2` …）、plan id、模型 tier、case 状态码、快照 version。原型里以紫色虚线标签示意。
- 数据缺口：过程中的逐轮情绪只在 `escalation_summary.summary.emotion` 里（findings §4）。若要逐轮显示，需要后端在 `progress` 事件或 `assistant_message` 上带出 `emotion`（一次契约扩展 + `make contracts`）。这是本方案唯一可能的契约改动，且可选。

客户可见文案里不出现情绪等级，只出现策略的人话：「先安抚，步骤尽量少」「直接给方案」。原因：对客户标注「愤怒」本身会激化情绪，也不合规矩。

## 3. 三套方案

### 方案 A 「服务台」：左对话 + 右服务记录，待办卡停靠在输入框上方

一句话：把客服的工单摆在客户眼前，并把「现在该做的事」从流里拎出来钉在底部。

```
桌面 ≥ 900 px                                  手机 < 900 px
+-------------------------------+----------+   +--------------------+
| ✦ 智能服务   [会话▾] 新建 ●正常  | 服务记录  |   | ✦  [会话▾]     ●   |
+-------------------------------+ 产品/问题 |   | Anker737·排障·已试2 ▸|   <- 记录条，点开成抽屉
|            今天 17:52          | 服务方式  |   +--------------------+
|        [用户气泡]              |----------|   |   对话流           |
| ✦ 助手                          | 进度     |   |   …               |
|   ○ chip ● chip ○ chip         |  ○ 理解  |   |   步骤3 等待反馈 ↓ |
|   ✓ 检索知识库 · 23 条          |  ○ 产品  |   +--------------------+
| 1 清理接口     依据6  还没解决  |  ● 排障  |   | [当前步骤卡 · 蓝边] |
| 2 换线测试     依据6  还没解决  |  ○ 结果  |   |  解决了|还没|做不到 |
| 步骤 3 · 等待你的反馈 ↓         |----------|   | (输入 …)     [发送]|
+-------------------------------+ 已尝试2/3 |   +--------------------+
| [当前步骤卡 · 蓝边 + 光晕]      | 依据 3   |
|  解决了 | 还没解决 | 做不到      | 案件     |
| (也可以直接描述…)   ▣ [发送]    | 复制记录 |
+-------------------------------+----------+
```

信息层级：记录面板 > 待办卡 > 对话流 > 头部。

交互模型：

- **首屏**：无历史时对话流只放一句开场白 + 品类 chip + 输入框；记录面板显示空态「开始对话后这里会记录产品、问题和每一步」。hero 文案退为 eyebrow 一行（保留赛题口号，不占三层）。
- **提问**：判别题 / 产品候选作为 chip 贴在提问消息下；点选后其余淡化，系统行记「已选择：…」。
- **待办卡**：`pendingInput` 指向的卡渲染在 dock（输入框上方），流里留一行虚线指针「步骤 3 · 等待你的反馈 ↓」；反馈后 dock 清空、指针变一行回执。凭证 / 服务信息 / 方案 / 评分卡同样走 dock。
- **依据**：卡上「依据 n」→ 记录面板「依据」区高亮对应条目（沿用 `onHover` 联动）。
- **升级**：摘要不再是流里 300 px 的大卡；记录面板整体切到「已整理记录 · 尚未接入人工」状态，顶部出现「复制排查记录」主按钮；流里只留系统行。
- **多问题**：记录面板顶部变成问题 tab；「新问题」按钮在面板底部。
- **手机**：面板折成头部下方一条「产品 · 阶段 · 已试 n 步 ▸」记录条，点开为全屏抽屉；dock 行为不变。

样式取向：工单感。面板用小号标签 + 等宽字体显示 SKU / 单号；对话区留白多、边框少；任务蓝只出现在待办与当前阶段。

覆盖：P1 ✓（dock）P2 ✓（面板）P3 ✓ P4 ✓ P5 ✓ P6 ✓（服务方式 + 评审视图）P7 ✓ P8 ✓（路线常驻面板）。

评审可感知：产品消歧、故障定位（依据）、排障记录、情绪策略、案件状态在一屏内同时可见，演示时不用滚动解说。

改动面：

| 层 | 改动 |
| --- | --- |
| 壳 | `App.tsx` / `App.module.css` 重写为 grid 双栏；容器最大宽 1072 → 1280；`HeaderBar` 精简；`ProgressBar` 下线，逻辑并入面板 |
| 新组件 | `RecordPanel`（从 `timeline` 派生产品 / 问题 / 步骤 / 依据 / 案件 / 人工状态，纯函数 `deriveRecord(state)` 放 `state/record.ts`，可单测）、`ActionDock`、`RecordStrip`（手机）、`QuickReplies` |
| 卡片 | `Timeline` 分成 stream 与 dock 两路渲染；`ObservationCard` / `ProductCard` 改为 chip 形态；其余卡套统一解剖 |
| 输入 | `Composer` 改胶囊、去 heading / uiState |
| 测试 | `App.test`、`HeaderBar.test`、`Composer.*`、`Cards.test`、`ObservationCard.test`、`SessionSwitcher.test` 需改；新增 `record.test.ts` |

工时：底座 1.5 人日 + 面板与派生 1 人日 + dock 与双路渲染 0.5 人日 + 测试与 390 px / 深色回归 0.5 人日 ≈ **3.5 人日**。

风险与不适合的情形：桌面双栏在 900–1100 px 的笔记本上右栏 340 px 会挤；面板派生逻辑要处理多问题与快照恢复；若演示场地只有手机，面板优势消失，退化为 C。

依据：客服工作台的通行形态（对话 + 工单 + 知识）；NN/g #1 / #6；官方「记录排障步骤」要求；赛题「可感知」。

### 方案 B 「向导」：当前任务是主界面，对话是可展开的记录

一句话：把售后当作一段有步骤的流程来走，每屏只做一件事；聊天退为底层记录。

```
桌面 / 手机同构（单栏，居中 680 px）
+------------------------------------------------+
| ✦ 智能服务         Anker 737 · A1289  ● 请求人工 |
| ▬▬▬▬▬ ▬▬▬▬▬ ▬▬▬▬▬ ▬▬▬▬▬ ▬▬▬▬▬                   |  <- 阶段轨，当前段蓝、带副标
|  理解    产品    定位   [排障]   结果            |
+------------------------------------------------+
| ✦ 两步都没解决。接下来用官方针对 A1289 的复位方法。 |  <- 助手当前一句话（含安抚）
|   已尝试 2 步 · 这是第 3 步 · 做完告诉我结果        |
| +--------------------------------------------+ |
| | 当前步骤 · 第 3 步                   依据 3 | |
| | 按 A1289 官方方法复位                        | |
| | 操作 …  预期 …  ⚠ 注意 …                     | |
| |  [ 解决了 ]  [ 还没解决 ]  [ 做不到 ]         | |
| |  选项之外的情况，用自己的话说                 | |
| |  (例如：灯亮了但屏幕还是黑的…)  ▣ [发送]      | |
| +--------------------------------------------+ |
| ▸ 已完成的步骤      2 步 · 都没解决              |
| ▸ 这台设备与问题    Anker 737 PowerCore 24K     |
| ▸ 对话记录          12 条                       |
|      整理记录给人工客服 · 这是另一个问题          |
+------------------------------------------------+
```

信息层级：阶段轨 > 当前任务（助手一句话 + 卡 + 内嵌输入）> 折叠区（已完成 / 设备 / 对话记录）> 出口。

交互模型：

- **首屏**：阶段轨在「理解需求」；任务区是 intake 表单感的一张卡：「一句话说型号和问题」+ 品类 chip + 照片；对齐线上开场白「一条消息里给型号与问题」。
- **当前任务的定义**：`pendingInput` 存在 → 对应卡；否则 → 最后一条助手消息 + 输入框（自由态）。判别题在任务区以大 chip 呈现。
- **推进**：反馈后任务区原地切换到下一步（300 ms 过渡），上一张卡收进「已完成的步骤」。阶段轨随 `stage` 移动。
- **对话记录**：默认折叠，展开后是完整时间线（复用底座渲染）；用户可以从这里追问，追问后任务区显示助手的回答。
- **升级**：任务区变成「整理记录」卡：摘要字段 + 复制 + 人工状态；阶段轨到「处理结果」。
- **多问题**：阶段轨左侧问题名可切换。
- **手机**：结构不变，结果按钮纵向排列 48 px。

样式取向：表单 / 向导感。字号更大（正文 16），一屏留白多；阶段轨是横条不是圆点。

覆盖：P1 ✓✓（任务即界面）P2 ◐（设备与问题折叠可见，依据在卡上）P3 ✓（对话默认折叠）P4 ✓ P5 ✓ P6 ◐ P7 ✓ P8 ✓✓。

评审可感知：阶段推进最清楚；但「听懂」（情绪安抚句、追问、澄清）只剩任务区上方一句话，历史对话折叠后不易展示。

改动面：

| 层 | 改动 |
| --- | --- |
| 壳 | `App.tsx` 重写为 rail + main；`ProgressBar` 改为阶段轨（保留 `progress.ts` 路线逻辑） |
| 新组件 | `TaskStage`（当前任务派生：`deriveTask(state)`）、`StepRail`、`CollapsedTranscript`、`QuickReplies` |
| 卡片 | 全部卡片走任务区大尺寸变体 + 折叠区小尺寸变体两套样式 |
| 输入 | `Composer` 内嵌到任务卡；自由态时独立 |
| 状态 | 需要新增「当前任务」派生与「上一任务收起」动画状态；快照恢复时要重建 |
| 测试 | 几乎全部组件测试重写；新增 `task.test.ts` |

工时：底座 1.5 人日 + 任务派生与两套卡片尺寸 1.5 人日 + 阶段轨与过渡 0.5 人日 + 测试 1 人日 ≈ **4.5 人日**。

风险与不适合的情形：与「对话式客服」的心智冲突，用户想回看上文要多一步；重复回复、追问、多意图分流这些「听懂」能力被折叠掉，与赛题口号「真正听懂」有张力；自由追问后「当前任务」的定义会含糊（助手回答算不算任务）。适合把排障 SOP 执行当主用途的场景，不适合演示情绪与多意图。

依据：NN/g 进度指示研究（确定性进度让用户愿意等更久）；向导模式是复杂表单的通行解法；线上 Live Chat 要求首条消息型号 + 问题。

### 方案 C 「精修对话」：单栏消息流，极简外壳，状态胶囊可展开

一句话：不改聊天的心智，把外壳与流里的噪音清掉，用一个可展开的状态胶囊承担记录职责。

```
桌面 / 手机同构（单栏，正文最大 760 px）
+------------------------------------------------+
| ✦     [● Anker 737 · 分步排障 3/5 ▾]        ⋯   |  <- 48 px 常驻栏；胶囊点开为记录抽屉
+------------------------------------------------+
|                 今天 17:52                      |
|                          [Anker 737 …难用]      |
| ✦ 抱歉，这次使用体验不好。插上手机…有反应吗？      |  <- 无框正文，首条带头像
|                                     [有的]      |
|   问题出现在给充电宝本身充电的时候吗？             |
|            ✓ 检索知识库 · 命中 23 条来源          |
| ✦ 737 连接设备时，屏幕显示更接近哪种情况？         |
|   ○ UVP  ● 屏幕显示异常  ○ 功率偏低  ○ 0.1W       |
|            已选择：屏幕显示异常…                  |
|  1 清理输出接口   依据 6            还没解决      |
|  2 换线测试       依据 6            还没解决      |
| ✦ 两步都没解决。接下来用官方复位方法…              |
| +--------------------------------------------+ |
| | 当前步骤 · 第 3 步  …  [解决了|还没|做不到]   | |  <- 内联，蓝边
| +--------------------------------------------+ |
|              (↓ 回到当前步骤)  <- 卡滚出视口才出现 |
| (也可以直接描述…)                      ▣ [发送]  |
+------------------------------------------------+
```

信息层级：对话流 > 内联待办卡 > 状态胶囊 > 抽屉。

交互模型：

- **首屏**：胶囊显示「新会话」；流里一句开场白 + 品类 chip；输入框在底。
- **待办卡**：仍在流里，但蓝边 + 光晕；新卡到达自动滚到可见；用户向上翻时出现「↓ 回到当前步骤」浮动胶囊（原型已实现）。
- **状态胶囊**：常驻显示「产品 · 阶段 n/5」，点开顶部抽屉：设备与问题 / 排查记录 / 进度与案件 / 复制记录、请求人工、新问题、切换会话。
- **依据**：卡上「依据 n」→ 抽屉「依据」区。
- **升级**：胶囊变「已整理记录 ▾」，抽屉顶部出现复制主按钮；流里一条系统行。
- **多问题**：抽屉里切换。
- **手机**：完全同构，胶囊抽屉即手机记录页。

样式取向：消息应用感（微信服务号 / iMessage 式），无框助手正文，气泡只给用户消息，边框和阴影最少。

覆盖：P1 ✓（蓝边 + 跳转胶囊，但仍需滚动）P2 ◐（抽屉里有，默认不可见）P3 ✓✓ P4 ✓✓ P5 ✓ P6 ◐ P7 ✓ P8 ✓（胶囊常驻显示阶段）。

评审可感知：需要演示者点开抽屉；对话本身最好看。

改动面：

| 层 | 改动 |
| --- | --- |
| 壳 | `App.tsx` 改为 bar + stream + foot（flex 列，stream 内滚）；`HeaderBar` 重写为 48 px 栏；`ProgressBar` 下线 |
| 新组件 | `StatusPill` + `RecordSheet`（复用与 A 相同的 `deriveRecord`）、`JumpToPending`、`QuickReplies` |
| 卡片 | `Timeline` 保持单路渲染；卡片套统一解剖；助手气泡改无框 + 头像合并 |
| 输入 | `Composer` 胶囊化 |
| 测试 | `App.test`、`HeaderBar.test`、`Composer.*`、`Cards.test`、`ObservationCard.test` 需改 |

工时：底座 1.5 人日 + 胶囊 / 抽屉 / 跳转 0.5 人日 + 测试 0.5 人日 ≈ **2.5 人日**。

风险与不适合的情形：记录默认不可见，评审要靠演示者开抽屉；长会话里待办卡仍可能被新消息顶走（靠自动滚动与跳转胶囊兜底）。改动最小、回归面最小。

依据：NN/g #8 极简；NN/g 聊天机器人研究里用户对「按钮 + 文本」的组合与「人工出口」的正面评价；现有壳层设计（spec_frontend_shell_redesign）的连续性。

## 5. 建议

**推荐 A，并以 C 为第一阶段。** 理由：

1. 评审现场大概率是桌面 / 投影，A 让产品消歧、依据、排障记录、情绪策略、案件状态同时出现在一屏，最符合「五难点可感知」；C 需要演示者反复开抽屉，B 把「听懂」折叠掉了。
2. C 的全部改动（底座 + 胶囊输入 + 无框消息 + 跳转）都是 A 的子集；A 的手机形态就是 C。先做 C 可在 2–3 天内拿到可演示的整洁版本，再加记录面板与 dock 升级到 A，不返工。
3. B 只有在把「排障 SOP 执行」当作产品唯一用途时才值得；与赛题口号「真正听懂」有张力，且工时最高。

若工期只剩 2 天：只做 C。若手机演示为主：C 即终态，A 的面板不做。
