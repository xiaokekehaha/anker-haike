# 官方 63 案例修复后全量复测

复测日期：2026-10-09。结论：**修复有明显效果，但尚未通过完整验收。最新一轮为 46 正确、15 部分正确、2 错误；重点补跑另外确认 T53 仍会走到错误路径。**

“正确”指依据当前已知信息回答准确、下一步合理，包括必要澄清、等待材料和真实转人工；不等于设备问题已经解决。“部分正确”表示方向基本合理，但有重要遗漏、对象偏差、重复步骤或交互障碍。

## 4. 优先处理的问题

### P1：适用性判断失败后，检索第一名直接变成操作方案

**问题 →** T20 说的是“无法确定位置，任务结束并返回基站”，却得到 `rv-0106` 的“7002 机器人离地”方案。原文没有 7002，原图仅显示基站放在地板上，不能补出离地故障。

**追踪 →** 第二轮 T20：知识库检索 `status=ok` → `diagnose.synthesize` 所需上下文 7191 tokens，超过上限 7174 → `model:ModelInvokeError` → `plans_ranked.source=retrieval_order`、置信度统一 0.3、无假设证据引用 → `diagnose_outcome.mode=evidence` → 执行离地方案。补跑再次出现，所需上下文为 7438 tokens。

这属于“**检索有结果，但结果未经适用性核验就被执行**”，不能归结为知识库没有收录。补跑 T53 也在超预算后从“无法开机”进入 `bp-0125` 的无吸力方案，说明同一问题跨案例存在。

**修复位置 →** `orchestrator/app/diagnose/synthesize.py` 的 `default_plans_ranked` 与模型异常分支。异常分支直接返回候选，绕过后续 `filter_hypotheses`。应让所有可执行方案经过相同的适用性验证；模型失败后，未验证的候选只能用于重试、澄清或说明暂不能判断。已经由确定规则核实的精确错误码路径可独立保留。

同时修上下文预算：按完整最终提示计算，包括候选标题、事实和证据，减少候选或压缩后再调用。仅扩大窗口是可选优化，不能替代异常分支的校验。

证据：[T20 全量](round2/T20.json)、[T20 补跑](followups/T20.json)、[T53 补跑](followups/T53.json)、[检查点记录](round2/checkpoint-evidence.json)、[补跑检查点](followups/checkpoint-evidence.json)。

### P1：免费服务资格已关闭，排障结束又进入同一关闭案件

**问题 →** T51 正确判断过保，也开始排障；但最后说 `Your case is waiting to be processed`，实际案件是 `closed_unresolved`，没有交接摘要或人工队列，排障任务仍是 `active`。

**追踪 →** 拒绝免费更换并关闭案件 → 推进排障 → 客户反馈未解决 → `escalate → service_context → propose` → `propose` 发现案件不在允许办理状态集合，统一回复“等待处理”。T51 两轮全量和补跑均出现；T53 第一轮及补跑也出现。

**修复位置 →** `orchestrator/app/sessions/l3.py` 的 `propose`、`remedy_closed`、`advance_tasks` 及排障结束路由。免费换货资格的结论、故障求助是否结束、案件是否等待人工，应分别表示。排障结束后给出明确终点或真实交接；等待话术必须以实际等待状态为依据，不能把所有不允许办理的状态都说成等待。

这不是“已经到人工审批，还要求继续比赛”的问题：这些失败会话实际上没有进入人工队列。T9、T63 的真实交接则已按终点通过。

T53 第二轮仅处理免费更换和质保日期便结束，未承接“或帮我修好”的请求，判部分正确。不能通过少建一个排障任务使任务队列表面全部完成。

证据：[T51 全量](round2/T51.json)、[T51 补跑](followups/T51.json)、[T53 全量](round2/T53.json)、[T53 补跑](followups/T53.json)。

### P1/P2：主诉、故障对象和因果关系仍会丢失

**T29：** 原文区分“清洁托盘不能排水”和“脏水箱已经空了”。第二轮状态只剩已做操作，`symptoms=[]`；正确 `rv-0254` 候选因 `no_supported_symptom` 被丢弃，随后询问“脏水箱不能排空时有没有错误码”。补跑问托盘浮子则合理，说明提取与后续判断仍有波动。当前证据能确定症状没有进入有效状态，尚不能区分是模型漏提取还是提取后被校验丢弃。

**T52：** 正确保留了“盒子自身充不上电”和“因此泵无法充电”两项事实，也拦住了直接执行错误方案；但澄清仍围绕泵马达，补跑又问泵放进盒子有没有卡紧、闪灯。应先处理根因对象“充电盒自身输入供电”，不能把后果当独立主诉。

**修复位置：** 事实提取/校验、`diagnose/synthesize.py` 的候选关联与澄清选择。需要保留“对象 + 现象 + 已做操作 + 因果关系”，并检查澄清是否重复或违背已知事实。当前 `_PART_FAMILY` 把 tray/tank/bin 等统一成 container 的做法过宽；同类容器并不等于同一物理部件。此为代码审阅发现的额外风险，不将其单独断言为 T29 本轮的全部成因。

证据：[T29](round2/T29.json)、[T52](round2/T52.json)、[事实检查点](round2/checkpoint-evidence.json)。

### P2：步骤类型改造没有覆盖全部生成入口

**问题 →** T19/T28/T38 的硬件结论、T34 的地图删除说明、T35 的正常机制说明仍是 `action`；T26 混入事实问句，T40 混入上传照片/视频要求。T51 还出现原因说明或标题作为操作卡。

**追踪 →** `official/qa_index.py` 的特殊 FIRST_TRY 拆分直接构造默认 `action`；`plans/qa.py` 对单段 answer 也直接构造默认 `action`，没有走通用类型判断。通用分类依靠词形匹配，说明中的 clean/power 等词也可能被当成动作。T46 已证明问题卡协议有效，残留集中在内容转换入口和混合段落。

**方案 →** 所有入口统一生成有类型的内容节点；混合段落拆成说明、问题、操作、材料请求。只有操作接受“已解决/未解决”，其他节点使用其对应输入。应验证生成结果，而不仅验证模型和前端都存在 `kind` 字段。

## 6. 对重构、业务流程、交互的判断

| 判断项 | 本轮结论 | 必要改动与可选复杂度 |
| --- | --- | --- |
| 系统是否要重构 | 不足以证明需要整体重写；共享模块仍需修正 | 必要：统一可执行方案的校验、完整上下文预算、事实保留、关闭/等待状态处理。可选：再设计更复杂的检索平台或更换模型，当前没有证据证明必须先做 |
| 业务流程是否要改 | 要补齐过保后的完整处理终点和请求覆盖 | 免费服务资格关闭后，排障如何结束必须明确；真实交接后停止，未知型号可明确列为人工待补；不按案例编号增加特例 |
| 交互设计是否合理 | 问题卡方向正确，但尚未覆盖全部知识内容 | 说明、问题、操作、材料不能共用操作反馈；状态话术要对应真实案件状态；页面布局仍需独立浏览器验收 |
| 是否主要是知识库查不到 | 本轮关键失败多数不是单纯缺资料 | T20/T53 是异常降级选错，T29 有正确召回却丢主诉，T52 是对象/因果及澄清偏移；卡片错误是资料结构转换问题 |

本轮也没有证据应把 T20、T51、T52 的失败归因于官方 badcase：原文足以区分定位失败和盒子自身充电，案件状态来自系统自身。T50 有语义歧义应澄清；T63 缺型号但可以带缺口真实交接。T4 的长短商品名称不应仅因文字不同就判为产品冲突，维持正确。其他官方资料质量结论沿用[原始资料复核](../2026-10-09-1553_source-quality-verification/workbook-verification.md)，不以“来自官方”自动证明当前回答适用。

后续验收应至少覆盖：模型不可用/超预算时不执行未验证方案；过保后排障未解决能到明确终点；主诉不被已做操作覆盖；所有内容生成入口产出正确卡片类型。完成后再跑相同 63 单，并单独保留上述 5 单的重复运行结果。
