# 智能售后对话：效果优先的有界检索补救

## Problem Statement

用户希望售后助手在首次检索没有找到足以支持排障的知识时，能换一种准确的表达继续查找，再给出可靠、有依据的排查步骤。

当前补救主要依据“检索是否返回结果”决定是否改写。检索服务可能返回不相关或不完整的内容，却仍被认为已命中，导致真正需要补救的问题直接进入诊断。已有相关性评分会硬过滤候选，在历史对照中误删过有效片段；这项退化不能被归因于该轮评测根本没有触发的 query 改写。

用户明确要求本次以效果为第一优先级，耗时暂不作为是否采用方案的否决因素。需要证明最终症状理解、证据引用、排查计划和处理结果更可靠，而不仅是检索返回了更多内容。

## Solution

在现有有界检索流程内，把补救判断从“有没有结果”改为“当前证据是否足以支持一个适用的排障方向”。首次检索没有结果、全部不相关、或虽相关但缺少关键内容时，都可以进入一次受控补检索。

评分用于识别知识缺口和决定是否继续查找，不再单独作为删除首轮候选的依据。补检索保留原意、否定和已确认产品范围；两轮结果去重合并后交给诊断模块综合判断，来源和轮次保持可追溯。第二轮失败或没有增益时，首轮证据仍可用；始终没有足够依据时，沿用明确标注的标准流程或升级路径，不编造故障原因。

流程为：首轮检索 → 证据充分性判断 → 足够则诊断；不足则改写或加入图片观察进行一次补检索 → 合并候选 → 诊断 → 现有步骤指导或升级。

## User Stories

1. 作为售后用户，我希望首次没有搜到知识时助手能再次查找，以便口语描述也有机会得到解决。
2. 作为售后用户，我希望搜到不相关内容时助手继续查找，以便不会把其他故障的说明当作答案。
3. 作为售后用户，我希望证据只覆盖部分问题时继续补查，以便最终指导覆盖当前关键症状。
4. 作为售后用户，我希望已有证据足够时直接得到排查步骤，以便流程有明确终点。
5. 作为售后用户，我希望“不是不充电，是充得慢”中的纠正和否定被保留，以便系统不会排查错误的问题。
6. 作为售后用户，我希望口语和专业术语之间可以准确转换，以便不需要了解手册术语。
7. 作为售后用户，我希望“还是不行”等后续描述结合当前产品、症状与已执行步骤处理，以便无需重新陈述上下文。
8. 作为售后用户，我希望新增现象被保留、明确纠正的旧现象不再当作事实，以便补查反映最新情况。
9. 作为售后用户，我希望更正设备型号后只采用当前适用范围的知识，以便不会收到其他设备的操作指引。
10. 作为售后用户，我希望产品或指代不清时先被追问，以便助手不会凭空猜测型号或故障。
11. 作为售后用户，我希望上传的故障照片能帮助补查，以便图片中的有效观察不会被遗漏。
12. 作为售后用户，我希望首轮找到的有效信息不会因一次模型评分被丢弃，以便补查不会破坏已有判断依据。
13. 作为售后用户，我希望第二轮失败时仍能使用已有证据，以便偶发故障不会清空排查进展。
14. 作为售后用户，我希望无依据时收到明确的标准流程或升级说明，以便不会把猜测当成已证实结论。
15. 作为售后用户，我希望安全风险和主动转人工仍优先处理，以便检索补救不会拖住必要的升级。
16. 作为售后用户，我希望等待补查期间仍能看到处理状态并取消，以便始终掌握对话进度。
17. 作为售后用户，我希望断线恢复后保留已显示证据和待操作卡片，以便对话可以继续。
18. 作为人工客服，我希望最终步骤和升级摘要能追溯其知识依据，以便接手时核实问题和已执行操作。
19. 作为质量评估人员，我希望分别覆盖空结果、不相关结果和证据不完整的案例，以便验证补救是否在正确时机发生。
20. 作为质量评估人员，我希望区分“补查已触发”“改写有效”“找到了有效知识”和“最终计划正确”，以便定位真实收益与失败原因。
21. 作为质量评估人员，我希望基线和新方案使用相同样例、知识版本和模型设置，以便对比具有可解释性。
22. 作为项目负责人，我希望优先看最终回答、引用和排障效果，并单独记录耗时，以便不会仅因多一次调用就否决有效方案。
23. 作为维护人员，我希望补查次数有上限且决策可追溯，以便流程可以复现、排查和回滚。
24. 作为维护人员，我希望新策略可独立启用，以便不必同时打开所有尚未证明有效的检索增强能力。

## Implementation Decisions

- 复用现有 intake、有效症状增量更新、产品消歧、KnowledgeScope、知识适配器、ModelRouter、诊断汇总与会话运行器。无需新建独立意图分类服务。
- 保留现有基础 query 构造；本规格实现检索后的补救，不改成每条消息都先做 LLM 改写。
- 将证据充分性与知识服务状态分开：知识服务保持 ok / no_match / unavailable 等真实状态；充分性描述能否支撑当前问题。服务故障不能伪装成不相关或无命中。
- 在产品范围已确认、确有有效症状且不处于澄清或升级状态时，首轮真实空结果可直接进入补救；已有候选时复用相关性评分能力判断 sufficient / insufficient / none。任意一个相关命中或故障卡命中不再自动阻止补救。
- sufficient 表示现有证据已足以支持适用排障方向；insufficient 和 none 均可触发补救。首轮故障卡及实际交给诊断的其他来源应纳入判断，避免因评估输入遗漏造成错误决策。
- 评分仅提供补查建议与带来源的内部质量标记，不生成业务事实、不直接选择工具动作、不依据 irrelevant 结论硬删除首轮候选。模型输出的证据标识必须来自输入白名单。
- 首轮有候选但评分失败、输出无法校验或充分性未知时，采用一次保守补查，仍保留候选。知识适配器整体不可用、可访问范围为空、用户取消时不以改写代替故障恢复；部分库不可用时保留其他库结果和降级标记。
- 改写使用用户原话、当前有效症状、已确认产品上下文及已有知识缺口线索。缺口线索不是事实来源，不得凭空加入型号、部件、错误码、数量、故障原因或维修动作。否定和明确纠正的语义必须保留。
- 复用现有受控改写校验，补充对应的否定、纠正与漂移案例。改写无效、与原查询相同或调用失败时停止该补救尝试，保留首轮结果，不无限重试。
- 保持首轮加至多一次补检索。图片观察优先使用既有补查路径，与文本改写共用名额；不能在图片补查之后再次启动第三轮。第二轮结束后直接综合已有证据，不递归扩大检索。
- 两轮结果按稳定证据标识合并去重。保留来源、产品范围、文档版本、检索轮次和反证属性。评分不得永久删除候选；必要的上下文预算截断应保留两轮代表性证据并可追溯，不能让第二轮直接覆盖首轮。
- 诊断模块应实际接收到保留的候选，避免仅在展示日志中保留却从模型输入删除。评分标记仅为辅助，不得强制模型忽略被误判的有效内容。最终假设必须引用有效证据并映射到允许的预写计划。
- 本次以最终效果为优先，延迟和成本保留观测但不设为效果验收否决项。实现时统一调整补查与模型任务预算、run deadline、取消及恢复口径，使被选中的必要环节有合理完成预算；不保留仅为低延迟目标而提前跳过必要补查的旧门槛。仍保留有限超时、请求和轮次上限，不执行无限等待。
- 新策略受明确配置控制；不得直接等同于启用旧版 grade 硬过滤或打开所有增强项。重排序、同义扩展、FAQ 和父块扩展保持其独立配置，不作为本规格的前置要求。
- 兼容现有消息与动作 API、SSE 卡片及恢复契约。新增内部 trace 记录充分性、补查原因、改写是否采用及拒绝原因、轮次和降级情况；快照与检查点需兼容旧会话，不计划新增业务表。
- 遵守 D15 的有限预写计划。实现时修订 D19 中评分硬过滤的语义及相关预算说明，保留代码选择补查动作、两轮上限和子流程模型调用上限，不引入自主无限检索。
- 当前规格是从对话综合的实现方案；测试边界尚待按 to-spec 确认。历史“模型评分退化”与“改写未触发”必须在文档和评测结论中分开表述。

## Testing Decisions

- 主验收边界拟复用已有会话 HTTP API：创建会话、发送文本或图片、提交动作，观察 SSE、最终快照、步骤卡、证据引用及升级结果。外部模型和知识服务在已有 ModelRouter / KnowledgeAdapter 边界使用可控替身，运行真实编排代码，不为每个内部函数新建测试接口。该边界待用户确认。
- 好的测试验证用户可观察结果与必要的外部交互契约，不锁死内部节点顺序、提示词全文、私有字段结构或模型表述措辞。外部调用记录仅用于验证范围不泄漏、补查有界及取消后不再发起工作。
- 复用项目已有检索事件、重新诊断、会话恢复、取消及模型降级测试先例。新行为主要在同一个会话验收边界覆盖；改写语义校验沿用已有纯函数测试，不引入新 seam。
- 必须覆盖：首轮空结果，第二轮提供有效证据后生成正确步骤；首轮非空但不相关，仍会补查并纠正排查方向；首轮部分相关但缺少关键内容，也会补查。
- 必须覆盖：首轮充分时不补查；相关故障卡可以参与充分性判断，但单纯命中故障卡不能绕过不足判断。
- 必须覆盖：评分把首轮有效片段误判为 irrelevant 时，片段仍进入诊断，最终允许正确引用；两轮重复命中去重，第二轮不覆盖首轮独有依据；低质量候选不能仅因被保留就强制成为最终引用。
- 必须覆盖：否定表达、纠正旧症状、多轮指代、型号纠正、未知产品先澄清；无效改写不被提交检索；不同产品范围的内容不能被错误合并为当前依据。
- 必须覆盖：图片补查与文本改写竞争时只消耗一次名额；第二轮仍不足时终止补查并走既有标准流程或升级；无证据时不编造假设。
- 必须覆盖：评分失败或未知时保守补查；改写失败、第二轮无命中或不可用时首轮有效证据仍可引用；整体知识服务故障和空权限范围不触发无意义的语义补救。
- 必须覆盖：较慢但在配置预算内完成的补查不会被旧延迟门槛跳过；运行 deadline 与恢复一致；取消、主动人工与安全风险仍按已有契约处理；恢复不会重复展示证据或错误启用过期卡片。
- 真实效果测试复用现有检索评测入口和样例机制，但必须让其调用与线上一致的补救编排，不能仅验证评分、改写各自的成功率。若现有入口不能覆盖完整链路，优先接入同一编排入口而非复制业务规则。
- 冻结并人工核对预期症状、可接受计划集合、证据支持及处理结果。评测包含上述三类补救场景、已有正确案例、否定纠正与多轮样例；未标注样例仅作探索或回归观察，不作为已证实收益。
- 基线和新策略使用相同知识版本与模型配置，对不稳定样例重复运行并保留逐例记录。报告补救触发与有效补救比例、最终计划/处理结果一致性、引用支持度及错误诊断；耗时、失败率、调用量单列。不能把 0 次触发或仅更多检索命中算成成功。
- 效果验收要求：新增补救场景可以触发并修复首轮失效；已有正确案例不出现未经解释的退化；否定、产品范围和安全验收无回归。若候选保留带来噪声或误引用，先修复综合判断与上下文选择，再决定启用，不能仅凭取消硬过滤宣称效果必然提升。

## Out of Scope

- 新建通用意图分类、闲聊、订单查询或退款办理系统。
- 将所有消息统一改为检索前 LLM 改写，或引入无限循环的自主检索 Agent。
- 全量开启 rerank、FAQ、同义扩展、父块扩展等其他能力，或把它们与本次补救收益混合归因。
- 扩展产品支持范围、重建知识库、替换模型供应商、允许模型临时生成排障操作。
- 重做前端交互、真实客服派单、质保资格判定及新的业务数据表。
- 以降低响应时间或 token 消耗为本次优化目标；取消超时、取消能力或有界执行保障也不在范围内。
- 在本次规格整理任务中直接修改业务实现、开启运行配置或部署。
