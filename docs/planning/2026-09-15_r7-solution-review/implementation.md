# R7 诊断决策补强实施说明

## 实现效果

多个候选各有独立计划、同时拥有共同审核计划时，系统直接进入共同计划。后续故障卡匹配、模型排序及操作发布必须遵守同一约束，不会重新引入仅适用于单个候选的计划。

问诊阶段停止也能给出候选现象、原始问答、未能解析的回答、待确认信息和真实停止原因。已经下发但没有收到反馈的步骤会明确标为“已提供但未反馈”，不计入已执行步骤；转人工或安全限制撤销操作卡时保留该记录。

## 代码落点

- `orchestrator/app/diagnose/decision.py`：扩展 DiagnosticDecision 快照；共同计划交集；约束绑定 issue、taxonomy 版本和计划版本；进展与预算判定；旧版本问答推断失效。
- `orchestrator/app/conversation/taxonomy.py`：记录回答前后候选、回答结果、原文、问题与 input_id，兼容已有检查点的答案记录。
- `orchestrator/app/conversation/reduce.py`：无法解析但确实在回答问题的输入记账；解释等对话不计账；事实依据变化使旧决策失效；撤卡前保留未反馈记录。
- `orchestrator/app/sessions/clarify.py`：持久化统一快照，区分覆盖缺失、安全限制、证据冲突、无进展和预算停止。
- `orchestrator/app/sessions/graph.py`：故障卡、synthesize 消费共同计划约束；正常检索返回也传入已耗尽计划集合。
- `orchestrator/app/guide/steps.py`：步骤发布再次检查计划及版本约束；已有证据、去重和安全检查继续生效。
- `orchestrator/app/escalation/summary.py`：从有效诊断快照与原始问答补足摘要，不依赖 plans_ranked 是否存在。

## 进展与停止策略

1. 有有效症状证据或共同适用计划，优先继续排障；实际操作仍须通过 guide 的发布检查。
2. 已接受的回答导致候选变化或明确选择现象，视为有进展。
3. 新增症状事实清除连续无进展窗口，保留总响应计数。
4. 连续两次无进展停止：全为 unknown 时说明用户无法确认；未解析等其他情况说明没有补齐下一步所需信息。
5. 没有下一步、但持续问诊达到八次响应时按硬上限停止，文案明确轮次限制。
6. 所有响应按 input_id 去重；解释、历史问答等对话不会消耗问诊预算。
7. 空候选集合按证据冲突处理；缺少可用判别问题按系统覆盖缺失处理。

## 设计边界

- 共同操作通过“同一个审核计划、同一个版本”证明兼容，不根据相似标题合并不同计划。跨计划只有部分步骤相同、后续路径不同的情形，仍需显式配置共同计划或动作模型。
- 决策中的计划首步引用表示审核计划入口；真正可下发的步骤以 guide 完成安全与去重检查后发布的卡片为准。
- 保留已有事实与问答结构，不引入未校准概率、熵或新的并行状态机。明确更正仍按已有问诊失效策略处理；本次新增的是决策快照失效，并未实现任意事实依赖图的细粒度重算。
- 没有增加升级前的强制检索；安全停止和明确人工请求保持即时路径。
- 本次开发未部署、未变更数据库，也没有调用线上模型进行验收。
