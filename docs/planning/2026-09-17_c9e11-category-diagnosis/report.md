# c9e11 会话：品类摘要错误与首轮追问设计

日期：2026-09-17。范围：原因诊断与解决方案；未修改业务代码、历史会话或部署。

## 结论

1. 内部产品没有从移动电源切换为扫地机器人。产品状态、知识检索和排障步骤一直对应移动电源；摘要对“只知道品类、尚无型号”的情况写死了“扫地机器人”。
2. “插上手机……有输出反应吗”是症状追问，不能确认产品身份。显示“确认产品”来自前端对通用澄清阶段的固定映射。
3. 这道首问来自人工配置。选题规则只比较候选数量的二分均衡程度；两道题同分，配置第一道获选。它没有基于真实故障概率、回答成本或下一步操作价值进行选择。
4. 还有一处事实错误：用户两次反馈“无法操作”，摘要和结束回复却写“已完成”。

## 1. 会话证据

来源：`GET /admin/api/sessions/c9e11fac2dfc48b0912bd12f26c710a0/journey`。

| 上海时间 | 输入或动作 | 系统结果 |
| --- | --- | --- |
| 15:36:02 | 我的移动电源出问题了： | 识别 `power_bank`，状态 `category_only`；询问输出反应 |
| 15:36:15 | 没有 | 候选变成“无法给设备充电”“接口松动或损坏”；检索移动电源手册；下发清理输出接口步骤 |
| 15:36:21 | 第一步 `cannot_do` | 下发更换数据线和被充设备步骤 |

| 15:36:26 | 摘要 | 产品为“扫地机器人（型号未确认）”；原因写“已完成”上述两步 |

有品类字段的节点均为 `power_bank`。检索 query 为“移动电源 无法给设备充电 接口松动或损坏 出问题了”，命中 `manual_pb`，计划为 `pb_port_debris`。

`category_only` 的含义是品类已知、具体型号未确认，不是品类未知。

## 2. 品类为什么变错

`orchestrator/app/escalation/summary.py:133–136` 的逻辑是：

```text
有已确认的产品名/型号 → 使用产品名/型号
没有且 product_state == category_only → 固定写“扫地机器人（型号未确认）”
其余 → 未确认
```

它完全没有读取 `state.category`。git blame 显示该回退来自 2026-09-12 的初始摘要实现；2026-09-17 多品类扩展更新了症状、检索与计划，遗漏了这一回退。

摘要润色模型只能修改 `problem` 字段，不能修改 `product`，因此本次产品错误由确定性代码生成。

最小复现直接调用真实 `build_summary`：

```text
输入：category=power_bank, product_state=category_only, product_confirmed=None
期望：移动电源（型号未确认）
实际：扫地机器人（型号未确认）
AssertionError
```

对当前目录 20 个品类逐一调用同一路径，19 个非扫地机品类全部显示错误。该结论针对同一 `category_only` 渲染路径，不代表这些品类都发生过线上故障。

## 3. 为什么在“确认产品”阶段问输出反应

后端 `sessions/clarify.py` 的决策入口同时负责三件事：确认产品、澄清症状、核对产品冲突。它们都可经由 `disambiguate` 阶段。

首轮真实决策可离线复现为：

```text
product_state = category_only
category = power_bank
clarification.reason = symptom
question = 插上手机或其他设备后，充电宝有输出反应吗（指示灯亮或设备显示充电）？
```

前端 `frontend/src/state/progress.ts:25` 把所有 `disambiguate` 固定显示成“确认产品”，提示为“分清是哪台设备”。因此后台正在了解故障，界面仍显示确认产品。

追问症状有必要：用户的“出问题了”没有说明具体异常。型号也不必一律追问：只有后续操作确实依赖型号时，型号才是必要信息。

## 4. 为什么偏偏选这道题

`config/symptom_taxonomy.yaml:64–94` 配置了移动电源的六种候选故障，以及两道二分题。

| 问题 | yes 分支 | no 分支 | 选题分数 |
| --- | --- | --- | --- |
| 有输出反应吗 | 自身充不进电、掉电快、发热、灯异常 | 无法给设备充电、接口松动或损坏 | min(4,2)=2 |
| 问题在给充电宝本身充电时吗 | 自身充不进电、灯异常 | 无法给设备充电、掉电快、发热、接口松动或损坏 | min(2,4)=2 |

`conversation/taxonomy.py:71–80` 选择分数最高的题；同分时保留配置中先出现的题。离线只颠倒两道题顺序，首问就变成了“问题出现在给充电宝本身充电的时候吗”。

用户回答“没有”后，`interview_answer` 按 no 分支过滤候选。剩余两种候选都对应 `pb_port_debris`，`decide_symptoms` 返回 `same_applicable_plans`，无需分清两者就开始共同计划。

“有共同适用动作即可继续”这个原则可以保留；问题在于生成候选集的证据规则不充分。

### 设计缺口

- **观察不能直接当成排他诊断。** 用户说没有输出反应，只能支持该观察，不能据此排除自身充不进电、指示灯异常等其他情况，也不能确认接口损坏。
- **一道题混合了两个观察。** “充电宝指示灯亮”和“手机显示充电”可能不同；回答“有”不能说明是哪一个，后续需要的事实可能仍未取得。
- **缺少症状定位。** 用户尚未说明问题发生在输入充电、对外供电还是其他使用环节，就先沿一条技术分支追问。
- **配置被当成真实排查依据。** 当前词表和移动电源计划标记为“人工演示样本，待真实资料替换”；分支逻辑和操作适用性不能仅靠结构校验认为有效。

这些是代码与配置暴露出的设计风险；本次会话并没有证据证明设备的实际故障是哪一种。

## 5. 为什么两次无法操作就结束，还写已完成

`config/plans.yaml:178–189` 明确规定：第一步 `cannot_do → s2`，第二步 `cannot_do → EXHAUSTED`；第二步只有 `not_solved` 才去第三步。

因此这次是配置路径结束，没有证明用户完成了检查，也没有证明所有可能操作都已尝试。配置中仍有第三步，但不能仅凭其存在就盲目跳转；是否可以绕过第二步，需要核对动作前置条件与依据。

`next_action_text` 把 `steps_executed` 中所有标题拼进“已完成{steps}”，没有检查反馈。列表中包含 `cannot_do`，因此形成事实错误；前后端复制文本也统一叫“已执行步骤”。

本会话真实可表述为：

> 移动电源，型号未确认。用户表示连接设备后没有输出反应。清理输出接口、更换线材和设备两项操作均暂时无法完成，尚未取得检查结果。当前自动排查未能继续，已整理记录供人工接续。

## 6. 从第一性原理推导方案

目标是在尽量少的用户投入下，给出适用、有依据的下一步；无法继续时准确传递已知事实。产品身份、用户观察、待验证原因、操作执行结果是不同的信息，不能相互替代。

### 第一层：修复确定性的事实错误

1. 产品展示按已确认产品名/型号 → 当前品类目录名称 → 未确认的顺序渲染。品类名复用目录来源，不再为任何品类写专用回退。未知品类保持未知。
2. 结束回复、摘要和复制文本都依据真实反馈区分“已执行未解决”“无法操作”“已解决”“已提供待反馈”。`cannot_do` 不得变成已完成或阴性检查结果。
3. 以活动问题的事实为来源，避免从整个历史对话重新猜产品；保留现有问题隔离规则。

### 第二层：让界面反映正在取得的信息

产品澄清显示“确认产品”；症状澄清显示“了解故障”；冲突澄清显示“核对设备信息”。可以沿用现有 `stage/substage` 传递目的，无需先新增一套流程系统。刷新后的快照与流式进度必须一致。

单纯把整个 `disambiguate` 改名“信息确认”能缓解文案矛盾，但不能让用户知道本轮到底在确认什么，不作为完整方案。

### 第三层：先取得有效观察，再决定问什么或做什么

1. 用户只说“出问题了”时先问实际异常，例如：“充电宝具体哪里不正常？例如给手机充不上电、充电宝自己充不进电，或其他现象。”允许描述多种现象、其他情况和不确定。
2. 用户已经明确说“给手机充不上电”时，直接使用已有事实，不重复首问。只有能影响下一步的缺失观察才需要追问。
3. 将一个问题绑定一个可解释观察，例如手机是否显示充电；需要充电宝灯状态时另行取得。没试过、不能观察与“没有”分别记录。
4. 答案先记录为有原话依据的观察；仅在有可靠规则支持时才排除某个原因。未提及或未选择不等于该现象不存在。
5. 在现有 `diagnose/decision.py` 中结合动作适用条件、所缺观察、操作负担与用户意愿选择下一步。保留共同计划能力，但不依赖错误删减后的候选集。
6. 对“无法操作”记录具体限制；当限制会改变后续动作时再追问，存在有依据的替代路径才继续。没有适用动作就如实说明限制，不生成虚假的完成记录。

最低必要复杂度是：统一事实来源、明确问答目的、区分观察与假设、按真实执行结果渲染。概率诊断引擎、自动学习最优问题、通用流程编辑器均为可选工作，本问题不需要先引入。

## 7. 验收条件与验证记录

修复后的回归至少覆盖：

- 每个已登记品类在 `category_only` 下保持正确品类；缺品类时不猜扫地机；已知型号时保留型号。
- 原始四轮交互最终为“移动电源（型号未确认）”，两步均为无法操作，回复与摘要均不得写已完成。
- 症状追问阶段显示“了解故障”，流式更新与刷新快照一致。
- 只说“出问题了”时不提前锁定输出故障；已明确输入/输出现象时不重复问已知内容。
- 灯亮但手机不显示充电、自身充不进电且无法对外供电、没试过、复合症状等回答不被错误压成一个排他分支。
- `cannot_do` 不写成检查失败；不会自动重发同样无法完成的步骤；存在有依据的替代动作时可选择，否则如实结束。
