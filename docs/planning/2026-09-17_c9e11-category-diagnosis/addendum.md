# 复评：产品确认是否应当成为统一前置关卡

## 2026-09-17 用户反馈复核

同意用户提供分析的核心结论：不应一律要求用户确认产品；只有未决信息会改变后续适用动作、检索范围或服务处理时才追问。上一轮“操作前必须确认对象”的表述容易被理解为统一的显式确认关卡，应改为“已有身份信息足以支持当前动作”。

本次完整读取 clarify.py、plans/models.py、faultcards/library.py、warranty/service.py、sessions/l3.py、conversation/commands.py 和现有澄清测试，未修改业务代码。

## 需要校正的实现描述

1. “只有多 SKU 一种显式确认”过于绝对：照片候选品类确认、产品冲突澄清也在询问用户。多 SKU 是专门的产品选择卡分支；commands.py 也允许有原话依据的文本回答转成 select_product 动作，不强制点击按钮。
2. “后来提到不同型号就冲突澄清”不准确：唯一命中的新 SKU 在 decide 中直接纠正；无 SKU 命中但新旧品类不同才进入所引用的 conflict 分支，多候选则再次出卡。
3. “只在确认改变动作时才问”是合理设计原则，尚不是所有代码路径的不变条件：当前多 SKU 分支只看候选数量，未先比较它们的适用动作是否相同。
4. `category_only` 的成立依据是品类信息，不依赖是否存在通用计划。无词表/排查覆盖的已知品类仍保留该状态，由后续决策表达覆盖不足。
5. 产品澄清上限绑定同一 subject 和实际问句，不是整个会话全局最多两轮。
6. `warranty/service.py` 在“已查到订单但当前设备没有 SKU”时返回 needs_manual_check；这不能概括所有服务入口。

## 服务流程的实际行为

`sessions/l3.py:99–114` 先查订单；在未达到 confirmed_sku 时，从订单 SKU 反查目录，匹配到范围内产品则自动填入 product_confirmed / category / confirmed_sku。此处不是主动询问型号。

因此不应提出“一进服务流程就补一次型号确认”。应先使用已有订单、设备和用户表达；只有无法建立当前设备与订单的关联、出现矛盾或缺少必要信息时再补问。订单商品与当前故障设备的关联是否充分，是值得单独验证的边界；本轮没有回放该路径，不把它宣称为已复现缺陷。

## 保留的结论

- 当前移动电源四个计划均为 category_generic，启动这些通用排查不必先强求型号。
- 不能由此推导型号在所有后续环节都无价值，型号仍可能改变检索资料与服务办理。
- 产品摘要错误不证明应增加产品确认轮次；摘要必须忠实表达实际身份精度。
- 首张步骤卡回显当前采用的产品/品类，便于用户纠正，属于可选改进，不新增阻塞确认。
- 首问是否有效、其答案是否被过度推断，与是否强制确认产品是两个独立问题；原报告中的症状问诊分析仍需单独处理。

验证方式：本轮为源代码与既有测试定义核对，未新增/运行测试，未操作真实服务或会话。

### Standards：规范评审

### Spec：规格评审

保留按目录读取品类名称的修复；这直接解决 category_only 被固定写成扫地机器人的根因。保留区分 cannot_do 的方向，但原修改只修复结束原因：结束回复仍写“已试步骤 / 已经做过”，前端展示和前后端复制文本仍称“已执行步骤”，反馈还直接暴露英文枚举。该问题评为 P2，现已补齐。

最终实现：

- 结束原因分别表达“已操作并解决”“已操作但未解决”“无法操作”；无反馈记录时不声称已尝试。

- 结束回复使用“当前问题和排查记录”，不把无法操作表述成已经做过。
- 产品仅知道品类时仍标明“型号未确认”；不增加统一的产品确认关卡。
