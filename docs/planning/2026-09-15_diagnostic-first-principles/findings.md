# 架构证据

- R4 实例：计划安全警告被当作设备风险；先前 drop 修复是保守止血，尚不能识别有效的条件性安全提示。
- R7 实例：旧事实编码把本轮 narrowed 状态覆盖成 superseded；澄清层同时依据关键词否决结构化症状。
- ISSUE_FIELDS 在会话顶层和 issues 内复制大批业务/派生状态；reduce_turn 与 persist_issue 往返拷贝，容易出现多处写入与过期覆盖。
- _diagnose_outcome 直接选首位假设进入计划；症状分类与选择可执行下一步耦合。
- route_entry 存在意图/阶段/卡片/业务布尔字段交错控制，diagnose 和 dialogue 两条输出路径未保证相同操作约束。
- AuthorizationGate/ActionRegistry 已具有政策、证据、授权与幂等保护，应保留这些实现，不应重造执行底座。
- 既有 11_conversation-facts-and-answers.md 已提出来源归属、统一事实读取与解释不授权；重做应把该原则落实到诊断而不是新增平行框架。

## 实施验证补充
- 诊断推断不能随任何新增症状一起失效：仅显式纠正撤销相关问答推断，追加的独立症状保留历史答案。
- 已完成会话可能保留评分卡，解释入口必须优先识别已解决状态，不能把它说成待确认产品/凭证。
- 预写操作来源需独立于在线检索返回；增加 approved_plan 来源事件，前端显示“预写排障资料”。
- 去掉诊断失败自动凭证收集后，业务请求仍需完整保留。将诉求投影收拢进 reducer，并确保跨订单时本轮明确退款诉求优先于旧换货诉求。
- 全量测试与真实接口结果见 implementation.md。上述变更均为用户授权设计实施范围，原始会话历史未改写。
