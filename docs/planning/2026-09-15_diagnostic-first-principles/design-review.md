# 诊断系统的第一性原理审视

日期：2026-09-15。本篇保留设计提案；后续实施结果见 [实施记录](implementation.md)。

## 结论

建议重做「从事实到下一步」的诊断决策模块，收拢重复判断与状态写入，统一操作建议的发布入口。现有 FastAPI、LangGraph、PostgreSQL、模型路由、知识适配器、业务动作授权与幂等可以保留。

判断依据是两条已验证的会话，而不是抽象的架构偏好：

- 30b15e97b9674aebaa97cc1202386781：手册中条件性安全提示被判为用户已报告危险。
- 2702fe9bdd4942e9ab84122d42a6848e：有效回答已经缩小候选范围，却被历史编码覆盖后判为澄清失败。

它们说明：系统缺少一个权威位置来决定「哪些是当前设备的事实、下一步为什么允许或不允许」。现有多个机制局部正确，组合后却互相否决。

## 1. 从目标推导设计

用户希望以合理成本解决问题。自动客服能可靠交付的最小单位是：一项有依据、适用、风险可控的下一步，以及检查其结果的方法。暂时不能推进时，应给出真实原因与可以接续处理的记录。

据此推导：

1. 不必先确定唯一硬件根因才能提供安全检查；但每个检查必须具有适用依据。
2. 不确定性应限制某些动作，不应自动终止所有帮助。
3. 提问是获取会影响下一步的信息，不能为了填满字段或走完图而提问。
4. 模型能理解与提出判断，但不能凭措辞创造设备事实、授权或执行成功。
5. 建议执行不等于已经执行；摘要完成不等于人工已经接手；转交不等于解决。
6. 所有入口都必须遵守相同的操作约束，用户换一种问法不能绕过。

以上是设计约束，不需要先搭建评分平台或再加一个模型。

## 2. 六处需要重做的设计

### A. 事实和推断的责任归属

当前问题：结构化 facts、symptoms、symptom_codes、symptom_interview、risk_cases、clarification 同时参与业务判断；ISSUE_FIELDS 又在顶层与 issues 内往返复制。R7 的实际覆写发生在 reduce_turn，重复存储和多点写入放大了推理难度。

建议：保留已存在的 issue 原始事实及来源记录，明确区分三种数据：

| 数据 | 例子 | 更新规则 |
| --- | --- | --- |
| 用户报告/观察/工具结果 | 用户称启动不了；按当前问题回答无充电指示 | 保存来源、对象、时间、问题引用及是否被纠正。用户报告不自动等于经测量确认的事实。 |
| 诊断判断 | 供电或充电方向值得排查 | 引用以上证据，可重新计算；不得反向修改原始报告。 |
| 本轮决定 | 询问某项缺失信息、展示某个检查或转交 | 由当前事实和能力重新决定，不能成为下轮永久症状。 |

将诊断判断集中在一个模块写入。读取方消费同一份只读视图，不再各用关键词推导第二套结论。订单事实继续归 BusinessContext，案件状态继续归 Cases，不把一切塞入新的万能事实库。

「不开机」和「不充电」可以同时成立，分类结果只是排查方向，不能强迫原始症状互斥。

### B. 安全判断的对象

当前问题：用户报告、视觉观察、步骤文案共用文本匹配语义，导致指导内容被升级成设备风险。

建议分开两项判断：

- 当前设备是否存在需要预防性限制的风险信号：看带来源的报告/观察，明确危险报告应先采取保护性限制，不能等待完全确证才保护。
- 待发布动作是否适用且安全：看动作、前提、停止条件与当前限制。

一个经过审核的步骤应把操作正文、适用条件、停止条件分别表达，而不是对整段文本做敏感词命中就推断设备状态。现有 PlanStep.caution 等字段可以演进，不另建平行 SOP 平台。

安全风险可以阻止继续充电或开机，仍允许读取订单、说明风险和准备人工接续；具体维修/换货审批由对应业务政策决定，不将「禁止物理操作」粗暴等同于所有业务都不可办理。

先前将步骤命中 R4 改为 drop 是保守止血：避免假造用户风险，也不会放行危险步骤；但会连正常的安全提醒一并丢弃，不是最终设计。不能靠删掉真实用户的安全词来解决这个问题。

### C. 澄清与症状分类

当前问题：以固定两次追问作为失败代理指标；旧词面判定不认可已有结构化症状；有效问答状态被历史编码盖掉。

建议只在「缺少的信息将影响下一项允许的行动」时提问。例如能否启动已知，不再重复；充电指示未知，且能决定走何种检查时再问。

判断次序：先应用当前回答，判断是否已有可执行下一步，再判断是否需要追加问题。若问答已经提供足够信息，次数达限也不应改判为无法理解。

保留对重复、无效追问的保护，先用可解释的条件：是否得到有效回答、是否补齐当前所需前提、是否已问过相同问题。暂不引入信息熵、动态置信度评分或把 2 改成 5。整体交互成本上限可以保留，但到限应诚实解释成本/能力限制，而非伪造症状未知。

### D. 方案选择与能力覆盖

当前问题：先将症状归入唯一候选，再选排名第一的计划。一个缺少证据的高排名计划也可能带入不适用内容；而不开机/不充电没有可执行计划。

建议让「能做什么」参与决策：已审核的适用计划/步骤及业务动作，明确产品范围、前提、禁忌、预期结果与停止条件。选择前检查适用性，再用模型排序辅助。

若多个可能原因允许同一个低风险检查，无须为了分出唯一原因而继续追问；如果没有适用方案，明确承认能力缺口，不借用无关计划，也不让自由回复生成替代方案。

应先补齐在本项目会话中已出现的不开机/不充电审核方案。每条完整覆盖：输入症状、必要追问、允许的检查、结果反馈、停止及转交；不继续只扩充类别词表。本文没有验证哪项具体设备操作可放行，新增 SOP 仍需相应设备资料和审核依据。

### E. 决策与表达

当前问题：diagnose/guide 路径检查操作，自由 dialogue 路径又可给新操作建议。第四轮的「还有其他方案吗」绕开了正式步骤流程。

建议全部入口先得到同一个决定，再选择文字、步骤卡、摘要等表达形式。解释可以描述已有方案与原因，但不能新增未获准的动作、诊断结论或办理承诺。

对高风险操作和承诺使用受控内容；如果保留模型润色，限定它只能改写经过验证的内容，并提供模板降级。不要仅靠一条系统提示保证安全。

业务写操作继续通过现有 AuthorizationGate 和 ActionExecutor，不从聊天表达层调用。物理排障建议与后台写操作不必用同一个授权类，但发布时必须服从同一个本轮决定。

### F. 升级与结束状态

当前 R 编码混合了安全风险、用户请求、预算耗尽、计划缺失、信息不足与范围外。它们可以继续用于审计兼容，但不宜继续充当一套含糊的业务状态。

内部决定应区分：缺什么信息、缺什么能力、什么动作受限、是否用户要求人工、是否工具暂不可用、是否需要人工政策判断。用小型结构化理由记录来源及未完成事项，不需要引入庞大分类体系。

「停止自动操作」「可继续问答」「人工转交进度」「问题是否解决」分别有自己的事实。安全停止后仍可以解释；整理摘要只叫 prepared；实际交付并收到回执才叫 submitted；用户/工具结果证实解决后才能 solved。

## 3. 建议的最小架构

```text
新输入
  → 语义理解：提出事实变更/问题回答/用户请求，带原话来源
  → 验证并更新当前 issue
  → 诊断决策：依据事实、风险、待答问题和可用能力决定下一步
  → 执行被允许的读取/发布被允许的检查或业务方案
  → 表达结果，等待用户或工具结果，再进入下一轮
```

建议新增或收拢为一个诊断模块，而不是给每个环节新增服务。示意外部接口：

```text
advance(issue, accepted_input, available_capabilities)
    → updated_issue + next_move + reason + evidence_refs
```

next_move 可为需要信息、读取信息、展示检查、提出业务方案、转交、回答或结束。本轮事实与决定在现有事务/检查点约束下提交；外部写操作仍通过现有持久化执行记录与幂等键。模型、知识、业务后端沿用现有 Adapter，不为假想变体新增接口。

这一 Interface 是调用者和回归验证共同经过的 Seam；调用者无需知道 MAX_CLARIFICATIONS、narrowed/superseded、各层旧路由优先级等内部约束。订单/案件另有已有所有者，不进入新的大而全 reducer。

LangGraph 保留为执行编排器。图节点展示执行顺序；诊断知识和状态优先级由诊断模块负责，不继续散落在更多 route_after_* 与意图例外中。

## 4. 保留与删除

保留：原始输入/事件溯源、issue 设备隔离、有效问题 ID 绑定、用户确认、幂等、取消与恢复、模型接入、知识适配、案件及后端事实所有权。

逐步替换/删除：

- 澄清中与结构化事实冲突的文本兜底最终裁决。
- 多处对 asking/narrowed/superseded 等派生状态的独立写入。
- 把知识警告变为设备风险的逻辑。
- 正式诊断停止后可绕过约束的自由操作建议。
- 把各种 R 编码当成统一「用户问题不清楚」的原因生成。

不建议此时更换 Agent 框架、增加多智能体、上知识图谱、重写存储或建设通用规划引擎。它们不能直接消除已证实的来源混淆和多处裁决。

## 5. 实施顺序与验收

### 第一步：先锁住真实失败路径

把两条会话变为端到端决定契约的回归输入：真实理解结果与已捕获证据固定，模型生成另做少量真实会话验收。修复事实覆盖、条件警告误判和摘要原因。

### 第二步：以不开机/不充电跑通完整纵向路径

收拢该路径的诊断所有权、补审核方案、统一发布入口。确认可解释、可继续、可停止和可接续。先做少量确定性的输入分支，不追求一次支持全部故障。

### 第三步：逐条迁移并删除旧裁决

每迁移一个流程，就撤掉该流程的旧规则写入，避免两套决策长期并存。已有 checkpoint 通过显式版本转换或只读兼容投影进入新模块；不清空历史事实，不自动撤销已有风险限制。镜像与配置一起校验版本，避免之前遇到的重启不兼容。

验收重点：

1. 用户明确「启动不了」后不会再被问同一个已知事实。
2. 两个有效否定回答保留结果，不能被旧编码覆盖。
3. 手册出现「若有焦味应停用」不会被说成用户报告焦味；用户真实报告危险仍先保护。
4. 改问「还有其他方案吗」不会得到越过约束的新操作；同一组事实在不同表达路径得出一致限制。
5. 无计划、工具故障、用户信息缺失、真实安全风险分别给出正确理由；人工未接收不能说已经接收。
6. 切设备、纠正事实、重复输入后，约束、问题与执行结果不串对象、不重复执行。

通过这些用户行为契约判断完成度，不用新增多少节点、覆盖了多少意图标签或单元测试数量代替交付质量。

## 6. 关键依据

- `orchestrator/app/conversation/reduce.py`：ISSUE_FIELDS 投影、reduce_turn 中旧 codes 覆盖 interview、persist_issue。
- `orchestrator/app/sessions/clarify.py`：文本兜底、症状判别状态和 R7 计数。
- `orchestrator/app/sessions/graph.py`：route_entry、_diagnose_outcome、guide、dialogue。
- `orchestrator/app/conversation/policy.py`：风险来源、限制与持久化。
- `orchestrator/app/conversation/answers.py`：已存在的对象/来源读取契约，应扩展贯彻而非废弃。
- `orchestrator/app/actions/gate.py` 与 `registry.py`：已有授权和执行能力，应复用。
- `docs/planning/2026-09-15_session-r7-analysis/report.md` 与 `docs/planning/2026-09-15_session-safety-diagnosis/report.md`：真实会话与离线复现。

这是针对已检查诊断路径的设计判断，不是对所有订单、售后政策或多任务流程已完成全面审计的宣称。
