# diagnosis-replanning 需求评审与实施

评审对象：`docs/claude/spec_2026-09-18_diagnosis-replanning.md`。原需求单保留，本文件记录采用范围、修正理由及实现结果。

## 结论

接受观察驱动的候选重评、配置路由闭合校验、排除原因可观测。采用常规候选与观察重评两级；保留型号、资源、安全、已执行与已耗尽边界。原会话的 UVP 计划可以由新观察重新进入候选，不需要修改原始症状事实。

## 需要修正的要求

| 位置 | 问题与例子 | 处理 |
| --- | --- | --- |
| A1 category | 型号适用范围承载资料与操作的实际适用性，不是模型推测。A1289 已显式排除通用长按复位计划；删除型号限制会重新开放它。`allowed_for` 本来就包含未被排除的品类通用计划。 | 不放宽型号，不增加重复的品类兜底阶段。 |
| A1 confidence | “没有候选”不能证明低置信度候选适用；自动降到任意分数可能把弱匹配直接变成操作。 | 保留 0.3 阈值；只有明确观察满足计划条件时，才通过独立观察路径重选。以后若要使用弱匹配，应先设计确认问题与评测。 |
| B1/B2 承接判定 | 只看同品类及 `gate != excluded`，无关计划也可能算作承接者；SKU 有交集不能证明声明方每个型号都有路。 | 承接者必须是观察声明方或显式引用该观察的计划；逐一检查声明方可进入的型号，允许多个承接计划联合覆盖。 |
| B1 第③条、B3 | 强制承接计划包含声明方全部症状码，与“观察可跨旧分类重选”冲突；为输出侧 UVP 排查添加自身输入故障码会扩大无观察时的召回范围。 | 不增加 `pb_no_input`，校验实际观察路由与型号范围。已有跨症状回归保留。 |
| B 校验版本 | 旧版计划在内存库中不生效，不能靠旧版承接者让新版缺口通过。 | 引用检查、路由检查与运行时使用同一套最高版本计划。 |
| C 输入归属 | 同一句“设备不在身边”可以同时回答观察题和更新操作条件，不宜强制只选一个归属。 | 接受配置声明的 unknown 短答，同时更新资源不可用；资源恢复后重新询问。通用 resolver 仍按原需求单另行设计。 |
| 1.2 统计推论 | R4 零步骤可能是正确的安全停用；零步骤升级的混合统计不足以证明所有情况都应该放宽。 | 保持安全限制优先；此次回归直接验证错误路径，不用该占比作为自动放宽依据。 |

## 已实施

- `decision.py` 抽出候选构造，先常规排序，再按观察重评；记录 `relaxed_level`、已评估级别和带级别的排除原因。
- 沿用已有 `reassess` 的 `guide_trace`，不再重复添加内容相同的事件。最终步骤发布也核对观察及型号，避免选中了却被旧分类再次阻断。
- `library.py` 在加载时检查路由选项。纯记录观察不要求新增分支；声明计划本身仍适用时也可继续原计划。此检查保证静态局部承接，不承诺在资源不足或所有步骤已执行后仍有操作。
- 管理端节点摘要仅保存枚举原因及计数；Journey 显示本轮候选评估级别，节点详情解释排除原因，不保存新增的用户自由文本。
- A1289 的未知观察选项补充设备不在身边的明确短答；相应请求保持可补答。资源恢复后重新询问，不让 unknown 变成永久死路。
- 保留上一阶段的现象改选、歧义澄清、旧卡片撤回、执行历史保存和恢复按钮。
