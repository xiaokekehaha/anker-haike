# 十轮开发、验证与真实案例复测

目标：在独立分支上，将官方案例暴露的问题按根因修复，完成十轮“定位 → 设计/需求 → 开发 → 自动验证 → 真实测试 → 复盘”，交付可供次日验收的代码和记录。无法合理解决的资料缺口、超出资料能力的问题据实登记，不把所有失败归因于官方刻意设坑。

起点：`eefc1a4`，继承上一阶段尚未提交的 R1–R5 修改；新分支 `codex/official-63-ten-rounds`。既有设计、需求和 295 项自动回归见 `../2026-10-09-1902_postfix-design-and-requirements/`。这些修改尚未真实复测，不能算本次十轮已经完成。

## 不变约束

1. 每轮先写具体问题与证据、通用规则、验收条件，再开发；不以案例编号、订单号或单条 QA 白名单调整生产决策。
2. 每轮至少跑全部 63 单原始案例，保存来源、完整轨迹、运行版本和逐案评判；补测变体与相关自动测试单独统计。
3. 每轮固定实际运行文件，检测到版本变化则拆分或重测，不能混算。到真实人工入队即比赛边界；不模拟人工审批，不虚构用户材料。
4. 正确澄清、资料缺口、业务允许的终点与系统错误分别记录；自动 SOP 分支分数不能代表内容正确率。
5. 确定性测试使用假模型和假知识库；真实案例走独立的真实评测驱动。原官方资料和历史报告不改写。
6. 自主决定常规实现，不能解决的问题写清证据和原因；不为凑轮数强行改代码。若某轮无需修改，记录复查依据并继续稳定性验证。
7. 不提交、不推送、不发布到外部环境。允许为本地验证启动/更新服务；不删除原有会话，不操作其他项目数据库。

## 工作顺序

- 建立本轮计数、测试驱动和版本证据；验证并真实复测 R1–R5。
- 基于第一轮结果推进 R6 知识节点、R7 请求证据、R8 已做动作及 R9 统计投影；每组有独立设计/需求与自动回归。
- 每轮处理新失败及保护正常流程，完成十轮全量；保留每轮受测版本、改动、缺陷和残留。
- 最后按原始目标逐项审计：十轮齐全、分支及代码完整、验证可复现、未解决项有分类和证据、最终报告便于人工验收。

开发开始后本文件冻结；补充设计写 addendum.md，各轮记录在 rounds.md 与对应 round-NN/ 下。
