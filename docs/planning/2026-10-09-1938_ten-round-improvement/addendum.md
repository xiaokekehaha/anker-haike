# 设计与需求补充

## 第 1 轮：完整 CI 揭示旧测试前提

问题：`make ci-local` 得到 988 passed / 5 failed / 2 skipped。三项巡检失败源于假诊断输出没有必填 `applicability` 和 `supported_symptoms`，以前 schema 失败后又走 retrieval_order 兜底，所以错误夹具也能出卡。另外两项检索事件测试关闭诊断模型却预期仍有操作卡。

方案：修正测试输入，给成功场景提供当前模型协议要求的、有来源的适用性结果。检索成功、证据事件、重复输入复用、型号更正和旧卡拒绝等断言保持不变。模型不可用时无步骤这一行为已经由 R1 回归覆盖，不恢复不安全兜底。

需求 R1.1：`inspection/scenarios.py` 中语义召回场景的假诊断输出符合当前协议；`test_retrieve_events.py` 成功场景明确提供假解释器与假诊断输出，重复输入仍不得重复检索/重发证据。只改测试前提和离线巡检数据，不更改生产判断门槛。修改后跑两文件，再复现完整 CI。

## 第 2 轮：分类回归口径

首轮相关测试 79 passed / 1 failed，唯一失败是旧断言“操作节点至少占 85%”。它的分母只含多段步骤，遗漏了 465 条单段答案；统一入口后分母改变，而且把说明错分为操作反而更容易通过这一断言。改为核对全量 QA 均有非空节点，并明确检验说明与硬件结论的类型；保留其余错误码、分支、媒体及流程断言。没有为通过测试恢复默认 action。

扩大回归 230 passed / 1 failed：T28 旧测试要求客户再次对“硬件结论”点击 not_solved，恰是本轮要消除的错误交互。更新为一次重启失败后直接进入资料收集，同时断言实际执行计数为 1、handoff 节点留痕、没有第二张操作卡。

## 第 4 轮：分支不能只修当前游标

代码核对发现 decide_next 用数组查找未执行步骤，prepare_step 跳过已回答问句时也只走默认边。仅修当前游标会在暂停、重试或重放时失效。补充需求：Plan.next_step_id 统一解释反馈和选项；决定下一步时从入口沿已记录答案重放，消费问句时也使用同一边。历史答案是分支选择的依据，不新增一份可能冲突的分支状态。加入真实 HTTP 分支验证，防止只测 verify 输出游标而漏掉最终发卡。

## 第 7 轮：备用入口与测试证据

首轮 101 passed / 7 failed。六个失败来自三个旧 T9 假解释器没有提供新协议的请求引文；补入原文实际存在的物流请求，保留交接、摘要刷新、改口和人工驳回等原断言。另一个 T2 失败是真实入口问题：模型关闭和上下文超预算两条备用路径直接返回关键词结果，绕过物流纠偏。统一经过 logistics_correction，避免“replacement accessories kit”被当成换货申请；没有放松额外查询校验。

新增测试首次收集失败源于 pytest 保留参数名 request，改名后继续。随后相关 122 项通过；审查 HTTP 测试时发现未启用业务服务，不能覆盖排序后的查询校验，需启用真实内存业务服务后重验，不能仅依赖空队列断言。

启用业务服务后新增 14 项通过，完整 CI 为 1094 passed / 2 failed / 2 skipped：失败均为固定提示开销基线。新协议的固定输入实测 4573 token、schema 2599 token，超过旧基线 4400/2560；实际 16000 token 预算、生产形状单次模型调用、全部密集历史/多对象/来源/风险保护测试均通过。经容量核对，将告警阈值更新为 4630/2650，生产预算不变。该改动反映新需求的已知成本，不删除预算保护。

## 验收轮数调整

用户补充“如果达到预期可以提前终止，不用10轮完整”。据此十轮改为上限，允许在已知问题经过修复、离线验证、真实全量复测及文档审计后提前结束。不能把尚在修复中的 R7 额外查询和明确维修诉求遗漏当作达到预期；不能把仅停在追问或人工边界的案例当作设备问题已解决。无法确认的官方资料问题与下一阶段知识结构改造单独留给用户验收。

## 第 9 轮：发现相互矛盾的请求定义

R7f 不仅是服务端引文嵌套过严。复读完整模型 schema 后发现 diagnostic_request_quote 的字段说明仍写着“须包含对应现象”“办理退换不填”，与新需求“退换或维修分别保留”冲突，提示正文另有一处旧要求。统一三处定义：请求与现象分别有来源，只有纯背景或仅办理不补诊断。这是协议内矛盾的修复，没有增加针对 fix it 或 T53 的正则。单测不能保证真实模型遵循新定义，仍需全量实测。

第八轮只读统计采证脚本首次 JSON 导出因 UUID 类型报错，显式转字符串后重跑成功。真实投影确认 T9=awaiting_human、T53=closed_unresolved、T40=consult_answered；T40 后者是待修的问题，不作为正确结果。

## 第 10 轮：评测摘要不能替代完整事件

初读 T40 的 instruction 摘要时认为“article below”无链接；读取完整 step_cards.media 与 rv-0073 源文后，确认 URL 保留。这是评测工具省略字段导致的误判，已向用户更正；inspect_round.py / compare_rounds.py 增加 media、caution、expected_result，全部 63 单重比无其他新差异。T32 的图片同样保留。不能因此给生产解析器增加新的缺口规则；rv-0371 末尾确实缺链接的独立证据不变。

同版本第十轮新增的 T23 风险分类与 T35/T53 终点粒度不稳定，足以否定“全量业务通过”。这些问题已经定位共同边界并设计 K8/K9；按用户允许记录复杂残留后结束本次迭代，不再为通过固定案例扩大词表。最终报告同时记录已修、未修和未覆盖。
