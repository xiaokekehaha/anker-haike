# 第 6 轮：区分“尚未抽取”与“用户不确定”

## 问题与追踪

第二轮 T29/T39/T41 的原文已有托盘排水、离线、烘干现象，intake 却只抽出操作或没有抽出事实。R3 将整个表单描述保存成 polarity=uncertain 的 symptom，适用性层据此强制泛问哪个部件。抽取状态被误写成用户语义；这不是检索召回为空的根因。

## 方案

将未解析表单描述保存为问题内的原始输入证据 unparsed_problem（原文和来源 input_id），不放进症状事实，也不给它猜极性。它可以支持召回和人工查看，不能单独授权操作。

在语义入口增加一次有界补抽：仅在当前意图确为 report_problem、结构化描述存在、没有任何合法症状事实/纠正且没有精确错误码时，针对该描述抽取事实。复用 intake 路由但使用小的专用 schema；不提供候选知识，避免看着检索结果反向编造症状。只有逐字引文确实在该字段中的 symptom 才合并回原解释器结果；否定和不确定原样保留。已有明确事实、自由邮件、查询类意图、模型不可用不额外调用。

补抽失败或为空时保留原文与抽取失败状态，绝不改成肯定事实，也不走检索第一名兜底。需要追问时明确已保留描述，仅请用户确认主故障，不以 uncertain 模板制造原话歧义。该成本仅发生在缺失的结构化描述，一次补抽，不循环重试；底层路由既有重试预算仍适用。

## 需求与验收

| ID | 需求 | 验收 |
| --- | --- | --- |
| R3.2a | 原文与语义事实分离 | action-only/empty intake 不产生 uncertain symptom；原文与来源仍可恢复、检索 |
| R3.2b | 独立、一次、可核对的补抽 | 原文无托盘症状时不能凭空增补；只返回操作、引文越界、模型失败不授权步骤 |
| R3.2c | 真不确定/否定保持 | does work 的明确 uncertain、明确否定、已有症状或错误码、纠正不触发补抽 |
| R3.2d | 链路与隔离 | HTTP 首封补抽后使用确认的事实查库发卡；原文证据按问题持久化，后续有依据的症状可完成解析；不引入额外任务或物理建议 |
