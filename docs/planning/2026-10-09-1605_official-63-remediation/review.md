# 官方 63 案例修复方案评审

评审人：Codex。日期：2026-10-09。对象：本目录 `plan.md`。代码基线：`bf29496`。

## 结论

**同意总体方向，但建议修订下面六项后再按方案实施。**

保留系统主体、补齐事实判断、任务结束条件、知识节点类型和交接摘要，符合全量测评证据。问题跨多个案例出现，应该修改共用机制。目前没有必要推倒重写，也没有必要建设通用流程编辑器。

主要风险在于：方案部分条款又用关键词和文档格式替代业务判断。这样可能修好原句，却在其他表达或知识条目上制造新错误。以下区分了已经验证的设计遗漏和实施前需要明确的约束；不是修改后的实测成绩。

## 1. 必须先修订的条款

### R1：错误码直通规则漏掉 T18，也应保留事实约束

**位置：** `plan.md:47`，2.2 第 3 条。优先级：P1，影响方案能否覆盖目标问题。

**问题与证据：** 方案规定同型号、同错误码且 `kind=steps` 时直接采用，并声称可稳定解决 T18。实际调用当前 `QAIndex.lookup("T2352", "3212")`，唯一结果是：

```json
[{"qa_id": "rv-0147", "kind": "answer"}]
```

这条知识只有一个清理滚刷的操作；`official/qa_index.py:187` 只有拆出至少两步才设为 `steps`。所以按原方案写，T18 仍不在直通范围内。`answer` 也可能包含可执行的单步操作，不能把排版类别当成执行资格。

**建议：** 错误码精确命中可以确定相关知识，减少模型重复判断，但应独立判断知识内容是正常说明、操作指导还是售后结论，覆盖单步和多步。执行前仍检查当前设备、当前故障、已知冲突、步骤前提和安全限制。不能为通过 `supported_symptoms` 校验，把知识标题推导的症状冒充用户已报告的事实。

**验收：** 同码单步、多步、正常说明、硬件结论分别走正确路径；历史错误码或已撤回错误码不触发当前操作；T13 未收录错误码仍不借用相邻方案。

### R2：不能按问题是否包含错误码删除澄清

**位置：** `plan.md:48`，2.2 第 4 条。优先级：P1，可能误删必要追问并提前交接。

**问题：** “你报的是 3212 吗”可能是在重复确认已知事实；“重启后是否仍报 3212”询问的是操作结果。两句都包含 3212，但应有不同处理。原规则会同时删除，并可能直接进入 R5（没有适用方案的交接原因）。

**建议：** 澄清结果同时给出要确认的事实项，例如 `error_code`、`persists_after_restart`，服务端判断该事实是否已经回答。重复问题应改选真正缺失的事实或继续已满足条件的方案，不能把“这个问题重复了”当成“没有方案”。

**验收：** 不重复问已给错误码；允许带该错误码询问仍未知的现象、发生时机或操作结果。

### R3：知识节点需要保留结构和条件，关键词分类不足以驱动流程

**位置：** `plan.md:91` 至 106，3.1–3.2。优先级：P1，影响所有由 Q&A 生成的卡片。

**已经验证的遗漏：**

- bp-0123 首段 `Step 1: Identify the Problem` 经当前 `split_steps` 解析后只剩 `Identify the Problem`。如果在现有 `Step.text` 上按 `Step N:` 判断标题，会漏掉它，再被“其余为 action”当成操作。
- 该条目前两个节点的原始编号都是 1，分别是标题和事实问题。`qa_id + step_no` 如果指原始编号，就无法唯一覆写。当前 `plans/qa.py:52` 已按位置生成 s1/s2；方案需要明确编号口径与版本。
- 官方 rv-0004 同一段内包含“如果出现马达错误→重启→仍报错才售后”。把整段归为一种类型，或见到 service/contact 就作为交接节点，会丢掉条件和先后关系。

**建议：** 保留原始标题层级、段落位置和来源，将混合段拆成有独立含义的节点。关键词规则可用于初筛；无法可靠识别的内容不能默认成为可执行操作。高频知识的人工覆写应绑定 `qa_id + 唯一节点标识 + 知识版本/内容指纹`，原文变动时检测失配。这是知识内容治理，不是按 T 编号写业务例外。

流转还需要明确四个条件：

1. 事实答案决定后续分支时，答案不明确或缺少分支配置应停下来澄清，不能默认下一步。仅收集背景、不影响后续条件的问题可以线性推进。
2. 材料“暂缺”只允许继续不依赖该材料的步骤；依赖材料的判断不得视作已完成。允许携带缺失清单交接，不要求比赛内完成后续人工处理。
3. 保修资格核实、纯人工交接、正常结束应有明确去向，不能仅凭 contact/service 字样统一赋予 R2 原因。
4. 说明节点应当能直接展示，包括末尾说明；不能只依附“下一个 action”，否则末尾无 action 时会丢失。

契约可保留统一卡片外壳，但回答、操作反馈和材料提交应当互斥校验；空答案、无效选项、旧卡片提交都不能推进。当前 `StepFeedbackPayload.feedback` 是必填，只增加可选 answer 字段还不足以形成合法协议。

### R4：事实字段的含义与校验来源还不够明确

**位置：** `plan.md:25` 至 46、56，2.1、2.2、2.4。优先级：P1，直接影响 T50/T52/T61 的修复质量。

**问题与例子：**

- `affirmed/negated` 表达原话肯否，`uncertain` 表达是否确定，混为一个字段容易再次改写事实。T50 的 `does work` 应保留“左侧能工作”的原话；未知的是用户究竟要求处理哪侧、哪项异常，不能因为像笔误就把原话本身重写。
- `subject`、`timing`、`matched_subject`、`matched_timing` 都是自由字符串，尚未说明怎样做“确定性核对”。只比较模型输出的两个字符串，不能可靠区分“盒子自身充电”和“盒子给泵充电”。候选标题也未必写全适用条件。
- `description` 不是固定的设备消息来源。T11 的 description 重复设备推送；T18 的 description 是客户自述“刚开箱、已移除贴纸、仍报错、如何解决”。同一字段还可能同时包含设备引文和真实人工请求。

**建议：** 保留原话、来源输入与引文位置；将陈述的肯否与“故障对象/含义待澄清”分开。只对需要参与规则判断的部件、现象、关系和时间方向做最小归一化，并保留未知状态；不必建立庞大产品本体。方案引用对应事实 ID，校验规则比较有定义的字段和知识条件，而非只信 `matched_*` 自报。

来源判断应细到引文片段：识别 push 的设备文本、description 中重复的设备引文和其余客户自述；位置不明确时保留不确定性。未通过主动人工校验后，应根据已验证诉求重新选择处理方向，不能仅按“有码为故障、无码为投诉”降级。

新增字段还必须贯穿事实保存、纠正、问题切换、诊断输入和摘要。当前 `reduce.py:226` 手工构造持久化事实，纠正分支会复制旧事实；实现时需防止只改 value 却留下旧部件/极性/时间字段。2.4 的澄清条件应判断“是否有足够明确的现象”，不能把“不能充电”等否定句当成没有有效症状。

### R5：跳过已做操作需要比较完整动作和结果

**位置：** `plan.md:111` 至 112，3.3。优先级：P2，可能误删有效检查。

**问题：** “同部件 + clean/restart 等动作词”不能证明完成了同一检查。例如“擦过滚刷表面”不等于“拆下滚刷清除轴端缠绕”；“之前重启过”也不一定说明本轮故障发生后重启仍无效。当前去重以已执行步骤的来源标识为依据，扩展到自然语言历史时需要补齐等价条件。

**建议：** 已做操作至少保留对象、具体动作、结果、发生背景和原话来源；只有确实覆盖当前步骤要求时才跳过。结果未知先询问结果；有新增检查点时保留并解释。用户自述已做与系统本轮收到操作反馈应分别记账，不能因跳过而虚增实际执行次数。

### R6：配件诉求应保留，但不宜默认立即转人工

**位置：** `plan.md:117`、143，第三批与 D3。优先级：P2，可能保留 T63 的信息缺口并影响其他诉求。

**问题：** 无购买执行接口，可以说明购买办理需要人工；但不等于不需要收集型号和部件。T63 本来就缺型号，同时有破损、购买和清洁效果三项诉求。加上 `parts_purchase`、提高优先级并直接交接，只解决“有没有记录购买意图”，没有解决“人工拿到的信息能否处理”。

**建议：** 保留独立购买任务，先复用已有信息；缺少关键型号或部件时做一次针对性澄清，用户明确要求直接人工等情形除外。已有可核实购买信息可以回答，实际下单由人工处理。交接前明确其他诉求是已回答、已一并交接，还是仍待补充，不能因为首项进入人工就遗留无归属任务。

## 3. 实施顺序与决策建议

保留三批总体顺序，但将评测修正作为独立前置；第一批内部按可单独验收的小项推进：

1. 冻结修正后的评审标签与停止条件，记录代码、模型、知识版本。
2. 先修首轮错误路由、已有事实未传入、过保任务结束和摘要丢失；这些不应等待完整节点改造。
3. 明确事实字段语义及来源规则，再实现结构化事实与适用性核对。
4. 第二批同时修改知识拆分、流程条件、契约和前端；已做操作的去重依赖这套明确语义。
5. 第三批完善业务对象展示、购买诉求和回复失败状态。每批用固定口径复跑，单独记录改善与回归，不挑最好的一轮作为成绩。
