# 全量测评与测试方法审查

## 目标

重新评估测试方式是否能衡量用户体验和业务正确性，再测试当前版本的全部 63 条官方案例。预期从原工单、官方 QA、业务规则及实际权限独立建立；旧报告仅在本轮判定完成后用于比较。

## 方法设计

1. 先读当前运行入口、官方材料、测评驱动和业务边界，记录现有方法的偏差。
2. 在运行前固定评分标准、各原始案例的允许下一步和禁止行为，不以当前系统输出反推金标。
3. 原始案例层覆盖全部 63 条正文及附件，只补原材料已明确的信息，未知事实不擅造；独立记录首轮与后续可覆盖结果。
4. 另建明确标注为模拟的多轮分支，覆盖解决、未解决、事实补充、不知道、暂停、身份补充、业务确认与人工边界；模拟数据与官方原文及主分母分离。
5. 采集 HTTP 事件、完整卡片和媒体、检索轨迹、任务/案件/会话结果，校验工作区与运行容器版本和运行前后稳定性。
6. 运行当前版本完整 CI，逐案阅读新证据，输出分层指标、责任分类、方法局限与下一步迭代方向。

## 验收

- 原始 63 案不缺失、不改写，不用历史评分作为断言；正文、附件、预期、脚本及运行版本可追溯。
- 自动执行完整性、首轮处理质量、多轮分支结果、最终解决证据分别计数，不能混为单个正确率。
- 区分系统缺陷、合理能力/权限边界、知识问题、信息不足、资料疑点、测试器错误及未覆盖；待查不得伪装成通过。
- 人工实际入队即本轮 agent 边界，停止自动业务办理；不模拟人工批准，也不伪造真实设备修复。
- 不修改产品代码或官方数据，不提交或发布；发现新问题先记录证据与通用设计建议。
- plan.md 冻结；方法实施中的调整和勘误写 addendum.md。
