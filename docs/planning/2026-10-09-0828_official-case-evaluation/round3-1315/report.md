## Spec

独立需求审查：**4 项已通过隔离 HTTP 复现的缺陷，2 项 P1、2 项 P2**。完整需求引用和精确定位见 [Spec 报告](spec-review.md)，原始状态与回复见 [spec-repro.json](spec-repro.json)。这些问题不能被 134 个既有测试通过覆盖。

### [P1] 客户改变请求，人工仍收到旧要求

位置：[l3.py:638](../../../../orchestrator/app/sessions/l3.py#L638)。

两轮输入分别为“没发货就先暂停”和“改成取消整个订单”。两者都属于 order_change，于是第二轮被当成重复请求。回复继续说已转交，但人工摘要和等待任务原话仍只有第一轮暂停要求，没有取消整单的信息。

修正方向：区分“同一次请求重试”与“同类业务的新要求”。用稳定请求编号识别重试；内容或条件改变时记录请求修订并更新摘要。任务队列也需更新关联请求，不只按 intent 和订单去重。

### [P1] 交接半途失败后，重试仍缺摘要

位置：[l3.py:643](../../../../orchestrator/app/sessions/l3.py#L643)。

完整 HTTP 故障验证中，案件状态及请求写入成功后，让摘要写入失败。客户再发一次请求，系统跳过写入并回复已转交；实际 handoff_summary 仍为 null，摘要写入累计只尝试了一次。

修正方向：案件入队、请求与摘要在同一个事务内完成；或提供可验证完整性并补齐的恢复协议。现有条件只看状态及意图，不能把半成品视为完整交接。实现说明将事务与可靠重放列为可选复杂度，但实测证明当前去重依赖这些保证。

### [P2] 人工处理后无条件推进了非查询任务

位置：[l3.py:609](../../../../orchestrator/app/sessions/l3.py#L609)。

换货申请带有待排障任务，客户在实际方案卡选择 request_human。系统先说已提交人工，再说 “Next up: device troubleshooting”；report_problem 被设为 active，阶段从 awaiting_human 被覆盖为 context。

这证明共用人工入口的行为已改变。**本次没有产生排障步骤卡或危险动作，不能声称安全闸门已被绕过。** 问题在于未按需求限制为允许继续的独立只读任务，并且改变了等待状态。

修正方向：任务推进检查等待原因、依赖和允许操作；第一阶段只继续独立查询。人工等待状态和客户明确的处理选择应保持有效。

### [P2] 人工已驳回，任务仍等待人工

位置：[l3.py:623](../../../../orchestrator/app/sessions/l3.py#L623)，关联出口 apply_human_decision 位于第 966 行。

后台驳回返回 HTTP 200，案件状态 rejected、会话 stage=done，order_change 任务却仍 waiting_human。新状态只有进入逻辑，没有在人工决定返回时更新对应任务。

修正方向：人工决定绑定任务/请求编号，按批准、驳回、要求补充的实际含义更新关联任务；不能把批准直接当成外部业务动作已完成。
