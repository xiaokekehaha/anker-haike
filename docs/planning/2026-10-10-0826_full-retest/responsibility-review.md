# 官方 63 案例：责任分类与迭代台账

依据：2026-10-10 08:27:20–08:30:04 的同一次运行、原文/附件、完整回复和卡片、关键 checkpoint、实际 SQL，以及已核对的官方 QA。没有新增模型运行。处理质量复评为 49 可接受、13 需改进、1 资料待核；T48 勘误见 addendum.md。

## 如何判定

**处理质量**回答“本次已覆盖的处理是否恰当”；**主要去向**回答“下一步主要由谁处理”。两者独立：合理转人工可以处理恰当，但用户问题仍未解决；如实说不知道，也可能同时存在上游检索缺陷。

主要去向每案一项，合计 63。优先列已证实系统问题，再列已确认知识缺口、知识根因待查、源文待核、明确执行边界、等待后续、当前诉求已回应。这个顺序用于分派工作，不代表因果只有一个。并存因素多选，不可把数量相加当总案例数。

| 主要去向 | 定义 | 责任与验收 |
| --- | --- | --- |
| 系统需修 | 已观察到可纠正的理解、检索构造、节点、状态或交互缺陷 | 研发先设计通用约束，按正常、反例和跨流程场景验收；不能按 T 编号写分支 |
| 知识缺口已确认 | 当前 QA 集无对应条目，或已选源文确实不完整 | 知识维护补可追溯内容；研发保留拒绝编造和真实交接。缺一条不等于全库无解 |
| 知识根因待查 | 本次未取得适用依据，尚不能区分输入不足、漏召回、筛选或源库缺失 | 联合核对原始问题、查询、候选、适用条件及源文，再分派责任 |
| 源文疑点待核 | 术语等疑点尚无足够证据判错 | 产品/资料维护核实，再决定修数据还是系统 |
| 明确执行边界 | 有证据表明需要人工权限、安全处理、实体维修或未接入工具 | 检查交接真实、摘要完整、不虚报办理。扩充权限/工具是业务选择，不是必修 bug |
| 等待用户或后续验证 | 需事实、确认、凭证、继续意愿，或只走到模拟失败后的材料收集 | 补充用户反馈和后续测试；不能直接归为能力不足或自动解决 |
| 当前诉求已回应 | 正常功能说明或对未给具体故障的投诉作了回应 | 保持现有处理；不据此声称设备修复或用户满意 |

证据口径：表中“实际”指本轮轨迹可核验；“待查/待核”指根因或资料结论未确认；“模拟排障未解”仅指驱动统一提交 not_solved。实体维修边界按源文结论或用户明确物损识别，不等于通过设备检测确认硬件病因。
