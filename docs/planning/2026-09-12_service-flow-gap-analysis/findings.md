# 核查发现

## 用户流程图（比较材料）
1. 客户输入文字、图片、购买凭证。
2. AI 理解问题：读图、产品消歧、情绪识别。
3. AI 补齐信息：主动追问、核查订单与渠道。
4. 匹配产品知识、服务政策、业务流程。
5. 排障并记录操作与客户反馈，判断问题是否解决。
6. 未解决时判断能否按规则自主办理：证据充分且有权限则 AI 自主办理售后；证据不足、政策例外或超权限则转人工。
7. 转人工交接事实、证据、排障记录、待决事项；AI 推荐方案、备选项、政策依据与回复草稿。
8. 人工补充判断、选择、修改或审批；AI 按决定执行并记录。
9. 跟踪执行结果与客户反馈，判定结案条件；满足则客户确认并结案，否则保留案件继续调查、处理或升级。

## 初步证据
- README 将产品定位为扫地机器人售后智能服务，覆盖情绪、产品消歧、多模态故障定位、分步排障、升级与凭证核对。
- 实现目录包含会话状态图、产品目录、知识检索、故障卡、计划、规则、图像与升级摘要。
- 工作树存在大量其他任务未提交改动；采用读取时的代码现状作为依据，历史进度仅作线索。
- 初步进度提示前端多张业务卡片与对话接线仍待完成，需核对 App 实际代码。

## 已确认设计边界
- `00_decisions.md` D2 / D3 / D16：凭证只抽取并核对模拟订单与渠道；不做完整质保流程，不输出质保资格结论，全部数据为模拟。
- `02_overall-design.md` §3：设计状态机为 intake / disambiguate / diagnose / guide / verify / escalate / done；升级摘要发出即结束，没有人工接单审批后回流执行的业务节点。
- `09_plans-rules-knowledge.md` §5.2：即使 order_verified，下一步仍是「资料已核实，转人工办理」。规则判定是否升级，不是授权 AI 退款/换货等业务动作。
- 图中的订单核查位于排障前；我们的设计主要在常规升级时收凭证核对，并允许跳过。安全与明确人工请求走直接摘要。
- 图中服务政策/业务办理覆盖面宽于现有产品排障知识与有限步骤计划。真实订单系统对接在原设计 F13 明确不做。

## 最终复核修正
- 前端在核查期间完成新的入口接线：`App.tsx` 已调用 `useSession`、`offline={false}`、`send`、`requestHuman`；`Timeline.tsx` 已挂产品/步骤/凭证/摘要卡。因此最终不再判断“前端为只读壳”，只认定代码已接入，本次没有做运行验收。
- `graph.py::apply_action` 当前只处理 request_human / skip_receipt / select_product，没有 step_feedback 或 confirm_receipt 分支；`guide_entry` 仍只发阶段事件。这能独立支持“步骤反馈闭环未完成”的判断，不依赖旧票面状态。
- `router.py` 对 rediagnose 明确返回 not_allowed_now / is not supported yet。会话事实增量与连续追问的设计补充仍属待实现内容。
- `build_summary` 具有产品、问题、观察、假设、已执行步骤、原因、情绪和凭证结果，但没有人工处理建议/待审批方案/待决事项专门模型。步骤字段存在不代表步骤执行反馈已接入。
- 代码搜索未发现售后自主办理、人工审批、执行回执、案件关闭/重开等业务实现；已有 ticket_id 属于检索历史工单导入，不是当前客户案件。
- `done(completed)` 是一次 run 结束事件；设计也明确澄清结束的 completed 不代表问题已解决，更不代表售后案件结案。
