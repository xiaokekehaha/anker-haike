# 用户售后流程图与现有系统对照

核查日期：2026-09-12。依据为仓库已确认设计和核查时的工作树代码（含未提交变更）。这是设计/实现核查，未做线上运行验收；未访问或修改数据库。

## 核心判断

我们的设计与图中的“理解问题 → 澄清 → 知识匹配 → 分步排障 → 解决或升级”主干一致。图中进一步要求“AI 自主办理售后 → 人工判断/审批 → AI 执行 → 跟踪与案件结案”，这些尚未形成现有系统的完整设计与实现。

需要区分两类差距：

- **原设计已有、实现尚未完成：** 分步排障与反馈推进、凭证 OCR/字段确认/模拟订单核对、多轮补充纠正等。
- **超出原设计，需要新增：** 售后政策与授权判断、自主办理、人工接单审批、按审批执行，以及案件跟踪与结案。

## 三处关键设计差异

### 1. 凭证核实的目标不同

我们的 D2/D16 明确限制为核实事实和给出下一步，不输出质保资格。即使设计中的订单核查返回 order_verified，下一步仍是“资料已核实，转人工办理”。因此，补完 OCR 与模拟核查之后，也不会自动获得图中的“AI 自主办理售后”能力。

依据：[前置决策 D2/D3/D16](../2026-09-12_smart-service-tech-design/00_decisions.md)、[凭证核查 L1–L6](../2026-09-12_smart-service-tech-design/09_plans-rules-knowledge.md)。

### 2. 升级摘要之后的流程不同

现有设计的升级路径是收集/核实凭证后生成摘要，再结束。代码中 summarize 也直接连到 END，没有“人工接手 → 审批 → AI 执行”的回路。文案出现“已转人工”不能证明真实人工团队已接单。

依据：[总体设计 §3/§4.3](../2026-09-12_smart-service-tech-design/02_overall-design.md)、[图节点与边](../../../orchestrator/app/sessions/graph.py)、[摘要生成](../../../orchestrator/app/escalation/summary.py)。

### 3. 结束一次对话处理与售后结案不同

现有系统持久化会话、事件和待输入状态，能支撑恢复。图中还要求在维修、退换或人工调查期间长期保留案件，并基于实际执行结果与客户反馈决定结案。这需要补充业务对象和状态迁移，不能直接复用一次 run 的 completed 状态。

依据：[执行契约](../2026-09-12_smart-service-tech-design/08_session-execution-contract.md)、[运行事件收尾](../../../orchestrator/app/sessions/runner.py)、[阶段与动作契约](../../../contracts/haike_contracts/common.py)。

## 落地顺序建议

1. **先完成已承诺的排障和凭证链路。** 后端票 34–36：步骤下发、反馈、结束/升级；票 40–41：OCR、字段确认、模拟核查；票 37 与会话记忆补充：连续追问、补充纠正。最新前端已出现对应接线，应继续验证前后端完整链路，不能只凭卡片存在判定完成。
2. **补人工处理链路。** 明确交接成功标准，增加案件/接单状态、待决事项、AI 处置建议与草稿、人工修改/审批记录。让人工决定成为可追溯的执行输入。
3. **按受限业务场景扩展自动办理与结案。** 先明确服务政策、必要证据与允许动作，再接售后执行工具和结果查询/回调，增加客户确认、未完成继续跟进、结案及重开规则。前两类是原范围补齐/人工闭环，完整自主办理属于范围扩展。
