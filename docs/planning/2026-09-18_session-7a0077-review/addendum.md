## 2026-09-18：核对 Claude 评审后的修订

本节修订 plan.md 的实施顺序与部分规则。plan.md 保留为设计基线；有冲突时以本节为准。本轮仍是方案评审，没有修改应用实现。

### 1. 同意的核心判断

问题应先定义为：第 3 轮确认无输出反应之后，系统没有获得新的、足以区分故障原因的设备观察；后续获得的操作限制和不满也没有有效改变取信息的方式。此前把统一回复放在第一批，优先级偏低，现改为先修执行事实与可恢复约束，再补动作选择能力。

- cannot_do 被写入 steps_executed，且 decision._first_open_step 与 guide.prepare_step 均无条件按该列表去重。这把“当时没做”转换成“已经做过，跳过”。
- decide_next 的候选循环会立即返回 step，missing observation 只能等待所有候选步骤都不可用后才成为 ask。这一处确实存在步骤优先的问题。
- prefer_proposal_over_more_steps 仅在 guide 内处理，无法影响本会话后半段的 complaint → dialogue 路径；情绪应影响所有相关路径的负担与服务选择。
- 摘要准备不是人工接单，不能作为故障已经解决的证据；用户有新信息或明确恢复条件时，应重新评估可用动作。

### 2. 需要校正的事实与推论

1. **升级不是严格的吸收态。** 第 10 轮实际走过 understand → disambiguate → retrieve → guide → escalate → summarize；系统已经重开诊断，随后被历史去重和缺乏其他动作卡住。第 6 轮 R1b 触发时 plans_exhausted=0，并非先耗尽计划再触发 R1b。修复重点是候选被排除的依据及其有效期，不是仅增加一条“允许重新进入”路由。
2. **不是所有信息增量都为零。** 三次 cannot_do 与不满提供了用户条件和服务质量信息。设备故障定位没有有效推进，系统又没有消费这些过程信息，才是可验证的失败。
3. **问题不保证有信息，操作失败也可能有信息。** 用户可能不知道、设备不在手边，或者不同回答根本不影响下一步；条件明确的验证步骤即使未解决，也可能排除假设。读屏需要设备可用，属于低负担观察，不是无条件零成本。
4. **已有问诊判别能力。** conversation/taxonomy.py 的 select_discriminator 会按候选集合划分选择问题；decide_symptoms 又可能因候选症状共享可用计划而提前继续。因此既要修后续 ask/step 选择，也要核对“共享计划即可结束问诊”的边界。
5. **plans_ranked 不是校准后的故障概率分布。** 本会话诊断模型实际只返回 pb_port_debris 一个计划，置信度先为 0.62，后为 0.55；检索到其他资料不等于建立了那些故障假设。仅在 top-2 接近时才提问会漏掉本例。不能据此推断实际大概率是小电流模式或老充电器，也不能承诺提前几分钟解决。
6. **没有人工接入，不意味着应普遍提高排查上限。** 用户仍可暂停或拒绝继续；没有有用、可做的动作时，应明确能力边界，保存记录和恢复条件。无限追问同样增加成本。R1b 的“停止继续推操作”目的保留，后续动作由可用能力和用户意愿决定。

计数校正：全会话有两轮检索，各 23 条命中；第一轮发生在第 3 轮内部，不能将 46 条全算为第 3 轮之后的成本。第 3 轮完成之后有 7 次逻辑 model_call：第 6 轮摘要一次，第 7—9 轮理解各一次，第 10 轮理解、诊断、摘要各一次。这些差异不改变主要结论。

### 3. 修改后的最小回路

保留四类状态：已确认设备事实、实际执行及结果、当前用户条件与意愿、真实可用的服务出口。计划排序帮助选择动作，但不能替代已验证事实。每轮先校验风险与用户命令，再更新状态，重新选择可用且有价值的动作。

动作包括提问、观察、操作、给出有依据的方案、暂停及实际可用的售后处理。观察可继续使用 ask 协议承载，首版不必新增外部动作枚举。

候选选择先过滤适用型号、风险、所需资源、意愿、已知答案及重复动作，再比较：答案或结果能否改变下一步、用户负担、是否已有直接可执行的可靠方案。先实现可解释的规则和选择理由，不用未经校准的 confidence 计算虚假的“信息增益/成本”数值。

### 4. 第一批：修状态语义和恢复，作为一个完整改动交付

不能只改 verify.py 和 _first_open_step，至少同时覆盖以下职责：

| 位置 | 必须修改的行为 |
| --- | --- |
| guide/verify.py | 保留原始反馈历史；solved/not_solved 才进入实际执行视图；cannot_do 记录暂时阻碍，不直接消费步骤并沿 next_on 连发 |
| conversation/reduce.py 与问题状态定义 | 按问题持久化阻碍原因、范围、依据、是否已询问及解除条件，支持恢复和切换问题 |
| diagnose/decision.py | 区分已执行、暂时不可用、证据不适用；不能仅因暂时阻碍永久耗尽计划；新事实或条件变化后重算相关候选 |
| guide/steps.py | 与选择器共用执行/阻碍判据，最终发卡前复查，避免旧游标绕过限制或再次错误去重 |
| sessions/graph.py | cannot_do 进入重新评估；保留 R1b 减负目的，但不机械导向不存在的人工出口；投诉、摘要后补充信息也消费更新后的服务约束 |

第一次 cannot_do 就停止无条件发下一步，不必等三次。备注已经给出原因时直接消费；原因未知且会改变选择时只问一次。未确认原因前只阻止重复推荐当前动作，不能推断用户所有“做”或“看”的能力都不可用。

例如“没有刷子”只限制需要刷子的动作；“设备不在身边”会同时限制读屏和插拔；“不想继续”改变继续服务的意愿。用户没有回答阻碍问题时，不继续循环追问。

阻碍解除后仍要重新校验型号、风险、证据和继续意愿，再发新卡片令牌。旧反馈保持历史事实，不能因为用户补充了一句无关症状就清空全部阻碍或所有 exhausted_plans。旧快照中的 cannot_do 必须按反馈语义解释，不能继续从列表名称推断已经执行；原始历史不改写，不保留两套长期决策路径。

### 5. 第二批：把提问和操作放进同一次选择

扩展现有 taxonomy 判别问题及 plan observations，而不是只把 pending_ask 的 return 上移。为有用的问题声明适用型号/症状、所需条件、回答选项及其对后续候选的影响；保留计划门槛问题与跨计划判别问题两种用途。

- 多个症状共享一个计划，不再自动证明无需继续区分；检查是否仍有会改变动作的未问观察。
- 只有一个排名计划时，仍检查关键假设是否缺证据，不以 top-2 是否存在作为提问的必要条件。
- 答案已知、用户无法观察、重复未答或各种答案都不改变后续选择的问题不再提出。
- 读屏问题只有在设备可用、型号支持且已配置可消费的回答分支时进入候选。检索文本可以供资料整理和候选生成参考，不能把每条命中直接当成已验证的问诊分支。
- 低负担且能改变选择的问题通常先于需要工具的操作；已有明确证据支持的简单处理可以直接给出，不设“所有问题问完才准操作”的固定顺序。

这一批包含知识配置建设。若不补充判别问题及答案映射，只改控制流，本会话仍可能没有任何可问的有用问题。

### 6. 第三批：让情绪改变可执行决策，再统一回复

在入口更新情绪依据与过程负担，再由诊断选择器及 dialogue/summary 等路径共同消费。情绪上升表示可能需要减负或改变方式，不能等同于准确测得进展比值，也不能凭空提高故障置信度。

操作阶段出现阻碍或不满时，优先检查是否可换成更省力的问答；问答也无效时，解释已知结论和缺口，提供暂停或真实可用的出口。用户明确说“很生气，但继续查”，应继续选择合适动作。仍保留 plan.md 中 no_signal/unavailable 不伪造 calm、投诉不被诊断模板吞掉以及单一主回复计划的设计。

型号资料冲突核验与最终发布校验是恢复发步骤的前置条件，不能等到最后才处理。本会话通用长按复位与库内 A1289 官方资料存在差异，应先核实适用条件；这里不直接给出未经核实的维修指令。

### 7. 验收标准与优先级

实施顺序修订为：**执行/阻碍语义与恢复 → 有依据的提问/操作共同选择 → 情绪入口及各分支消费、回复一致性。** 型号适用性和真实能力文案贯穿各批次，先保证正确再开放新的用户动作。暂不先做整个 service_policy 抽象重构。

必须用离线测试证明以下行为：

1. 连续 cannot_do 不产生任何“已执行设备操作”的事实，不因这些反馈永久耗尽计划；也不重复发同一卡或持续追问原因。
2. “缺刷子”“设备不在身边”“不想继续”产生不同限制；恢复条件满足后，适用步骤可重新进入选择，旧令牌不可重复提交。
3. 摘要之后补充有效观察，可以改变候选和下一动作；无关信息不清除限制；真正执行无效的记录继续有效。
4. 只有一个排名计划、多个症状共享计划时，仍能选择已配置且有判别价值的问题；答完后确实更新候选或下一动作。
5. 读屏不可用、答案已知或缺乏映射时不问；不能仅为了增加轮数发出无效问题。
6. 不满在问诊、步骤和摘要后均改变相关服务选择；纯不满不伪造新设备事实、恢复证据或真实人工接单。
7. 提问和重新发卡仍满足事件幂等、反馈校验和恢复一致性；不通过丢弃事件掩盖重复回复。

增加选择日志：本轮新增观察、候选变化、执行结果、约束变化、实际服务进展或无进展，以及选择/排除动作的原因。该日志是效果证据，不能用“发了一张卡/生成了一次摘要”自动判定已经取得进展。允许必要的确认、解释与暂停，不把每一条消息都硬算成故障定位动作。

### 固定开销：先削真实浪费，再按实测值重设护栏

两处护栏原本分别只有 38 和 15 token 余量，是「不许再长」的绊线，不是预留额度。任何新增抽取字段都会必然触发，所以先把新增里可削的部分削掉：

- `OperationUpdate` 由「resources 列表 + participation + step_request」压成单一 `signal` 枚举加 `quote`，schema 175 → 118 token。副作用是排除了自相矛盾的组合（pause + retry），并让「一轮一句引用」成为结构约束：`update_conditions` 现在先校验 `quote in text`，不通过则整条不生效。
- interpret 提示里 operation_update 与情绪两段由 274 → 143 token。signal 名本身自解释，提示只留策略，不再重复枚举值词义。
- authority 层原本同时下发 `steps_executed` 和 `step_attempts`，而后者是前者的超集，每次调用为每个已执行步骤付两份。改为只传 `step_attempts`（`builder.py` 紧邻的注释原本就写着不要为已执行步骤付第二份）。

削完后 schema 2519、system+authority 4127。两处护栏改为 2560 / 4170，并在断言旁注明数字来源与余量，下一次增长仍会先在这里失败。

`app/prompts/reply.py` 的 `reassurance_messages` 和 `app/bakeoff/tasks.py` 的 reassure 模式保留未动：bakeoff 是离线模型对比工具，删除其基准项超出本次评审范围，需要单独确认。它现在基准的是生产已不使用的提示。

### 情绪：模型给了等级但没给引用

原实现里 `cues` 为空即把 level 整个作废。生产用的是 flash 档模型，漏填数组字段是常态；而首轮「怎么这么难用」的「难用」不在 `complaint_terms.yaml` 里，规则层也接不住 —— 本次改动最想修的首轮承接会落空。`test_wants_human_from_extraction_escalates_like_r3` 正是这个路径：模型给 angry、不给 cues，结果落成未判断。

改为分三种：

- 有引用 → 采信，`source=model`
- 无引用且为 calm → 仍视作无信号（calm 是 schema 默认值，不是观察）
- 无引用且非 calm → 降到最低的非平静等级 `dissatisfied`，`source=cues_missing`

关键词规则仍可在此基础上上调。`source` 已进入 `emotion_strategy` 观测事件，可以按 model / rules / cues_missing / no_signal / unavailable 分别统计。

### 承接语

原为对三个等级共用一句常量，等于把模板换了个位置。改为按等级分档，且只在该情绪**首次出现或加重**时发出：与本轮之前 `emotion_track` 里的最高等级比较，未超过则不再承接。原会话 06:18 连续三轮不满只会承接一次，加重到 angry 时换成对应的一句。判定纯从既有 `emotion_track` 推导，不新增状态字段。
