## 2. 第一性原理：这次失败的三层

```
用户原话            系统推断                    推断的用法
─────────          ─────────────────────       ─────────────────────────────
"是的，很慢"   ──►  symptom_code = pb_no_input ──►  allowed_for(∩codes)：硬过滤
                   （词表里没有"回充慢"这一族，          retrieve / synthesize / decide_next
                    模型被要求从候选码里挑一个）          三处各用一次，终身有效
```

- **第一层：事实与推断没有分开。** `pb_no_input` 写在 fact 记录的 `symptom_codes` 字段上，和用户原话「很慢」享有同等权威。用户看不见这个码，也没有理由去「更正」一句真话。reduce.py 的 corrections 机制在这里无用武之地。
- **第二层：词表没有槽位。** `symptom_taxonomy.yaml` 的 power_bank 只有「充不进电 / 充不满」，charger 才有「充电慢」。intake 提示词写了「无法匹配留空」，模型仍挑了最近的码。封闭词表 + 硬过滤，任何缺槽位的描述都会被挤进邻近分类。
- **第三层：知识到动作只有一条窄门。** 第 3 轮检索已命中：`official_anker737_ports#c1`（只有 USB-C1 能输入）、`#c2`（回充时间取决于充电器 PD 能力）、`manual_pb#c21`（老 5V1A 充电器充得慢不算故障）、工单 T0227/T0207/T0212（A1289「自己充不进电」= 5V1A 充电器，换 PD 充电器）。但 diagnose 模式下用户只能收到「计划库里的步骤卡」；`pb_input_check` 对 A1289 整计划排除，A1289 又没有回充专用计划，`_diagnose_outcome` 在 plans_ranked 为空时直接 R5、非空时进 guide，`reply` 节点从 retrieve 实际不可达。于是模型被迫在两个输出侧计划里挑一个（0.72 给了 output_check，理由里已经出现「UVP」），接着替它去问一道输出侧的判别题。

第 3 轮那道题不是「用户的问题需要它」，而是「候选计划需要它」。design §3.4 要求问题必须能改变处理，这里答案确实改变了处理——改成了死路。

## 3. 三个问题的回答

### 3.1 有没有回退机制

有，但是局部的、面向用户改口的：

| 能改的 | 机制 | 备注 |
| --- | --- | --- |
| 用户事实 | supersede / retract，保留来源与修订 | 只覆盖用户说过的话 |
| 观察题答案 | 请求 asked/unparsed/unknown 期间可补答 | answered 之后没有改选入口 |
| 资源 / 暂停 | operation_conditions，本会话第 6 轮成功恢复 | 恢复后回到同一条死路 |
| 问题切换 | new_issue / resume_issue，挂起与恢复卡片 | 「说错了」与「另一个问题」没区分 |
| 案件 | reopen | 不撤销外部单 |
| 本轮运行 | cancel run | 不撤销已提交事实 |

不能改的：

- 系统推断（symptom_codes、plans_ranked、diagnostic_decision 的 allowed_plans）。`basis_changed` 只在事实被替换/撤回或新增症状时把 pending_card 和 diagnostic_decision 置空；**新观察不清 plans_ranked，也不重排**。反过来，第 7 轮事实零变化却重新检索并重新 synthesize（6007 tokens），得到同一份摘要 rev2。触发方向正好反了：该重算的（观察变了）不重算，不该重算的（事实没变）重算。
- LangGraph checkpoint 的 time-travel 不是答案：重放会重跑模型和外部调用，`update_state` 只是分叉，会话本身是追加式的。要的是信念修订，不是状态回滚。

### 3.2 业务流程设定是否合理

骨架合理：结构化解释 → 事实写入 → 有来源的计划库 → 执行前安全/授权检查 → 卡片绑定与发布边界。这些保留。

不合理的部分：

1. 过早硬分类（§2 第一、二层）。
2. 六道闸门全是交集与排除，唯一「加回来」的是 `effective_exhausted`。任何一道误判都把集合清零，而清零只有一种解释：escalate。历次复盘（ce6 / r7 / f30 / 0f8809 / 37cea3）形状一致，说明是结构问题不是单点 bug。
3. 结束原因失真三处：`knowledge_coverage_missing`（实际知识存在，缺的是候选一致性）；观测台把 R2 显示为「适用步骤已耗尽」（实际 0 步）；`prepared` 前台文案已区分，观测台 outcome 仍是 `escalated`。
4. SKU 排除按整计划粒度：`pb_input_check` 因为某一步不适合 A1289 被整体排除，连工单证明有效的「换 PD 充电器」也一起排除。不适配的是步骤，排除的却是计划。
5. 判别题归计划所有（`diagnostic_observations` 挂在 `pb_737_output_check` 下），谁进候选谁的题就被问；题目与用户问题的相关性没人判断。

### 3.3 agent 框架是否合理

它不是自主 agent，是确定性状态机，模型只在三处受约束地出现：解释输入（intake）、给计划排序（synthesize）、润色摘要。在「步骤只能来自审核过的计划库」这个安全约束下，这是对的形状。LangGraph 只做调度与持久化，也对。

结构问题只有一个：「下一步是什么」由七处共同决定，各自有独立的 escalate 出口——

```
decide_symptoms ─► codes ─► allowed_for ─► constrain_plans ─► synthesize(∩allowed) ─► decide_next ─► guide 循环 ─► _diagnose_outcome
      │R5/R7                   │                                   │                      │R2              │R2                │R5/R2
      └──────────────────── 每一处都能单独把用户送去 summarize ─────────────────────────────────────────────┘
```

同一个会话在两天内为这条链修了两次、回滚了两次（4b656e7→409a10d、3fbb741→e5cb4e5），工作区里还有第三次（decision.py 未提交）。三次都在某一道闸门上打补丁。这本身就是「闸门链」结构的证据。

## 4. 对工作区未提交改动的评价

`decision.py` 当前改法：观察门槛已满足的计划不再被症状码否决；尚缺观察的计划仍需症状码支持。

- 机械上能解开本会话：`pb_737_laptop_uvp` 进候选，下发「用 USB-C2 验证笔记本充电」。
- 但它静默接受了问题范围的切换。用户的主诉是「自身回充慢」，下发的步骤处理的是「给笔记本充电」。用户既没被告知系统已经把他的问题换了，回充慢也没有任何交代。
- 它也没有触及 §2 的三层：推断仍写在事实上，词表仍没有槽位，检索命中的回充资料仍然到不了用户手里。

它与 analysis.md P0「冲突时询问问题范围」是两个方向。我的判断：

- 「症状码集合与解锁计划的症状码不相交」这个条件两种方案都需要检测，现在的 diff 没有检测，只是放行。
- 检测到之后，一句澄清（「你前面说的是给充电宝本身充电慢，UVP 是接笔记本时出现的，这两个都存在吗？」）比静默切换更符合 design §1「每次交互至少取得一种进展」——它同时消除歧义并给回充慢留了入口。代价是一轮。
- 如果不想多一轮，最低要求是下发 UVP 步骤的同一条消息里说明「回充慢的部分另行处理」，并把回充慢留在 open 状态。这需要 ask_observation / guide 的文案能引用两个现象，改动面比澄清大。

倾向澄清。这是判断题，留给用户定。
