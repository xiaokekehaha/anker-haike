# 从执行步骤到依据观察做下一次决策

状态：设计建议，尚未实施或部署。

## 1. 第一性原理

目标是以合理的用户投入，安全地恢复设备使用；不能恢复时，减少交给人工后的重复沟通。步骤数量、唯一故障标签、候选模型分数都只是手段。

每个交互必须至少有一个明确用途：恢复功能、取得会影响后续处理的观察、完成用户明确要求的服务。候选原因未唯一不妨碍执行共同适用的检查；型号未知也只应阻止确实依赖该型号的动作。

核心循环：接收事实 → 筛选适用动作 → 选择下一次交互 → 记录观察/执行结果 → 更新事实。计划耗尽意味着当前动作集合需要重新评估，不等于硬件故障确诊，也不自动意味着必须转人工。

## 2. 当前断点

1. `StepFeedbackPayload` 只有 feedback 与 note。未解决不告诉我们灯是否亮、是否开始充电、是否已经完成所需观察。
2. `apply_feedback()` 同时记账、按 next_on 跳转、判断次数上限、切换计划和决定 R2。它依据先前的 plans_ranked 切换，没有基于本次具体观察重算。
3. `decide_symptoms()` 已以事实为依据筛选计划，但主要服务排查前问诊；步骤结果没有进入同一决策循环。已有 observation 类型事实可以复用。
4. verify、guide、retrieve 等位置各有结束出口；情绪动作也可能在执行两步后返回 R2。同一个结果由不同语义的条件产生。
5. 两步计划的检查目的与 expected_result 不匹配：观察供电灯、触点的预期应是获得状态，当前却以设备恢复使用为预期。正常观察被“未解决”吞掉。

## 3. 最小设计

### 3.1 结果分成两件事

- 功能是否恢复：保留 solved/not_solved/cannot_do 兼容现有客户端。
- 检查得到什么：给需要判别结果的步骤声明一个结果问题及有限选项，反馈中允许携带选项 ID；没有具体结果时保持 unknown。

示例（待核实设备适用性后的配置）：第二步观察充电，结果可为“有充电提示，但仍无法启动”“没有充电提示”“还未观察完/无法判断”。“已恢复正常”保留快捷结束入口。需要区分灯和触点时拆成独立观察，不用一个二元反馈覆盖两个事实。

用户只说“不行”仍记为 not_solved；不得自动写入“没有充电提示”，也不得排除供电问题。需要补问时只问尚缺且会改变后续处理的观察。尚未观察完不能直接算作检查失败；也不能凭点击快就断言用户没做过，可接受其明确提供的既往检查结果。

绑定 issue_id、card_id、plan version、step_id 与 input_id；旧卡、重复请求、其他设备的回答不能污染当前事实。沿用现有事实写入与纠正机制，保存原始引文、来源和时间，不建立第二套互相竞争的诊断记忆。技术推论与用户观察分开。

### 3.2 扩展现有 decision，而不是新增并行判定层

把 `diagnose/decision.py` 扩展为同一问题的下一动作决策入口，内部继续复用产品识别、问诊、计划库和风险判定。

建议接口（设计名，不是已实现接口）：

```python
decide_next(issue_context, available_knowledge) -> NextAction
```

输入是当前问题的事实视图、已尝试动作、待回答问题、用户偏好与适用知识。输出为一个 ask / step / resolved / handoff_offer / safety_stop，并携带 reason、依据和目标问题/步骤 ID。

函数返回决策，不直接调模型、写数据库或发布事件。解释与可验证动作由调用方执行；检索在已知事实变化且缺少候选时触发，同一事实版本与知识版本的查询避免重复。步骤反馈、自由文本与图片发现应汇入同一事实写入路径，再调用同一决策入口。

`verify.py` 逐步收缩为验证反馈绑定、记录执行结果和提供当前计划后续候选；`graph.py` 负责调度。安全检查仍在发布操作前执行，避免把统一决策误做成单次检查后永久放行。

### 3.3 下一动作的选择顺序

1. 实际风险证据：停止相关操作，说明原因，进入相应服务路径。
2. 用户明确要求人工或停止：遵从意愿，保留已有记录；实际接入成功之前不声称“已转接”。
3. 用户确认功能恢复：结束当前问题；独立未解除的风险不能被“已解决”覆盖。
4. 检查反馈缺少必要观察：存在会改变处理方式的问题时才问，已回答的观察直接复用。
5. 有适用、未执行且有来源支持的动作：发布步骤。现有 next_on 可继续提供候选，但不能覆盖新的风险、用户意愿或相反证据。
6. 当前计划耗尽：根据更新后的事实评估其他计划或有价值的判别问题；已排除、不适用和已完成的操作不复发。
7. 没有支持的下一动作：说明覆盖边界，提供人工选项与完整摘要。

开始不引入概率推理引擎。先用适用条件、已知事实、完成记录和简单优先级即可。模型可以提取有原文依据的观察、解释检索证据或提出受约束候选；操作内容仍受来源和产品适用性校验。

### 3.4 问题必须能影响处理

为结果问题与判别问题声明其答案影响的动作前置条件、排除条件或接单所需字段。发布前判断当前候选下答案是否会改变可用动作、操作许可或必要服务处理。

现有“是否出现充电指示”可复用，但不能只因 taxonomy 中有这道题就强行补问。如果两种答案都只能得到同样的客服建议，就直接解释当前能力边界；接单需要的信息可以标为可选补充，而不是假装仍在排查。

共用一个基础检查方案时，先做该检查可以是合理选择，不需要恢复“候选原因必须唯一”的旧门槛。

### 3.5 计数、情绪和终止

- R1 的操作次数、跳过次数保留为负担信息，逐步改成询问是否愿意继续或提供人工选项；不能单凭计数断言诊断失败。
- R7 关注实际问答的连续无进展。新事实若排除了动作、改变适用性或完成必要观察，就属于进展；不能只看症状候选数量。
- 同一问题、同一上下文不反复问；无法回答时允许换一种表达或提供替代输入，仍不能获得必要信息则说明限制。
- 保留单次运行的工具调用/节点上限防止程序循环。技术超限、模型不可用必须记为系统问题，不能伪装成用户描述不清或设备无法修复。
- 情绪影响表达长度、交互负担和服务选项。单独一次“不行”是步骤结果，不能作为必须结束排查的充分证据。
- R2 改成明确原因的对外投影：计划耗尽但有后续、知识覆盖缺失、用户不愿继续、操作受限、实际风险应分开。旧规则码仅在兼容/观测层映射。

## 4. f30 应有的行为

用户：不能启动。系统执行共同适用的供电/充电检查，这一步本身可以保留。

第一步：收集供电灯、触点的检查结果，已观察正常不等于整机已恢复。用户明确提供的结果不重复问。

第二步：记录是否出现充电提示。用户说“仍然不行”时只表明功能未恢复。

之后：

- 有新观察，且存在相符的已核实处理路径：继续对应路径，不重启之前的两步。
- 缺少会改变路径的观察：针对性问一次，不重新问型号和最初症状。
- 当前知识仍只有这两步且没有其他有依据的路径：如实说明“已完成供电与充电的基础检查，当前资料不足以指导后续操作”，提供人工处理选项。不能保证这条会话从此一定多出第三个步骤。

“没有充电提示”不能直接确诊电池坏了；“有充电提示”也不能证明电池、供电系统全正常。

## 5. 分阶段实施

### 第一阶段：一个完整的最小闭环

从 rv_power_supply 切入，覆盖后端、契约、前端与真实模型回放，不先泛化成流程编辑器。

1. 给步骤增加可选 observation 定义，扩展反馈契约与 StepCard；旧客户端无该字段时仍正常工作。
2. 按事实模型写入结果，支持绑定、去重、unknown 和纠正。
3. 计划耗尽返回内部 reassess 状态，接到扩展后的现有 decision；新事实若使现有步骤不适用，也进入 reassess。
4. 限制重新检索与相同问题/动作复发。只有有价值的下一动作才能继续，否则明确 handoff_offer。
5. 显示真实结束原因，并保持 prepared / 实际接入成功的区分。

涉及：`contracts/haike_contracts/{common,actions,events}.py` 及生成 schema/types、`app/plans/models.py`、`config/plans.yaml`、`app/conversation/reduce.py`、`app/diagnose/decision.py`、`app/guide/verify.py`、`app/sessions/graph.py`、`frontend/src/components/StepCard.tsx` 与摘要视图。

### 第二阶段：集中终止决策

将 guide、retrieve、verify 分散的非安全终止条件移到同一决策入口；删除已迁移的分支，避免新旧两套规则叠加。先保持其他计划行为可回放，再逐计划引入结果观察。运行保护独立保留。

### 第三阶段：补齐真实知识覆盖

整理“不开机/不充电”各观察分支的适用型号、可执行操作、预期观察和停止条件。对确实缺乏路径的分支补充可信手册或经审核服务流程，再发布新动作。检索命中文档不自动变成设备操作授权；无依据的分支保持人工出口。

## 6. 验收标准

- 原始 f30 两次未解决路径可解释：有后续依据时继续，确实无覆盖时明确说明；不把“不能复现 R2”当作唯一成功标准。
- 相同“未解决”但不同观察可产生不同候选处理；没有配置不同处理时不能编造差异。
- unknown/cannot_do/尚未观察完不被写成阴性结果，未解决不自动排除故障原因。
- 用户早已提供充电指示信息时不重问；纠正后更新事实并重新评估，不累积矛盾的有效事实。
- 不重复已执行动作、不重启耗尽计划；相同事实版本不反复检索；流程最终能停下。
- 明确风险、主动人工和确认恢复路径保持正确，prepared 不被显示为已接入。
- 原 R7 会话：正确承接型号/品类回答、已接受症状回答和图片结果，不退回旧的门槛。
- 故障模型不可用/知识检索失败显示系统原因，不伪装为 R7 或已排除所有方案。
- 使用 decision 的公开接口和真实事件入口测试，再做新会话烟测；不修改历史会话来制造通过。

观测应同时看用户确认解决、重复提问/步骤、人工后需重复提供的信息、真实无覆盖分支与安全错误；不能只追求转人工比例下降。
