# 最近修改方向与真实资料接入清单

日期：2026-09-17。范围经用户确认：9 月 16—17 日相关提交、当前未提交多品类改造、仓库内赛题补充材料。比较基点 `1dcb06c`，观察 HEAD `4dd9b0b`；工作区可能继续由其他会话修改。

## 1. 判断

**方向正确；下一阶段应优先把资料接入、审核、版本一致性和验收做成固定流程。**

最近三条主线都值得保留：

1. 照片观察、用户回答和步骤反馈共同更新诊断事实，再选择下一步，改善“问过还问”和“答了不影响流程”。
2. 操作由预写计划约束，步骤绑定证据锚点，办理经过政策与授权校验，符合补充材料强调的按业务规则办事。
3. 品类信息从代码默认值移入目录、症状表、计划和故障卡，为新资料复用同一条流程提供基础。

需要调整的是交付重心：现在已经有足够的演示品类验证架构，优先补接入入口和验收门槛。真实知识库到位，并不自动产生可执行排查计划，也不自动增加可办理的售后动作。

补充材料依据为 [9/14 赛题解析归纳](../2026-09-14_hackathon-brief-gap-analysis/findings.md)，本次未重新访问赛事网站。旧 [gap-analysis](../2026-09-14_hackathon-brief-gap-analysis/gap-analysis.md) 中“L3 零覆盖”已经过时：当前已有政策、授权、执行回执、案件和人工协作骨架。L3 指调用业务系统完成办理；目前业务系统仍为模拟实现，符合既有演示阶段设计。

## Standards

规范轴发现 3 项，独立于需求轴统计：

1. **P2，设计约束违反。** [policy/engine.py:49](../../../orchestrator/app/policy/engine.py#L49) 在 `decide()` 内调用全局 `get_catalog()`；目录没有冻结在政策包内，首次加载还可能读磁盘。相同政策和输入可能受目录版本影响，违反 [政策设计 §4](../2026-09-14_l3-closed-loop-design/04_policy-engine.md)“全过程无副作用，decide(input) 可离线重放”。应在组装 `PolicyInput` 时补品类，或显式固定目录版本。
2. **P3，编码约定违反。** [guide/steps.py](../../../orchestrator/app/guide/steps.py) 和 [knowledge/reachability.py](../../../orchestrator/app/knowledge/reachability.py) 新增函数内导入，违反 `AGENTS.md`“只用顶层导入”；当前 Ruff 默认检查不覆盖该约定。调整依赖方向后移到顶层。
3. **P2，可能的一次变化需多处修改。** [knowledge/faq.py](../../../orchestrator/app/knowledge/faq.py) 仍手写品牌和品类词，而目录已有名称与关键词。后续加品类仍可能改 Python。产品词应来自目录，通用语气词单独保留。

规范轴合计：2 项明确约束违反、1 项启发式问题；最高 P2，政策判定依赖未固定。

## Spec

需求轴发现 3 项：

1. **P2，实现错误：缺失手册可能被证据检查放过。** 可审计引用规格要求每个步骤锚点的对应片段可达。[reachability.py:123](../../../orchestrator/app/knowledge/reachability.py#L123) 在找不到文档且 FAQ 关闭时，将缺失手册也标为 `skipped_faq_off`；分块检查给 `no_chunks`，[cli.py:213](../../../orchestrator/app/knowledge/cli.py#L213) 两者均不判失败。应先确认文档确实属于 FAQ，其他缺失文档必须失败。
2. **P2，实现错误：新版引用可能不支持旧步骤。** 规格要求引用“这一步真正的出处”。[anchors.py:51](../../../orchestrator/app/knowledge/anchors.py#L51) 仅按文档和锚点识别，不核对版本或内容；执行步骤仍取计划里的原文。例：新版手册保留 `c12`，但修改了操作，旧步骤会挂新版主引用。必须联合验证文档版本、段落内容和计划版本。
3. **部分实现：演示标识未贯穿证据链。** 多品类规格要求演示样本“不冒充官方手册”。当前标识主要在文件注释或开头，导入白名单不保留该属性，FAQ 命中不包含注释，计划本地证据统一为 `approved_plan`。应将来源类型、审核状态传至检索、步骤证据和前端；`approved_plan` 仅说明来自预写计划，不能证明官方来源。

需求轴合计：2 项实现错误、1 项部分实现；最高 P2，锚点检查与版本归因存在缺口。区域过滤、真实资料清洗和真实样本评测属于已规划的后续工作，不计为本次回归。目录品类走 R5 是 9/17 新决策，不再按旧票据“无计划即 R8”判错。

## 3. 为快速接入预先固定什么

先固定内部资料格式与验证规则。资料到位后主要填写字段映射、补内容和审核差异；只有出现新的业务语义时才扩代码。

资料分四条接入路径：

| 原始资料 | 转换产物 | 最小保留字段 | 谁确认 |
| --- | --- | --- | --- |
| 产品技术知识库、说明书、FAQ、故障图 | 产品目录、按章节切分的知识、排查计划和视觉标注草稿 | 资料 ID、版本、来源、页码 / 章节、品类、型号、区域、语言、有效时间、发布状态 | 产品 / 售后专家确认操作适用范围 |
| 脱敏历史工单 | 标准工单、症状映射、开发集与独立验收集 | 原工单 ID、会话组、批次、原话出处、产品、症状、处置、结果、渠道、地区 | 数据负责人确认脱敏与字段含义，售后复核抽取 |
| 授权经销商名录 | 版本化名录和确定性匹配索引 | 经销商 ID、规范名、别名、平台、地区、授权状态、有效期、备注 | 渠道负责人确认冲突和授权语义 |
| SOP 与售后政策 | 条款原文、政策规则、决策样例 | 条款 ID、原文位置、版本、适用品类 / SKU、国家、平台、渠道、有效期、例外、费用承担 | 业务负责人审核资格及可自动执行范围 |

共同元数据建议包括 `source_type`（演示 / 组织方资料等）、`source_ref`、`doc_id`、`doc_version`、`content_hash`、`batch_id`、`publish_state`。不把资料来源和是否获准发布合并为一个字段。待审核资料默认不能进入正式检索与步骤库。

原始文件保留原样，映射、规范化结果、拒收报告、审核记录、发布清单分开保存。真实原始资料放经确认的受控目录；不自动提交 Git。敏感内容不能写进日志、评测快照或回放包。

## 5. 到资料后的快速流程

1. **先收一小份代表性样本。** 包含同名产品、型号差异、不同国家 / 渠道、成功和失败工单、至少一项政策例外。先确认字段和业务含义，再处理全量。
2. **固定首批验收范围。** 优先一个已有品类加一个新资料完整的品类，各选高频故障；一条排障成功路径、一条失败后换货 / 人工路径、一条咨询路径。
3. **预检与映射。** 输出字段映射、缺失 / 重复 / 冲突清单；给原文件计算哈希，记录来源批次；把验收样本隔离出来。
4. **分路转换。** 手册入章节与证据索引；工单进入清洗和结果标注；名录进入匹配库；SOP 进入条款和政策草稿。模型只辅助抽取，原文与审核结果必须保留。
5. **补可执行内容。** 审核症状映射、预写计划、视觉提示、故障卡、政策条件和动作边界。型号专用操作不能因为用户没报型号就放宽为品类通用。
6. **隔离试导入。** 跑离线校验、解析、元数据核对、证据可达性、检索和端到端案例；先消除错范围 / 错版本 / 错承诺，再调整召回和措辞。
7. **固定版本组合并发布。** 更新发布清单，加载一致的目录、计划、知识与政策；核实运行时版本和缓存。后续增量重复同一路径。

现有 `make seed`、`make kb-ingest`、`make kb-verify`、`make kb-anchors`、`make kb-eval` 可复用，但不构成已经完成的批次接入系统。`kb-anchors` 需先修复上述漏检；`kb-ingest` 会修改知识库并调用嵌入服务，资料权限和目标环境确认前不执行真实导入。

原 P1 的 #67–80 是本地规划票据，未核实对应在线 issue 状态。建议重排为：**#70 范围与发布 + #71 工单管线 + #73 名录 + #74 政策骨架先准备；#67–69 用真实内容补齐；#72 / #78 做真实评测；#75–77 / #79 按首批业务路径补；#80 后续做质量闭环。** 不再把数据未到作为通用校验骨架的阻塞。

## 6. 发布前验收门槛

- 来源可查：每条已发布资料、步骤与政策都能回到文件、版本、页码 / 章节；演示内容可机器识别且用户可见。
- 范围正确：错品类、错型号、错区域、未发布、已撤回、已失效资料均不可被使用；该规则同时覆盖远端知识、FAQ、故障卡和本地预写步骤。
- 版本一致：知识锚点存在；步骤与原文一致；同版本内容漂移被拒绝或显式产生新版本；更新不会把旧操作挂到新版引用。
- 流程闭合：确认产品 → 选计划 → 操作 → 用户反馈 → 下一步 / 结束；失败后进入正确售后路径；无资料明确交接。
- 办理正确：政策决策样例全对、越权为零、重复提交不重复创建；无法确认的结果进入查单 / 人工处理。
- 评测独立：真实验收集未参与知识和规则制作；分别报告各品类覆盖和失败原因。赛题基线作为目标，不能把合成测试通过率当作真实托管率或满意度。
- 发布可复现：配置、知识、政策、动作和接口版本有统一清单，缓存加载一致，回退按现有 runbook 执行。

## 7. 资料交接需要明确的事项

| 事项 | 具体需要 |
| --- | --- |
| 交付形式 | 文件种类、字段说明、数量、语言、扫描件比例、故障图片与工单关联键、更新频率 |

| 审核责任 | 操作步骤、症状标注、经销商冲突、政策条件各由谁确认 |
