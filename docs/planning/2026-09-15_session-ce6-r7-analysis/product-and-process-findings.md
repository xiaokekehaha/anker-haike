## 与 ce6 的共同根因

ce6 两次症状回答都有效，候选缩到吸力下降 / 拖地异常，却因配置缺少下一问而 R7。9db 则是没有消费图片、问题与计数目标错位，再因型号零匹配而 R7。两者共同把系统未能继续的原因归成“用户不明确”。上一轮症状决策重构没有完整处理产品澄清、视觉前置条件和无下一问的分支。

### 1. 输入证据与流程前置条件相互阻挡

当前路由先 disambiguate，再在产品 confirmed_sku/category_only 后进入 vision。缺品类时正需要图片提供线索，却被产品确认拦在读图之前。_new_fault_images 又只取本 run 图片，后续文字补齐型号时，先前未读图片不会自动补处理。

改造方向：先消费本问题未处理的文本和附件，记录来源与处理状态，再决定缺什么；图像可提供候选和待确认信息，不能自动提升为精确型号或故障结论。以附件 ID/内容身份记录处理进度，不能仅靠当前 run 判断。

### 2. 系统选择要问的字段，模型却可以问别的字段

clarify 节点按 decision.reason 计数，make_question 允许模型自由生成字符串，二者没有强绑定。日志说问了产品，不代表用户看到的真是产品问题。

改造方向：持久化明确的待回答问题（目标字段、问题 ID、问题内容、来源、回答处理结果）。确定问题目标后，文案必须表达同一个目标；简单字段优先确定性问题。收到信息应区分已回答但目录未覆盖、答非所问、无法回答、纠正旧信息。轮次上限只能兜底，不能代替这些判断。

### 3. 把信息状态与系统覆盖状态混在一起

产品 category_only 的建立还依赖该品类是否有通用计划；症状没有可配置下一问就被转成信息不足。前者混合“知道设备是什么”和“能支持什么”，后者混合“用户说了什么”和“系统会问什么”。

改造方向：先保存已知事实，再判断下一项合法动作需要什么。精确 SKU 仅在它改变步骤适用性时成为前置条件。品类已知、型号未匹配、信息不足、知识/问题覆盖不足，应保留不同原因。存在能改变方案选择的问题就继续询问；允许吸尘与拖地同时异常；没有支持的方案时如实说明能力边界。

### 4. 异响方案覆盖仍很浅

config/plans.yaml 的 abnormal_noise 目前仅匹配 rv_suction_motor_fault，步骤结果要求确认后停止使用等待人工，所有 next_on 都为 EXHAUSTED。来源片段描述“持续异响、焦味或机身过热”，会话只有“运行异响”，没有持续性或危险伴随现象的信息。

这不是本次 R7 的触发点，但修好入口后可能遇到。应依据已批准的产品知识审核风险条件、现象确认问题与可用步骤，避免直接将一般异响认定为电机故障；也不能为了延长对话绕开适用的停止条件。本轮没有验证外部手册或变更任何安全条件。

### 5. 展示与摘要需要使用真实决策依据

前端把所有 R7 固定显示为“多次澄清仍不明确”，掩盖问题覆盖不足与计数错误。ce6 的摘要只取 facts，漏掉已接受问答，写成“用户尚未描述问题”。两条会话 handoff_status 都是 prepared、case_id=null，实际只准备摘要，未显示已接入人工。

## 最小重做范围与验收

保留现有事实存储、目录和预写步骤；集中重做“证据消费 → 决定下一动作”这一边界，不另造更多并行状态机，也不只增加澄清次数。

需要覆盖完整会话回归：图片单独输入；图文输入后纯文字补充；问症状不扣产品次数；明确异响加未知型号；有效回答缩小候选却缺下一问；两种症状并存；已知品类但无适用方案；真实风险条件触发停止；摘要与实际问答、真实转交状态一致。

本轮完成只读诊断和副本验证，未修改应用、历史会话或部署。工作区已有视觉改造文件保持原样。
