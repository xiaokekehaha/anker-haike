# ce6 会话诊断结论

## 真实过程（2026-09-15，北京时间 16:32–16:33）
1. 用户“我的机器坏了”并上传图片；系统追问型号。
2. 用户“eufy X10 Pro Omni”；系统确认型号并问能否正常启动。
3. 用户“可以”；答案 yes 被接受，候选由 8 类降至 6 类。
4. 用户回答“效果不好”；对“是清扫或拖地的效果不好吗”的答案 yes 被接受，候选降为吸力下降、拖地异常。
5. 当前问题配置只有启动、充电指示、清扫/拖地效果三个判别问题，缺少区分吸尘与拖地的下一问。
6. 当前适用计划中 suction_low 有方案，mop_failure 无方案，无法走“候选拥有同一非空方案集合”的继续路径。
7. decide_symptoms 返回 reason=no_discriminating_question，outcome=escalate；clarify 将其映射为 R7，随后整理摘要。

## 直接证据
- 末轮 turn_decision.symptom_answered=true；两条 answers 都为 yes。不是回答没识别，也不是答案被覆盖。
- diagnostic_decision.reason=no_discriminating_question；不是 answers_unavailable，不是固定两次计数器触发。
- 原始 checkpoint 19 的副本运行真实 decide() 可复现；只在进程内补一个区分两类的问题，结果立即从 escalate 变为 clarify。见 repro.py / repro-result.json。
- UI 将所有 R7 固定显示为“多次澄清仍不明确”，与此次实际原因不一致。
- 摘要 problem 只从 facts 读取；facts=[]，因此写出“用户尚未描述问题”，忽略已存 answers 中明确的“效果不好”。
- handoff_status=prepared，case_id=null，消息明确说可复制给人工：实际没有接入人工或客服接单。
- 用户首轮上传了图片，但四轮节点没有 vision；该会话不能视为图片检查已经完成。本次未判断图片内容是否足以定位故障。

## 机制判断
这是上一轮重构未覆盖的设计缺口。旧的状态覆写已修复，但“没有可配置的问题”仍直接等价为“用户信息不足，转交”。本次用户持续提供有效回答，尚有成本很低且会改变可用方案的追问，因此停止过早。

合理的下一轮应询问：具体是灰尘/颗粒吸不干净、拖地后仍有污渍，还是两者都有？允许两种现象并存。确认拖地异常后如仍无方案，应说明能力覆盖不足，而不是反复要求用户描述。

需要分别修正：问题覆盖及无下一问的处理策略；R7 展示真实结构化原因；摘要同时利用事实与带问题来源的回答。仅追加一个问题可修本分支，但不足以解决其他未覆盖分支。
