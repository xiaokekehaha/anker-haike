## 0. 结论

1. **新版与 09-25 版只差一处**：第二章标题改为「读图：带着客户的问题提取证据（非核心）」。正文、4 张嵌入表、图片逐字节一致。
   所以这次复评的问题是：读图降级、不再照顾既有决策之后，方向该怎么调整。
2. **09-25 分析漏掉了一个结构性问题**：新版的工作单位是「服务事项」（一个 Worker 承接一个可独立完成的事项）。
   代码里没有这个实体，只有三个各管一段的替代品，外加一套手工同步的双份状态（§2）。
   分流、接稳、幻觉的变更处理、人工台、客户进度这五项都要在事项层上做，所以这是唯一需要**重做**的地方，其余都排在它后面。
3. **Leader / Worker 采纳为角色架构，但不做成多个自主 LLM agent**。09-25 分析的结论是「拒绝多 agent，保留现状调度」，
   其中前一半保留，后一半推翻：「一个活动 issue + 按序队列」满足不了新版的例子（召回 + 插头故障），需要重做（§3）。
4. **读图降级的后果**：T7（订单截图识别）、L1（照片回答观察题）、问题驱动读图、视觉评测集都不再投入。
   现有视觉代码保持原样，不删。
5. **两项从「可选」升为必做**：接稳的行动风险评分（新版明确要「综合评分 + 依据 + 建议调整」），
   AI 复核（只能否决、不能放行；新版异常表第 2 行要求）。

## 2. 重做：服务事项模型

### 问题

新版要的是「多个事项各自保存进度、各自完成、统一沟通」。代码里「一个客户诉求」散在三个实体里，每个只覆盖一段：

| 实体 | 覆盖什么 | 缺什么 | 位置 |
| --- | --- | --- | --- |
| issue | 一个设备的排障容器：事实、步骤、卡片 | 状态只有 `draft` / `open`，没有完成态；「完成」借用会话级 `stage=="done"`，这个值同时表示「排障解决」「案件关闭」「查询已答」 | `conversation/reduce.py:145,358`；`sessions/l3.py:562,701,901` |
| case | L3 办理记录：完整状态机、方案、授权、执行 | 只在 L3 路径上懒创建，只做排障的 issue 没有 case；与 issue 1:1，SKU 与订单号一旦写入不能改 | `cases/service.py:80,158,170`；`sessions/l3.py:142` |
| task_queue | 一句话里的多个意图 | 条目没有 `issue_id` / `case_id`；本身存在 issue 里面；同一 issue 的所有任务共用一个 case；单意图轮次不入队 | `conversation/tasks.py:61,81-90` |

另有两处结构问题：

- **双份状态**：`ISSUE_FIELDS` 里每个键都同时存在会话顶层和 `issues[active_issue_id]` 里，
  靠 `reduce.py:93-96,511` 和 `persist_issue`（`reduce.py:614-621`）手工同步，中途还有 4 处直接写 `issues[...]`（`graph.py:560,979,2770`、`l3.py:783`）。
- **同一事实多处存放**：订单号有 4 处（`case_order_no`、`case.external_refs`、`receipt.fields`、business subject）；
  「客户要什么」也有 4 处（`requested_remedy`、case 事件、`proposal.chosen_option_id`、任务意图）。

### 追踪：新版第四节的例子在现有代码里怎么走

客户一句话：「充电宝在召回名单里，插头也坏了，线是好的。」

```
understand ── interpret: intents=[refund_or_replace, report_problem]
   │
   ├─ reduce: 每条消息最多开一个 issue，事实都挂在同一个设备上      ← 两个产品并成一个 issue
   ├─ tasks.enqueue: 两个意图入队，按固定优先级排序，只发一句
   │     「您提到的需求将按顺序处理：A → B」
   │
   ├─ route_entry: 只走一条分支（L3 或排障）
   │     L3 → service_context → 建 case（一个 SKU）                  ← 订单只能挂一个 SKU（protocol.py:31）
   │                         → policy: 没有召回政策 → 无匹配 → 转人工 ← Remedy 里没有召回（common.py:205）
   │
   ├─ reply: 队列里有未完成任务时直接不出模型回复（graph.py:2794）      ← 回复不汇总其他事项
   │
   └─ 插头故障排在队列里，advance_tasks 只从 track / consult / close 进入（l3.py:1016）；
      前一个任务进了 await_human，路由只去 commit_issue，队列不会自动接续，
      客户得自己再提一次插头的事（graph.py:1279-1288 的显式恢复）           ← 与「等人工时其他事项继续」相反
```

注：09-25 分析 §2.3 说「`await_human` 不阻塞会话，其他 issue 可推进」，指的是客户主动切到另一个 issue 时可以推进；
这里说的是同一个 issue 里排队的任务不会自动接续，两者不矛盾。

如果插头报的是安全问题（R4），授权门会挡住整个会话的所有办理（`actions/gate.py:44-47` 检查会话内任何一条 R4），
而 reduce 层本意是只限制对应设备（`reduce.py:402-410`）。两层对范围的理解不一致。

### 方案

用一个一等实体「服务事项」（ServiceItem）替代三者，case 成为事项的持久化记录：

```
Session
 ├─ known        会话级事实投影：订单（含多行）、设备、区域渠道、已提供信息、口述已做步骤
 │               （09-25 分析 §3 的投影，从 issue 级提到会话级，跨事项共享）
 ├─ requests[]   客户原话里的每条诉求 → 对应 item_id；Leader 用它核对有没有遗漏
 └─ items[]      ServiceItem
       item_id
       kind        troubleshoot | recall | refund | exchange | query | human
       subject     设备 / 订单行（一单多品时指向某一行）
       phase       intake → gathering → troubleshooting → proposing → reviewing
                   → awaiting_human → executing → submitted → in_progress → done
                   | closed_unresolved
       waiting_on  customer | human | backend | none
       done_when   完成条件（客户反馈已解决 / 业务结果回执 / 人工结案），区分「已提交」「办理中」「已完成」
       facts       事项内事实（症状、步骤反馈、方案依据），引用 known 里的共享事实
       proposal / review / executions / commitments
       risk        R4 等限制按事项 / 设备生效
       priority, depends_on
```

每轮流程（Leader 负责调度与沟通，Worker 负责推进事项）：

```
客户输入
  │
  ▼
Leader.understand   一次模型调用：拆诉求、映射到已有事项或新建事项（代码校验映射）
  │
  ▼
Worker.advance × N  每个受影响的事项推进自己的状态机（排障子流程 / 办理子流程）；
  │                 不需要客户操作的事项（等人工决定、等物流回执）在后台推进
  ▼
Leader.schedule     在需要客户操作的事项里选一件：客户指定的优先，其次办得快的；
  │                 政策和依赖先过滤
  ▼
Leader.check        接稳检查（§5.2）：这一步会不会让事情更糟；给出分数、依据和调整
  │
  ▼
Leader.reply        一次措辞调用：本轮只引导一件需要客户做的事，同时汇总其他事项进度
```

### 为什么必要

- 分流：一句话多产品、一单多品、事项独立完成、等人工不影响其他事项，这四条都要求事项是一等实体。
- 幻觉：新版异常表第 5、6 行「暂停原动作，更新原任务」，前提是能说清是哪个事项的哪个动作。
- 人工台与客户进度：新版要求「分别展示各项服务进度」，现在客户侧只显示活动 issue（`frontend/src/state/record.ts:83,92`）。
- 接稳：「拟问信息是否已提供」要跨事项查，现在事实按 issue 隔离，换个事项就又问一遍。

### 可选复杂度

- 真正的并发执行（多个 Worker 同时调模型）：不需要。一轮内顺序推进受影响的事项就够了，「并行」指后台进度并行。
- 把 LangGraph 换成多图或 Send API：先不做。一个 Leader 图加两个按事项调用的子流程函数足够；需要时再拆子图。
- 事项之间的通用依赖求解：不做，只支持「A 完成后 B 才能办」和「同一订单行的退款与换货互斥」这两种。

## 9. 复议（同日）：「召回 + 插头」不典型，§2 的重做降级

用户质疑：这个例子典型吗？不典型就不该为它把系统做复杂。同意，本节取代 §2 的重做建议和 §8 的 E1 / E2。

### 证据

- 我们没有任何真实分布数据：`data/knowledge/kb_tickets/tickets.csv` 是 380 条脚本生成的工单，一条一个症状；主办方的脱敏工单还没拿到。
- 「召回 + 另一件故障品 + 一件正常品，一句话说完」是三个低概率条件叠在一起。召回本身是阶段性事件：发生时单一召回咨询会暴增，但很少和别的故障同框。
- 赛题对分流的原话是「一句话混杂多个需求」和「同一产品在不同渠道 / 国家的服务策略差异」。没有提召回，也没有要求一单多品。
- 新版文档表 4：AI 分流约 40% 是简单问题。高频的是单事项，其次是同一产品或同一订单上叠多个意图（故障 + 要换货、换货 + 改地址、故障 + 查另一单物流）。

### 第一性原理：客户要的是什么

1. 说过的每件事都有着落，不会被漏掉；
2. 已经说过的信息不再问第二遍；
3. 每件事按对应的国家 / 渠道政策处理。

满足这三条的最小机制不需要事项实体、后台并行或订单行：

| 需要 | 最小做法 | 现状 |
| --- | --- | --- |
| 不遗漏 | 诉求清单：每条诉求记原话和状态；结束会话或回复「还有别的吗」之前核对，有未处理的就接着办 | task_queue 已有雏形，缺两点：只在多意图时建（`tasks.py:61`），且转人工后不自动接续（`await_human` 只去 `commit_issue`） |
| 不重复问 | 会话级已知信息投影（09-25 分析 §3），跨 issue 共享 | 事实按 issue 隔离；T6 已补了一部分 |
| 按政策路由 | 政策按区域 × 渠道匹配 | 引擎已按 region / channel 取政策（`policy/engine.py:30-45`），但 27 条政策全是 US，其他区域全部转人工 |
| 统一回复 | 回复末尾一句汇总未完成的诉求 | 队列有未完成任务时直接不出回复（`graph.py:2794`） |

### 调整后的清单

**改为必做（小改动）**
- 诉求清单：单意图也入账；task 条目带上 `issue_id`；`await_human` 之后与「已解决」之后都检查诉求清单，自动接续下一条。
- 回复汇总：删掉 `graph.py:2794` 的抑制，末尾用固定模板列出其他诉求的状态；模型不描述挂起任务的具体动作（原抑制要防的风险）。
- R4 按设备生效：授权门只看当前事项设备的 R4。这是两层不一致的缺陷，与例子是否典型无关。
- 已知信息投影提到会话级。

**降为「有数据再做」**
- 服务事项实体重做、graph.py 按 Leader / Worker 拆分、双份状态合并：技术债是真的，但它不挡住高频场景；等真实工单显示「一句话多设备」占比不低时再做。
- 订单行（一单多品）、多事项后台并行、客户侧多事项进度条。

**召回只做单事项版**
- 召回名录 + 「我的产品在不在召回范围」查询 + 召回处置转人工审批；名录查不到就如实说查不到并升级（赛题禁止「编造召回答案」）。不做召回与其他事项的组合编排。

**不受影响**：接稳行动风险评分、AI 复核（只否决）、金额 / 地址检查、P0 各票、读图降级（§1、§5–§6 中不依赖事项实体的部分照旧）。

### 决赛主案例改选

用同一产品或同一订单上的多意图，外加一个区域差异，例如：

> 「Q45 耳机左耳没声音，想直接换个新的；另外我上个月那单充电器物流到哪了？」（Amazon US）

它能演示：诉求拆分与接续（排障 / 换货 + 物流查询）、问清（先排障再判断换货）、政策与授权门（换货条件）、统一回复汇总。
同一句换成 DE 官网渠道时，政策不同，演示「同一产品不同国家 / 渠道策略」。后者需要至少补一个非 US 区域的政策来源（09-25 分析 P2）。
