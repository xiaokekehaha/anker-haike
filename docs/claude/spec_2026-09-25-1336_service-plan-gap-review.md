# 《智能服务方案：痛点、解析、方案与优势》对照现状：迭代方向

日期：2026-09-25。输入：`~/Downloads/智能服务方案：痛点、解析、方案与优势.docx`（下称「方案」，含 4 张嵌入表）。
核对方法：四路只读代码审计（读图与防重复追问 / 多事项 / 审查执行与人工台 / 情绪·知识·渠道·指标），关键结论逐条抽查源码。
本文不改代码、不改配置、不提交。标「疑似」的条目只读过代码，未运行验证。

方案开头说的「现有 AI 售后系统已具备意图识别、补单、退款」指 Anker 线上系统，不是本仓库。
下文的差距指「anker-haike 要演示出方案里的能力还缺什么」。

## 0. 结论

1. 方案与现有系统骨架一致的部分：问清（判别树 + 卡片 + 观察门）、排障域防幻觉（计划库白名单 + 证据引用）、
   政策引擎（条款原文 + 缺输入转人工）、授权门 + 幂等、人工审批最小回路。这些可以直接作为预赛论据（§6）。
2. 方案反复强调「不重复索取、不重复操作」（读图、问清、接稳三节都提到）。现有系统在这条上有 8 处漏口（§2.1、§2.2），
   根因是事实分散在五处存储，没有统一的事实投影。这是一处底座改动，能同时覆盖方案的四节（§3）。
3. 方案的分流（第四节）是本仓库最大的新增量：同一会话多个产品、多个事项，各自推进、统一回复。
   现有代码支持「多 issue + 一个活动 issue + 按序队列」，但一句话里的两个产品会并进同一个 issue，订单只能挂一个 SKU，也没有召回概念。
4. 方案第六节的七行异常处理表里，有 4 行没有实现，其中「提交后结果不明」会重复调用创建接口，目前只靠 mock 后端的 upsert 避免重复建单。
5. 方案有四处主张与仓库既有决策冲突，需要你定（§1、§5）。

## 1. 对方案四处主张的态度

| 方案主张 | 既有决策 / 证据 | 态度 | 建议形态 |
| --- | --- | --- | --- |
| 读图「先读客户文字，带着问题看图」 | `diagnose/vision.py:159` 有意不给视觉模型看用户文字：09-15 实测用户说「滤网堵了」，qwen-vl 与 deepseek 都报出不存在的滤网堵塞 | 部分同意。目标对，做法要改 | 感知阶段继续不看文字（不看客户结论）。感知之后加一步：用从诉求导出的问题清单逐条核对 findings，输出「已回答 / 无法判断 / 与描述矛盾」。问题清单可以驱动局部裁剪复看（沿用铭牌复看的做法），不进感知提示词 |
| 分流用 Leader Agent + Worker Agent，独立任务并行 | D-L3-12「多意图顺序处理，并行打乱一次一卡」；09-18 复评「不做：加 agent」 | 同意需求，不同意做成多个 LLM agent | Worker = 现有 issue 状态机（每个事项一份）；Leader = 确定性调度（`reduce_turn` 分事项 + 优先级 + 遗漏核对）+ 一次回复组织（模型只做措辞）。「并行」指后台进度并行（等人工、等物流），客户操作仍一轮一步。方案自己在「需要进一步讨论的边界」里提的「一封邮件多操作 vs 每轮一步」就是这个张力 |
| 审查时「由另一个 AI 复核情境理解与处理方案」 | D-L3-5 政策 / 授权 / 执行零 LLM；06 §5 多模型交叉审核列 P2 | 有条件同意 | 只做否决信号：AI 复核只能「暂停转人工」，不能「放行」，确定性规则仍是唯一放行门。这与方案表第 2 行「程序检查与 AI 复核分歧 → 暂停交人工」一致。代价是每次办理多一次模型调用（约 1–2 s）。可选复杂度 |
| 接稳用「情绪 × 下一步风险」加权综合评分 | 已有四级情绪 + 轨迹 + 规则矩阵（`config/emotion_policy.yaml`） | 同意方向，评分公式是可选复杂度 | 情绪一侧已经有了；真正零覆盖的是行动风险一侧：重复索取、重复操作、停滞、失约的检测。先把这几项做成确定性特征并给出原因，评分公式等有案例再定权重 |

## 2. 逐节对照

### 2.1 读图（方案第二节）

| 方案要求 | 现状 | 差距 |
| --- | --- | --- |
| 围绕诉求提取证据 | 视觉调用只收图片 + 固定指令（`diagnose/vision.py:159-178`） | 没有问题清单，也没有「哪些仍无法判断」的输出 |
| 写入共享信息提取表 | 图片事实进 `issue.facts`，但没有 `observation_id`（`diagnose/observations.py:43` 只认带 id 的观察） | 照片已拍到充电触点脏污，计划仍会问「基站与主机的充电触点状态如何？」（`config/plans.yaml:214`） |

| 划痕 / 使用痕迹 / 漏液的凭图核实 | 只有安全词触发 R4 | 没有「凭图核实客户主张」的流程（方案嵌入表第 2、3 行） |
| 需要图片案例检验 | `data/eval/vision/cases.yaml` 为空集，README 标 pending_data | 真实故障照片 0 张 |

另：未核实的铭牌读数存在 `visual_product.model_hint`（`sessions/graph.py:450-455`），不能跳过确认是对的，
但目前完全没用上，后续仍开放式问型号。可以作为产品卡的首选项，仍需用户点确认。

### 2.2 问清（方案第三节）

现状是最强的一节：判别树最小分裂选题、≤6 族首问多选、观察卡片、三态反馈、R7 预算。差距集中在「已提供 / 已完成」的识别：

- 客户说「重启过了」没有对应事实类型；步骤只按「本会话已执行」或「同源指令」跳过（`diagnose/decision.py:445-452`），会再下发一次。
- 购买日期不能从文字里取（`conversation/interpret.py:56` 的 context_field 只有 region / channel / platform）。
- 凭证卡只用 OCR 结果预填，不用用户已经打出来的订单号、已知的渠道（`sessions/receipt.py:261-269`）。
- 是否需要收凭证只看 `receipt.status`（`receipt.py:314-320`），订单号已绑定的判断只在 L3 分支里。
- 「不知道型号」只看当前这一轮文字（`sessions/clarify.py:314`）。
- Amazon 邮件「两轮锁定问题」：没有邮件渠道（§2.8）。

### 2.4 接稳（方案第五节）

- 情绪检测与策略：四级 + 引文校验 + 规则只升不降 + 轨迹，已有（`emotion/policy.py`）。
- 策略动作大多没有消费者：`offer_human`、`skip_optional_clarify`、`suggest_compensation_review` 只出现在 YAML 与一条巡检断言里；
  `shorten_steps`、`flag_complaint_risk` 实际按策略名或情绪级别判断，不读动作。只有 `prefer_proposal_over_more_steps` 被读取（`diagnose/decision.py:670-675`）。
- 三种策略的 YAML `prompt` 不生效，走的是 `prompts/system.py:27-34` 里写死的文案；写死的 `reassure_and_shorten` 含「承诺尽快解决」，与 YAML「不做无法兑现的承诺」矛盾。
- 行动风险检查（方案的核心）：没有。已有的是分散的护栏（同步骤不重发、同观察最多问 2 次、跳过 3 次停止、上下文卡只问缺项）。
  承诺账本有记录（`cases/service.py:357-380`），没有逾期 / 失约检查；没有客户侧等待时长。
- 观测：看板「非平静情绪占比」的说明写「首轮情绪」（`frontend/src/admin/pages/Board.tsx:69`），实际存的是最新一轮（`analytics/derive.py:220`）。

### 2.6 知识准备（方案第七节）

- 结构：手册每篇一个文件、带 front matter，可单篇替换；计划库 57 条在一个 `config/plans.yaml` 里，只有整体版本号，单步骤不能单独替换。
- 按国家 / 渠道：`KnowledgeScope.region` 字段存在，检索过滤没用它（`knowledge/adapter.py:242-262`）；政策 27 条全是 US，其他区域 `no_policy_matched` 转人工。
- 发布状态：`publish_state` 写死为 `published`（`knowledge/official.py:187-188`），没有任何过滤读它；没有「草拟 → 审核 → 发布」。
- 「AI 读资料 → 模拟求助 → 暴露缺口」：没有。可复用的零件有：`make kb-eval`、`make kb-official-verify`、`make kb-anchors`、`make inspect`，以及线上的 R5 / `knowledge_coverage_missing` / 检索无命中率。
- 步骤配图配视频：`TroubleshootStep` 没有媒体字段。

## 3. 共用底座：统一事实投影

**问题**：事实分散在五处：`issue.facts`（用户陈述、图片观察、图片签名、步骤反馈）、`steps_executed` / `step_attempts`、
`BusinessContext.subjects[].facts`（订单）、`state.receipt`、`service_context`。每个「要不要问」的判断各自只看其中一两处。

**追踪一例**：

```
用户上传基站照片 ──► vision findings: 充电触点 / 污渍
                      │
                      ├─► issue.facts: kind=observation, source=image_observation（无 observation_id）
                      │
decide_next ──► 计划 dock_* 需要观察 dock_contacts
                      │
                known_observations() 只认带 observation_id 的事实  ──► 视为未知
                      │
                      └─► 下发观察卡：「基站与主机的充电触点状态如何？」   ← 客户刚拍过
```

同形状的漏口还有：未核实铭牌读数不进产品卡、打字给出的订单号不进凭证卡、口述「已经重启过」不成为事实、口述购买日期无处落。

**方案**：在现有 reduce 层加一个只读投影 `known(field)`，统一回答「这个信息有没有、来源是什么、置信如何」：

```
来源                               投影字段（示例）
───────────────────────────        ─────────────────────────────
user_report / image_observation    observation[obs_id] = value, source, verified
receipt OCR / 订单查询              order_no, purchase_date, channel, sku, region
step_feedback / 口述「已做过」       step_done[step_id] = claimed | executed
service_context                    region_purchase, region_use, platform
```

凡是「出卡 / 追问 / 下发步骤」之前都先查投影；图片来源的值标 `verified=false`，出卡时作为预选项让客户确认，而不是跳过确认。

**为什么必要**：方案第二、三、五、八节都依赖它（读图复用、问清不重复、接稳的重复索取检测、人工台的「已提供信息」）。
不做它，每一节都要各自再写一遍「查一下有没有」。09-18 复评 P1「推断与事实分离」也落在这里。

**可选复杂度**：把五处存储物理合并成一张表。不需要；投影足够，存储保持现状。

## 4. 优先级

### P0：小改动、直接对应方案表格、演示可见

| 项 | 改动 | 对应方案 | 验收 |
