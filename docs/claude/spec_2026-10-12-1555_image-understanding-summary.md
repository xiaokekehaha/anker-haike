## 1. 核心判断

**照片不是内容，是一次测量。** 模型读图会出两类错：

| 错误 | 系统能否察觉 | 补救成本 |
| --- | --- | --- |
| 漏读（没读到型号） | 能，字段为空 | 追问一句 |
| 误读（编出一个型号） | 不能，字段看起来正常 | 锁错产品，整条排障路径错 |

另一个实测事实：模型看不清时不知道自己看不清，自报置信度不随画质变化。
所以方案的主线是：**可信度在模型外部建立**，未知是默认值，误读要降级成「多问一句」。

## 2. 流水线

```
上传
 │
 ▼
L0 预处理（prepare.py，无模型）
 │  EXIF 方向写进像素；超过 12MP 才降采样；无改动不重编码
 ▼
L1 像素门控（quality.py，无模型）
 │  过暗 / 过曝 / 太小 / 模糊
 ├── 命中硬阈值 ──► 补拍卡（具体原因 + 指引），0 次模型调用
 ▼
L2 纯图读图（vision.py，1 次模型调用）
 │  输入只有图片 + 指令，看不到用户文字和产品名
 │  输出顺序：observations → content_kinds → findings → model_hint
 ▼
L3 铭牌复看（_reread_nameplate，按需 1 次调用）
 │  model_hint 非空即触发：按 cell 裁出那一格、外扩 50%、放大 2×，再读一次
 │  confirmed / overridden / erased / skipped:<原因>
 ▼
L4 代码层融合（无模型）
 │  受控词表归一 → 签名映射到排障方案 → 图文冲突比对 → 安全词检查
 ▼
L5 对用户
    隐式回显「从照片里我看到：…」/ 冲突澄清 / 安全升级 / 型号确认卡
```

L0、L1、L4 全部是确定性代码，可单测、零 token。模型只出现在 L2、L3。

## 3. 提取什么信息、怎么适配不同的图

不按图片类型各写一套提取模板，也不让模型自由描述。提前准备的是一套**固定 schema + 受控词表 + 签名表**，
所有图走同一次调用；图不同，变的是哪些字段有值。

### 3.1 提前准备的三样东西

| 准备项 | 位置 | 内容 | 来源 |
| --- | --- | --- | --- |
| 输出 schema | `VisionObservation`（`diagnose/vision.py`） | observations / content_kinds / findings / image_quality / model_hint / model_hint_cell / model_hint_image | 从下游消费者反推，零消费者的字段已砍（§4.3） |
| 受控词表 | `config/vision_vocab.yaml` | 29 个部件（覆盖五个品类，如滚刷、尘盒、镜头、鸭嘴阀）、16 种现象（缠绕、堵塞、满、破损、烧焦、鼓包等），另加「其他」「不可辨」 | 人工维护；评测发现缺词就补（如「满」） |
| 签名表 | 同文件 `signatures` | (部件, 现象) → 官方 Q&A 方案，如 `滚刷+缠绕 → qa_rv_0272 / 0189 / 0408`、`镜头+污渍 → qa_bp_0201` | 主办方官方 Q&A，每个型号一条 |

读图指令由词表生成（`_instruction()`），词表是唯一真源，改词表即改提示词。

### 3.2 一次调用适配不同的图

指令要求按固定顺序输出，字段顺序即生成顺序：

```
第一步 observations   看见了什么（自由文本，≤5 条，每条 ≤20 字）
第二步 content_kinds  逐图定性：fault_photo / document / other
第三步 findings       只给 fault_photo 写；part / phenomenon 从词表选，附 evidence、cell、image_index
其余   model_hint     有铭牌才逐字符抄，看不清的字写 ?，没有填 null
       image_quality  能否看清
```

| 上传的图 | observations | content_kinds | findings | model_hint |
| --- | --- | --- | --- | --- |
| 扫地机底部，滚刷缠满头发 | 「滚刷表面缠绕大量毛发」 | fault_photo | 滚刷 / 缠绕 / 中下格 | null |
| 亚马逊订单截图 | 「订单页面，含订单号与金额」 | document | 空 | null |
| 机身背面带铭牌 | 「机身背面有铭牌标签」 | fault_photo | 外壳 / 正常（不回显） | `X10 Pro`，右下格 |

「不同的图提取不同信息」靠两点：字段允许为空，加上模型先给每张图定性。
不需要先调一次分类模型再路由到不同提取器，省一次调用和一次路由出错的机会。

### 3.3 提取结果怎么变成可用信息

模型输出只是原料，后续由代码消费：

| 字段 | 去向 |
| --- | --- |
| findings | 查签名表得到方案 → 写成 `source_kind=image_signature` 的症状事实，与文字症状同等进候选集（§4.9）。签名表外的组合（如外壳 / 破损）只记为事实并过安全检查 |
| model_hint | 裁剪复看，两次一致才自动锁产品，否则出确认卡（§4.7） |
| content_kinds | document 图不算换货所需的「故障图片」证据（§4.8） |
| observations | 安全词检查（烧焦、鼓包直接升级）；补充检索 |

### 3.4 单据有独立的固定字段提取

流程走到收集购买凭证时，调用的是另一个任务 `warranty.receipt_ocr`（`sessions/receipt.py` 的 `ReceiptOcr`），
固定抽订单号、销售方、国家、购买日期、金额，外加 `unreadable` 字段列表，结果出确认卡让用户核对。

走哪种提取由**流程当前在等什么**决定（排障中走读图，收凭证时走订单识别），不是看到图再猜。
这也是 §4.8 问题的来源：客户在首问里就传订单截图时，系统一度把它当故障照片处理，所以读图里补了逐图定性。

### 3.5 这套做法的边界

- 词表外的东西只能落到「其他」，对应不到方案；新品类、新故障要人工补词表和签名表。
  这是有意的取舍：受控词表就是让模型在选项里选，而不是自己造词。
- observations 是自由文本，仍可能编造细节，因此不参与锁产品和选方案。
- 09-26 读图降级后，「上传任意截图即自动识别订单」（T7）不做。

## 4. 技巧逐条

### 4.1 预处理：保住像素，不盲目压缩（L0）

- **问题**：手机竖拍带 EXIF 方向，原样送模型就是一张侧躺的图；常规做法把图缩到约 1MP 省 token。
- **例子**：3000×2250 的整机图缩到长边 1568 后，铭牌小字直接消失。
- **方案**：`ImageOps.exif_transpose` 把方向写进像素；只有超过 12MP 才降采样；无需改动时零重编码。
  代价是首轮调用更贵更慢，换来小字可读。

### 4.2 像素门控：差图不送模型（L1）

- **问题**：模型自报的 `usable` 不可靠；差图送进去只会得到建立在看不清之上的结论。
- **方案**：四项像素指标 + 两档阈值（`config/vision_vocab.yaml` 的 `quality`），硬阈值直接出补拍卡。

| 指标 | 量法 | 为什么这样量 |
| --- | --- | --- |
| 过暗 | 灰度 **95 分位** | 用中位数时，曝光正常的深色机身图只有 64，会被误判欠曝；Anker 设备多为深色。95 分位问的是「画面里还有没有正常曝光的地方」，正常深色机身约 205，真欠曝塌到 30–47 |
| 过曝 | 亮度 ≥250 占比 **且** 结构塌陷 | 单看饱和占比，白底订单截图天然 80–96%，10 张官方附件里 5 张被误拦（10-09）。改为「饱和且梯度结构塌」：白底文档 133–201、真过曝 13–80，分得开 |
| 太小 | 短边像素 | 低于 300 基本是裁剪截图或极远拍 |
| 模糊 | 对比度归一后梯度 **99.5 分位** | 拉普拉斯方差在模糊半径 ≥2 后饱和；梯度均值受画面平坦度影响。只做软阈值，不单独拦人，因为阈值是合成图上标的 |

- `usable = 像素层 AND 模型判定`。模型只能补充「我也看不清」，不能推翻像素层的硬拦；
  模型说不可用时，像素层的软原因并进补拍指引，告诉用户是「太暗」还是「太远」。

### 4.3 字段由下游决策反推（L2 schema）

- **问题**：每多一个字段就多一个「请给我一个值」的要求，模型倾向给值而不是拒绝。
- **例子**：旧 schema 的 `severity` / `location` / `quote_region` 全仓零消费者；`confidence` 被当阈值决定排障先验，而它是模型自评。
- **方案**：只留有消费者的字段：`findings{part, phenomenon, evidence, cell, image_index}`、`model_hint`、`model_hint_cell`、
  `content_kinds`、`image_quality`。砍掉 `severity` / `location` / `confidence`；`quote_region` 改为九宫格 `cell`，第一次有了消费者（裁剪坐标）。

### 4.4 受控词表 + 「不可辨」通道

- 部件、现象用 `vision_vocab.yaml` 枚举，指令由词表生成，词表是唯一真源。
- 「不可辨」与「其他」分开，并写成正常选项：模型默认不会主动弃答，必须给出这条路。
- 平衡项：报告同时统计「无幻觉率」与「未过度弃答率」（门槛 ≥90%），防止退化成全部「不可辨」。
- 签名判定从 `confidence >= 0.7` 改为符号条件：部件、现象都可辨，且 `evidence` 非空。

### 4.5 describe-first 与正向指令

- schema 字段顺序即生成顺序：先写 ≤5 条可见事实（observations），再逐图定性，最后填故障枚举；
  `evidence` 要求抄 observations 里的那句话。
- 指令只写「要做什么」（「仅输出图中可直接看到的内容」），不写「不要编造」。
- 契约层把 `""` / `无` / `null` 归一为 `None`，修掉模型「留空」导致枚举校验失败（schema 首过率 93% → 100%）。

### 4.6 图文分路：视觉调用看不到用户文字（A5）

- **问题**：用户的先入之见会污染测量；同一次调用再报告「图文是否冲突」，是被污染的一方在报告自己有没有被污染。
- **例子**（`mislead_filter`：图中滚刷缠满毛发、滤网干净，用户说「应该是滤网堵了」）：

| 模型 | 文字同调用、无 evidence | 文字同调用、要求 evidence | 图文分路 |
| --- | --- | --- | --- |
| glm-4.6v | 只剩「滤网正常」，真实故障丢失（2/2） | 滤网正常 | 滤网正常 2/2 |
| qwen-vl | 滤网正常 | **滤网堵塞**，并编出证据「网格被灰尘完全覆盖」（3/3） | 滤网正常 2/2 |
| deepseek | 滤网正常 | **滤网堵塞**（r=2 两次） | 滤网正常 2/2 |

  结论：`evidence` 只有在测量独立时才是反幻觉锚点，否则会变成事后合理化。

- **方案**：
  - `build_messages` 签名里没有 `text` 参数，用类型保证视觉调用拿不到用户文字。
  - 读图用独立系统提示，不注入情绪策略和会话状态。查出旧的 `_state_summary` 一直在塞用户症状和**产品名**——
    先告诉模型型号，它会抄下来而不看铭牌。
  - 图先文后，多图逐张加 `Image N:` 标签。
  - 冲突改在代码层用词表 + 用户口语别名做符号比对（`conflict.py`），三种形态：同部件不同现象 / 用户点名 A 而故障在 B /
    用户点名的部件没拍到。上例输出「您提到的是滤网，但照片里看到问题的是滚刷（缠绕）」。
  - 守卫：没有任何带证据的 finding 时不说「照片里没拍到 X」，不在一无所知时反驳用户。

### 4.7 铭牌裁剪复看：重新测量优先于加强推理（L3）

- **问题**：小铭牌上模型会编出格式完全合理的假型号，且不带 `?` 占位。
- **例子**（09-14 合成图，3000×2250，铭牌金标 3 行）：

| 铭牌字号 / 占全图 | deepseek 全图 | qwen-vl 全图 | glm-4.6v 全图 | 九宫格裁剪 + 2× |
| --- | --- | --- | --- | --- |
| 34px / 0.84% | 3/3 | 3/3 | 3/3 | — |
| 22px / 0.38% 低对比 | 1/3 | 3/3 | 3/3 | 三家 3/3 |
| 14px / 0.15% 低对比 | 0/3，编出 `MODEL YJ-107-2-P / SN: ADV23751P`，复跑编出另一组 | 3/3 | 3/3 | 三家 3/3 |

  10-09 复测同一现象：14px 铭牌实际 `X10 Pro`，DeepSeek 两次给出 `X1C Pro`、`XJC Y10`；裁剪后四家均 6/6。

- **方案**：按模型给的 `cell` + `image_index` 从**原图**裁出该格、四周外扩 50%、放大 2×，第二次调用只做逐字符转写，再交叉核对：

```
两次一致                 → confirmed，verified=True，可自动锁 SKU
两次不一致               → overridden，取裁剪值，verified=False，出确认卡
裁剪图读不出             → erased，清空型号，回到追问
无 cell/无序号/预算不足  → skipped:<原因>，verified=False
```

- 两条从失败里得到的规则：
  1. **校验的触发条件不能来自被校验者。** 最初「读不清才复看」，而编出来的型号没有 `?`，按字面判「读全了」，绕过复看；
     改成「看到铭牌才复看」后，阶段 1 一次 deepseek 编出 `T2351` 时恰好没给 cell，又绕过了。
     最终触发条件是 `model_hint` 非空，任何会被下游消费的型号都要复核。
  2. **使用权限挂钩验证等级。** 只有 `verified=True` 的型号能自动锁产品；未验证的进产品候选，让用户点一下确认。
     deepseek 的失效方式由此从「静默锁错单」降成「多问一句」，它的速度优势才成立。
- 可观测性：`reread_verdict` 写进 trace。r=3 每家 90 次中 overridden 2–3 次，这些在旧逻辑里会直接锁 SKU。

### 4.8 逐图定性：上传时机不等于图片内容

- **问题**：`purpose=fault` 记的是「上传时系统在等什么」，却被当成图片内容。客户首问里传的订单截图既被当故障照片做曝光门控，
  又凑齐了换货证据的「故障图片」一项（10-09 官方 63 单复核）。
- **方案**：同一次读图调用加 `content_kinds`（fault_photo / document / other），不增加调用次数。
  判为 document 的图不产生 finding、不算故障证据。方向取「排除确认是单据」，读图失败时退回旧行为，
  视觉链故障不堵死换货流程。

### 4.9 照片结论进入排障决策

- **问题**（09-17 会话复现）：照片读出「滚刷缠绕」，客户文字说「异响」，候选集按文字症状过滤，
  `rv_suction_hair_wrap` 被筛掉，最后落到「确认异响后停机等人工」。原因是读图事实是 `kind=observation`，不带症状码。
- **方案**：可用 finding 按签名找到方案，把方案的症状码写成 `kind=symptom, source_kind=image_signature` 的事实，与文字症状同等进候选集；
  部件观察（滚刷、尘盒）推出待确认品类。
- 10-12 补一条（T48）：读图不随意图走。客户拍指示灯问绿灯含义被判产品咨询，读图只挂在排障路径上，图里的外壳裂纹丢失；
  改为有未读图片先读图（事实进问题记录、过安全检查），读完回到产品咨询。

### 4.10 回显用隐式确认，且由代码拼句

- 步骤卡首句「From the photo I can see: … If that's not right, just tell me.」放独立字段 `StepCard.seen`，不混进已审核的步骤原文。
- 句子由代码从 finding 确定性拼出，不经模型再措辞，避免把可能编的内容再念一遍。只回显一次，只回显有证据的故障项（「吸口正常」不回显）。
- 读图属于高置信、低后果，用隐式确认；退换、判责等不可逆动作仍走显式确认。

### 4.11 评测：按失效方式裁决，不按平均分

- **问题**：阶段 1 报告 deepseek 综合 95%、qwen-vl 84%，工具判 deepseek 主位；而 deepseek 是唯一编过铭牌的，qwen-vl 是唯一在误导文字下编证据的。
  两种幻觉各扣几分，被其他样本补回。
- **方案**：字段级指标（部件、现象、方案命中、铭牌读出、无幻觉、安全召回、可用判定、未过度弃答）+ 两段式裁决：
  先过硬门（铭牌无幻觉 100%、误导文字无幻觉 100%、未过度弃答 ≥90%），不过的直接出局，再按准确率排序。
  期望里的现象从签名表反查，不手写，避免「滤网满」和「滤网堵塞」都对却被判错。报告表头带提示词与词表版本。

## 5. 效果

### 5.1 合成图 bake-off（`reports/bakeoff-*`，各阶段 repeats 不同，方向性对比）

| 指标 | deepseek 基线 → 阶段 4 | qwen-vl | glm-4.6v |
| --- | --- | --- | --- |
| 综合准确率 | 65% → 96% | 80% → 93% | 69% → 91% |
| 铭牌读出率 | 67% → 100% | 100% → 100% | 0% → 100% |
| 无幻觉率 | 83% → 100% | 100% → 100%（阶段 1 曾降到 83%） | 100% → 100% |
| 部件 / 方案命中 | 83 / 67 → 100 / 100 | 83 / 83 → 100 / 100 | 83 / 67 → 100 / 83 |
| 可用判定 | 100%（6 例） | 100% | 100% |

可单独归因的两项：铭牌行的提升来自裁剪复看（日志逐条 confirmed / overridden）；误导文字用例的无幻觉来自图文分路。
像素门控的 `gate_underexposed` / `gate_too_small` 三家均 **0 token、4–15 ms** 出补拍卡；深色机身、大片纯色铭牌两条对照无误伤。

## 6. 解决的难点

| 难点 | 失效表现 | 对应技巧 |
| --- | --- | --- |
| 小字幻觉 | 编出格式合理的假型号，不带 `?`，复跑结果不同 | 保像素预处理 + 无条件裁剪复看 + 未验证不锁 SKU |
| 模型不知道自己看不清 | 自报 usable / confidence 不随画质变化 | 像素门控外生可信度，`usable` 取 AND |
| 用户先入之见 | 真实故障被挤掉，或为不存在的故障编证据 | 图文分路（类型约束）+ 代码层冲突比对 |
| 深色设备与白底单据 | 正常深色机身判欠曝，订单截图判过曝 | 亮端 95 分位；过曝 = 饱和且结构塌 |
| 上传时机被当成图片内容 | 订单截图当故障照片，凑齐换货证据 | 同一次调用逐图定性 `content_kinds` |
| 照片结论被文字症状过滤 | 照片说缠绕，文字说异响，正确方案出局 | 签名写成 `image_signature` 症状事实 |
| 平均分掩盖静默错误 | 编造过的模型综合分最高 | 字段级指标 + 硬门两段式裁决 |

## 7. 边界（材料里需如实说明）

- **09-26 起读图降为非核心**（[方向复评](spec_2026-09-26-1656_service-plan-direction-v2.md)）：订单截图识别 T7、照片回答观察题 L1、问题驱动读图、视觉评测集不再投入。
  现有流水线保留并继续修缺陷（10-09 逐图定性与过曝判据、10-12 带图咨询先读图）。
- bake-off 主体是合成图：对小字、曝光等分辨率问题有效，对真实故障纹理无效。安全召回（烧焦、鼓包）在合成图上不作数。
- 真实照片只有官方 5 张实物 + 5 张单据，每项两遍，100% 只表示这些检查项通过。

  字段级高分不等于无幻觉。这些文本不驱动锁单或方案选择。
