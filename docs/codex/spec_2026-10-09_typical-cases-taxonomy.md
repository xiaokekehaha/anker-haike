# 客服典型案例与难点分类

日期：2026-10-09。用途：解释哪些真实输入会使客服回答出错、错误发生在哪个环节，以及合理流程应满足什么条件。

核心难点是把客户诉求、故障事实、业务对象和知识适用条件对应起来，并在多轮交互中保留这种对应关系。关键词相同、资料已召回、模型选中方案、人工请求已登记，分别只能证明各自环节的结果，不能直接证明客户问题已经解决。

本文收录官方 63 案例首测、此前抽样测评和修复复测中的典型问题。**历史案例用于说明失败机制，不表示这些问题在当前版本仍未修复。** 首测、后续复测和构造示例分别标明；已修复问题仍保留为回归用例。修复是否完成，以对应版本的验收记录为准。

## 1. 术语与分类总览

- **意图**：客户希望系统做什么，例如排障、查询物流、购买配件、联系人工。
- **实体**：被谈论的具体对象，例如一台设备、它的充电盒、订单、商品或包裹。
- **事实**：有原始来源的陈述，包括现象、已做操作、查询结果；客户陈述与后台记录可能不同。
- **召回**：从知识库找出候选资料。**排序**：决定候选先后。**适用性**：判断候选的对象、现象和前提是否符合当前问题。
- **任务**：一项诉求及其处理状态。**交接**：将需要人工办理的请求和信息交给人工处理流程。
- **LLM**：大语言模型，用于理解自然语言和提出判断；规则负责可以明确核验的约束。

一个案例可以涉及多类问题。以下按主要失败环节分类，案例数量不能相加作为失败总数。

| 分类 | 核心难点 | 代表案例 | 错误会怎样影响回答 |
|---|---|---|---|
| A. 意图与说话来源 | 谁在说话、要求处理什么 | T11、T58/T60、早期 T1/T7/T56 | 把设备提示当成人工请求，把物流问题当成设备故障，未明确问题就交接 |
| B. 实体类型、关系与归属 | 整机/部件、上下游、订单/配件是否对应 | T52、T47、整机主语误澄清回归 | 给错对象排障，或用旧包裹回答新配件 |
| C. 事实含义与并列症状 | 肯否、时间方向、确定性、问题范围 | T50、T61、T57 | 把能工作变成不能工作，把提前启动变成无法启动 |
| D. 召回、排序、选用与校验 | 正确资料在哪一层丢失 | T18、T22、T30、T34；T13 对照 | 明明有资料却说无指导，或拿相似资料强行出步骤 |
| E. 知识转交互流程 | 问句、操作、材料、说明和条件分支 | T46、T19/T24/T26/T40 | 让客户对事实问题点击“未解决”，并误记为操作 |
| F. 历史操作与多轮状态 | 已做什么、何时做、结果如何 | T27、T36、T37、T31 | 重复已做检查，首次求助却跳到重新决策 |
| G. 多诉求与任务结束 | 一项受阻后其他诉求如何继续 | T9、T51/T53、T63 | 漏掉购买或排障，仍有待办却宣布结束 |
| H. 附件用途与材料条件 | 图片是什么、能证明什么、是否必需 | 早期 T55、T46、T40、T48 | 将发票当故障照片，或把“未解决”当作材料已补 |
| I. 人工交接与办理结果 | 摘要完整、对象一致、请求真实登记 | 多轮 T9、T22、T34、T63 | 只说已转交却未登记，人工收到旧要求或错误信息 |
| J. 回复范围与中断恢复 | 正常说明、失败状态、重试边界 | T35；中断构造用例 | 半段答案像已完成，或重试重复办理业务 |
| K. 数据与评测质量 | 资料错误、冲突、缺口和标签错误 | T2、T4、T46、T57；T50/T52/T61 标签 | 奖励错误回答，或把合理澄清误判成失败 |

## 2. A：意图与说话来源

问题：出现“联系客服”不能直接推导出客户要求人工；出现“不工作”也不能直接推导出设备故障。需要确定这句话的说话者、指向对象和当前求助目的。

| 案例与输入要点 | 历史错误链路 | 根因 / 备注 | 合理处理与验收点 |
|---|---|---|---|
| T11：设备 EB1L 提示包含 `Click to contact customer service for assistance` | 判断客户主动要人工 → 跳过排障 → 交接 | 正常路径由模型判断意图，程序只检查引文出现在原文，没有核验来源；关键词兜底也有同类风险。正确 EB1L 资料 `rv-0481` 存在 | 将设备文案作为故障证据；仅客户本人的明确请求触发主动人工。真实人工请求和安全升级仍应生效 |
| 早期 T1：主机未收到，只收到配件 | 将未收到货理解成设备故障 → 进入排障 | 物流对象和设备状态未绑定。早期三次观察仅一次误判，不是必现；后续复测正常 | 查询主机与配件的物流，不凭“未收到”生成设备故障 |
| 早期 T7：tracking number `not working` | 将追踪号查不到理解成设备坏了 → 先问型号 | 模型将状态谓语绑定错对象；意图排序再把错误排障诉求提前 | 追踪查询失败属于物流；若同一句另有“摄像头离线”，保留独立故障诉求，不能整句统一归类 |
| 早期 T56：摄像头离线，反问 `Is that your warranty?` | 优先查保修 → 无订单却提示“涉及多个订单” | 反问的语用含义被误读；零候选被错误表示成多对象歧义。这是两层问题 | 保留离线求助；区分“没有订单”和“有多个可能订单”。客户明确说先别排障时应尊重停止范围 |
| T58/T60：对 App 表达不满，具体阻碍不明 | T58 提供暂停/人工选项却未问具体问题；T60 检索无匹配后直接交接 | 情绪诉求与具体问题未分开；T60 的描述完整性按词数放行，不能证明已具备可排障信息 | 询问在哪个操作、哪一步、出现什么现象；已有型号直接复用。明确人工请求或安全风险按各自规则处理 |
| T45 对照：客户报告烫伤 | 立即停用、禁止充电并安全升级，没有操作卡 | 安全升级有独立事实依据，与设备文案里的“联系客服”不同；属于已验证的正确行为 | 保留独立安全路径，不能因收集一般症状或处理其他任务而重新开始受阻排障 |

**“设备在说话”只适用于具体片段。** T11 的问题描述重复了设备推送，因此该段属于设备文案；不能据此把所有 `Problem Description` 字段都当作设备消息。该字段也可能是客户自述，或者同时包含设备引文与“请直接帮我联系人工”。来源应保留输入位置和片段范围。

必要方案是带来源的意图与事实记录。只删除一个关键词，或增加一条“description 都是设备文本”的规则，会在新的表达上再次出错。

## 3. B：实体类型、关系与归属

问题：实体识别既涉及多个产品，也涉及一件产品的内部关系。发现两个名称不同，还需要判断它们是同一对象的不同称呼、整机与部件、上下游部件，还是不同订单的商品。

| 案例与输入要点 | 历史错误链路 | 根因 / 备注 | 合理处理与验收点 |
|---|---|---|---|
| T52：`My charging case will not charge therefore I cannot charge my pump motors` | 检索充电主题 → 选“泵放在盒子里充不上电” → 优先检查盒子到泵的触点 | 将“电源 → 盒子”的故障，换成“盒子 → 泵”的故障。原句在事实和查询中保留，不能统一归因于上游没抽到句子；仅比较模型填写的候选主语，无法区分同一盒子的受电/供电角色，详见 §3.1 | 先处理盒子自身的输入供电；有歧义时明确区分两种方向。候选和追问都不能预设成下游触点问题 |
| T47：问 Hub `T8D02181-80` 是否发货，旧订单商品是整机 `T8D04121` | 查到旧订单已签收 → 直接作为查询答案 | 订单号匹配不等于查询商品匹配；当前订单表没有这件 Hub 的发货记录。Hub 与主机型号不同本身合理 | 明确查到的是旧整机包裹；索取配件订单或服务案件编号，不推定 Hub 已签收或尚未发货 |
| 第一批修复复测：`my pump`、`stofzuiger`、产品名与候选部件不同 | 将整机名称当成具体部件 → 判对象冲突 → 产生不必要澄清 | 把“整机与部件名称不同”误当成“故障对象不同”。记录涉及 T55/T36/T40/T54/T62 等 7 单，不与首测失败统计合并 | 整机名称允许对应其部件候选；只对明确部件或关系作冲突判断，但仍须检查候选适用条件 |
| 同批复测 T29：`Water tray` 对 `cleaning tray` | 名称不完全相同 → 判对象冲突 | 名称差异不足以证明是两个部件；同类部件可能有不同称呼 | 结合型号部件资料归一化。中心词相同可避免明显误拒，但不能证明所有 tray 都是同一个部件 |

`_is_part()` 的作用是判断主语是否指向具体部件，让冲突校验避免把整机与其部件相互排斥。它并不证明候选适用，也不证明部件损坏。以英语词表、中心词或字符串包含关系判断，只能覆盖部分明确表达；多语言、左右两侧、数量和上下游关系仍需保留结构化信息与未知状态。

最小关系表达可以是“对象类型、对象标识、所属设备、作用方向、关联订单/任务”。庞大的产品本体库属于可选复杂度，不是修复这类问题的前提。

### 3.1 T52：主语相同，充电关系仍可能相反

**受电方**是接收电能的对象，**供电方**是向其他对象输出电能的对象。同一个充电盒在不同链路中承担不同角色：

| 内容 | 充电链路 | 盒子的角色 | 故障含义 |
|---|---|---|---|
| 客户说盒子自身无法充电 | 电源 → 充电盒 | 受电方 | 盒子自身的输入充电失败 |
| 候选讨论盒子无法给泵充电 | 充电盒 → 泵 | 供电方 | 盒子向泵供电失败 |

两者都可以用 `charging case` 作主语，部件名称相同并不意味着现象相同。T52 的历史偏差发生在选方案时，不能仅因已经抽到充电盒名称，就认定实体理解和适用性判断正确。

本次阅读的工作区 `filter_hypotheses()` 将用户事实的 `subject` 与模型填写的 `matched_subject` 交给 `_subject_conflicts()` 比较。两个字符串相同或互相包含时直接返回“不冲突”，没有独立核验充电关系中的供电方与受电方。

因此，**如果模型把下游供电候选的 `matched_subject` 也填成 `charging case`，这项主语校验就不能拦截方向错误**。这只是该校验的能力边界；候选最终是否保留，还取决于适用性、症状覆盖和证据等其他检查。

证据状态需要分开：历史 T52 的方案方向错误已确认，当前字符串校验的上述缺口已由代码确认；这次具体运行是否填写了相同主语并因此未触发 `subject_mismatch`，仍需核对对应模型输出和实际筛选记录，不能由最终选错方案倒推。

必要方案是将用户事实和候选适用条件表达为“谁给谁充电、失败发生在哪一侧”，而不只增加部件词表。候选条件应绑定知识来源，LLM 负责将客户表达映射到关系，程序核对有定义的方向；方向未知才澄清，方向明确冲突则拒绝候选。验收应覆盖两个主语都为 `charging case`、但供电关系不同的输入。

## 4. C：事实含义与并列症状

问题：事实既要保留说了什么，也要保留肯否、发生时间和范围。客户表达有歧义时，不能为了匹配某个方案而改写原话。

| 案例与输入要点 | 历史错误链路 | 根因 / 备注 | 合理处理与验收点 |
|---|---|---|---|
| T50：`the left one does work` | 按左侧故障理解 → 给无吸力排查和复位 | 字面为“左侧能工作”。可能笔误，也可能另一侧异常，原材料不能裁定。陈述肯否与故障对象未知是两件事 | 保留肯定句，确认有问题的哪侧、哪个功能；获得回答前不补否定词、不预设吸力故障 |
| T61：提前两小时启动，App 未记录清扫 | 匹配 schedule 主题 → 追问或操作围绕“7051 无法启动” → 遗漏记录缺失 | “已经启动但太早”与“没有启动”方向相反；又存在第二个独立症状。较晚首测中的事实和查询保留了原意，错误在候选适用性及追问前提 | 同时保留时间偏移和记录缺失；询问与实际现象相关的设置或记录条件。无适用资料时完整交接，不强配不能启动方案 |
| T57：多台摄像头异常、一台正常，客户怀疑系统变化 | 若直接匹配升级故障条目，会把怀疑写成已确认升级故障 | 客户没有确认升级及版本；一台正常、多台异常的范围也不能丢失。这是候选适用性风险，不表示该轮澄清本身错误 | 先区分离线、无法打开画面、不录像；需要时收集实际版本和发生时间，依据当前有效证据确认升级关联 |

“不能充电”是明确的故障事实，不能因为是否定句就从有效症状中删除。“没有异响”则是在排除异响。规则应理解否定作用于哪个状态，而不是统一丢弃带否定词的句子。

每个有效症状都应有去向：适用指导、待澄清、无资料交接或已确认解决。无需为每个症状硬配一条操作。

## 5. D：召回、排序、选用与校验

问题：最后没有给出方案，可能是没有检索、没有召回、预算裁掉、模型误选、事实丢失或引用校验失败。它们需要不同修复，不能统一归为“知识库没答案”。

| 案例 | 已确认的历史链路 | 根因 / 备注 | 合理处理与验收点 |
|---|---|---|---|
| T18：已给 3212，仍追问 3212/3202 | 模型抽到症状 → 引文插入 `...` 拼接不连续原文 → 事实未入库；正确 `rv-0147` 已进入候选上下文，但被空症状集合校验拒绝 | 更深的日志及固定历史函数复现支持“引文失败 → 空事实 → 拒绝正确候选”。不能仅以同版本复测成功归为模型适用性波动 | 引用失败可见并有界修复；查询与诊断共享事实。已知码值不重复问，允许问“操作后是否仍报该码” |
| T22：7002、轮子未着地 | 引文将两段倒序拼接 → 事实全部丢弃 → 正确 `rv-0106` 被拒绝 → 人工出口 | 查询有原文回退，诊断却使用空症状，两个环节输入不一致；摘要随后也丢现象 | 保存表单可定位字段；修复来源引用，不能把抽取失败伪装为客户未描述 |
| T34：返修后地图丢失 | 模型修正 `siscovered` 拼写或改变大小写 → 来源校验失败 → 正确 `rv-0312` 被拒绝 → 摘要称无故障现象 | 语义理解存在，但逐字来源不合格，事实被静默丢弃。该历史机制与后续复测中的查询主体缺失要分开 | 语义值可归纳，引用应由可定位原文支撑；不能只放宽大小写来解决所有跨段拼接问题 |
| T30：E4、边刷异常 | 正确 `rv-0443` 已进入上下文且被模型判适用 → `evidence_ids` 填了用户事实编号 → 知识引用校验拒绝 | 用户事实编号与知识证据编号混用。离线仅替换为合法知识编号，原校验即可保留候选 | 两类引用分开；服务端维护候选到知识的映射。错误引用先修同批输出，不能直接取消证据校验 |
| T13：5116 | 精确错误码索引未收录 → 不借用相邻错误码 → 交接 | 合理的知识缺口对照。转人工不自动等于失败 | 如实说明资料缺口，保留错误码；不能为了降低人工率改用 5112 |

这四个有资料的历史案例中，目标资料都已进入模型上下文。增加召回数量不能修复其直接原因。既有“再看被预算排除的其他候选”恢复，只适用于候选被裁掉，不能修复空事实或错误证据编号。

### 5.1 每一层应分别记录什么

| 环节 | 判断问题 | 失败时的处理 |
|---|---|---|
| 入口路由 | 是否执行了本轮需要的检索 | 修正路由；如 T31 首轮不能重评不存在的旧方案 |
| 查询构造 | 型号、对象、现象、错误码是否保留 | 修复查询；不能只留下 `cannot use them` 而丢掉 maps |
| 召回 | 期望资料是否进入候选集合 | 检查索引、过滤与查询；必要时补知识 |
| 排序与上下文预算 | 正确候选是否真的交给模型 | 调整排序或裁剪；可重看被排除候选 |
| 语义选用 | 对象、方向、时间和前提是否匹配 | 未知前提才追问；已知冲突拒绝；相关主题不能冒充适用 |
| 事实与证据校验 | 使用的是合法、对应的事实和知识吗 | 修复引用或输出；不能宣称知识缺失 |
| 业务出口 | 是否仍有必要澄清、可用指导或真实缺口 | 按明确原因继续、等待或交接 |

检索排序分与模型自报的 confidence（置信度）都不是已校准的答对概率。不能看到 0.016 就判无资料，也不能给候选赋 0.3 后认定能执行。

精确型号与错误码命中可以减少候选范围，仍须核验是否属于当前设备、当前故障，以及安全和步骤前提。单步指导也可能有效；文档被解析为 `answer` 或 `steps` 的排版分类不能替代执行资格。

模型明确返回“无适用方案”，与模型调用失败、输出格式异常要分开。不能将语义拒绝自动恢复成检索排序第一名并出卡。

## 6. E：知识转交互流程

问题：客服文章的编号段落不是天然的操作步骤。标题、事实问题、上传请求、检查操作和后续交接可能混在同一段，需要保留语义及条件。

| 案例与内容 | 历史错误链路 | 根因 / 备注 | 合理处理与验收点 |
|---|---|---|---|
| T46：`Identify the Problem`；“持续还是间歇？”；录制音视频 | 按编号拆段 → 全部生成操作卡 → 点击“未解决”推进并增加已试次数 | 缺少节点类型，反馈协议统一；标题与事实问句没有操作结果。原始 Q&A `bp-0123` 还包含不适用于该型号的外接软管检查 | 标题直接展示；问题收事实答案；视频使用材料节点；仅实际操作记录操作结果 |
| T19/T24/T28/T38：硬件或保修结论 | 结论成为“步骤” → 客户必须点未解决才能看到后续 | 判断说明和客户操作混淆 | 直接说明结论与下一步，不要求操作反馈、不累计尝试 |
| T26：清洁液事实问题混合条件操作 | 一张卡里既问情况又要求按条件操作 → 一个反馈无法表达实际答案 | 同一段存在多种语义，缺少条件分支 | 拆成事实问题和满足条件才执行的操作；未知答案不能默认满足条件 |
| T40：检查瓶体并要求照片 | 反馈“未解决” → 流程推进到质保 | 操作反馈未证明材料已提交 | 操作与材料分别记录；材料暂缺保持缺失，不阻止不依赖材料的其他步骤 |

| 内容类型 | 应接收的输入 | 状态含义 |
|---|---|---|
| 事实问题 | 选项、短答或“不确定” | 更新事实；必要时决定分支 |
| 操作 | 已解决、未解决、无法执行 | 记录操作结果；无法执行不算已完成操作 |
| 说明/结论 | 通常无需反馈 | 展示信息；不增加已做次数 |
| 材料请求 | 上传或明确暂缺 | 更新材料及缺失状态；不自动确立资格 |
| 人工交接 | 按业务要求确认或直接登记 | 保存请求与交接信息；不等于人工接单或业务完成 |

必要方案是有类型、有条件的节点及对应载荷校验。可先审核高频知识并作带知识版本的覆写；通用流程编辑器属于可选复杂度。关键词分类只能辅助初筛，未知段落不能默认变成可执行操作。

## 7. F：历史操作与多轮状态

问题：客户来信前的操作也是排障信息，但它不是对当前卡片的反馈。判断能否跳步，需要比较具体动作、对象、背景和结果。

| 案例与输入要点 | 历史错误链路 | 根因 / 备注 | 合理处理与验收点 |
|---|---|---|---|
| T27：已照建议检查、无堵塞，异响持续 | 再次给滚刷清堵 | 只记录本轮卡片反馈，没有利用客户自述历史 | 保存已做检查和无效结果；转到剩余适用检查，重复时解释新增检查点 |
| T36：已清洁、更换滤网和刷子，仍很吵 | 完整重放通用清尘流程 | 历史动作与当前持续现象没有联合使用 | 区分换过什么、检查过什么、现在仍怎样；不能因“已清洁”删除所有不同的清洁检查 |
| T37：水箱满，管路和胶圈正常 | 优先给缺水补水整段方案 | 已知部件状态没有约束候选选择 | 避免重复问已明确状态；必要时只确认尚未覆盖的密封或安装检查 |
| T31：首次来信说已擦过电气触点 | 被解释成操作条件变化 → 进入 reassess（对旧方案重新决策） → 没有旧方案即交接 | 历史动作被当作当前流程变更；入口未检查是否真的有可重评的诊断状态 | 将来信前动作记为历史；没有旧方案就进入正常产品确认和检索 |

“擦过滚刷表面”不等于“拆下滚刷清除轴端缠绕”；“以前重启过”也不等于“本次故障后重启仍无效”。动作等价才跳过，结果未知先问结果。客户自述已做与系统收到本轮操作反馈应分别记录，不能跳步后虚增执行次数。

## 8. G：多诉求与任务结束

问题：主意图用于安排处理顺序，不应吞掉其他诉求。当前任务有结果、整轮可以结束、客户业务已办完，是不同状态。

| 案例与输入要点 | 历史错误链路 | 根因 / 备注 | 合理处理与验收点 |
|---|---|---|---|
| T9：查主机物流；若未发货则暂停；先谈其他产品；对未通知不满 | 早期处理改单分支后结束，物流 pending；较晚首测查询和入队正确，但摘要仍套故障模板 | 每项诉求的对象、条件和完成条件不完整；不同轮次问题不同，不能合并描述成同一结果 | 查询与条件暂停分别保留；登记暂停请求后答复允许继续的独立查询；预计发货日期不是保证，登记不等于暂停成功 |
| T51/T53：申请换货并求助排障；运行当日已过保 | 正确拒绝免费服务 → 整会话 done → 排障仍 pending | 免费服务资格办理结果被当作全部请求结束；还承诺过继续排障 | 只关闭对应服务任务；继续允许的自助排障，或明确取得停止结论。过保后指导范围属于业务选择，任务遗漏是确定缺陷 |
| T63：刷罩损坏、买不到配件、清洁效果差，型号未知 | 保留损坏和清洁后交接 → 购买诉求遗漏 | 意图类型缺少购买，任务和摘要未完整承接多诉求 | 保留购买任务，利用已有信息并澄清关键型号/部件；实际购买需人工时交接。其余诉求各有处理结果或归属 |

等待人工后能否继续，取决于任务依赖、安全约束和客户要求。可以继续不依赖人工结论的只读查询；不能为了清空队列恢复客户已要求停止的排障，或执行尚待批准的动作。

验收需要检查每项任务的结果、等待原因和归属，不能只看 `stage=done` 或第一句回复。也不能把 `waiting_human` 当成客户业务已解决。

## 9. H：附件用途与材料条件

问题：图片内容、提交用途和能证明的事实是三件事。图片清晰不代表适合故障诊断，已有附件不代表所需材料全部齐全。

| 案例与输入要点 | 历史错误链路 | 根因 / 备注 | 合理处理与验收点 |
|---|---|---|---|
| 早期 T55：附件实际为订单截图，首问默认按 fault（故障图）上传 | 白底凭证触发 too_bright（过亮） → 要求补拍；后续材料清单也受用途影响 | 默认用途、图片质量规则和证据用途耦合。该问题在后续复测中改善，保留为历史回归 | 识别凭证用途；白底不能单独否定可读凭证。凭证不能替代故障影像和 SN（序列号） |
| T46：原附件是订单材料，投诉是马达异响 | 若把附件存在当成已收到噪音视频，会跳过必要采集 | 已有材料与所需材料类型不匹配；声音问题通常无法由订单图证明 | 已知凭证可复用；需要判断噪音时明确收集对应音视频，不重复索取同一已验证凭证 |
| T40：请求照片却只有操作反馈 | 点击“未解决”被当成材料环节完成 | 反馈协议没有表达材料状态 | 上传、暂缺与操作结果分开；必要材料缺失不自动视为满足资格 |
| T48：设备照片可见绿灯和外壳裂纹 | 若凭绿灯直接下故障结论，会超过已有知识 | 看见现象不等于知道该型号灯态含义。原测评中的诚实说明不足是合理行为 | 优先复用已知型号；没有可靠对应知识时说明缺口，不编造灯态结论 |

必要方案是按用途与事实关联保存材料，并区分必需和可选。自动材料识别可以辅助，不能凭“已上传一张图”统一完成全部证据条件。

## 10. I：人工交接与办理结果

问题：交接既有信息完整性，也有动作真实性。成功话术必须来自已持久化的结果；新请求、同请求重试和摘要刷新还需要正确绑定。

| 案例/验证场景 | 历史错误链路 | 根因 / 备注 | 合理处理与验收点 |
|---|---|---|---|
| T9 11:48 复测：回复已交给同事 | 案件仍 open，仅有订单识别事件，无交接摘要，物流 pending | 不可执行诉求分支提前返回，未走真实交接；评测只看话术又产生假通过。后续修复复测已观察到真实入队 | 验收案件、请求与交接记录，而非匹配一句“已转交” |
| T9 多轮边界：先“未发货就暂停”，后“改为取消整单” | 同为 order_change → 被当成重复 → 人工仍收到旧要求 | 用同类意图代替同一次请求识别；新语义被去重吞掉。这是隔离 HTTP 已复现的历史缺陷 | 稳定请求编号识别重试；内容或条件变化应记录修订并更新对应任务/摘要 |
| T9 故障注入：入队成功后摘要写入失败，再重试 | 看到已入队状态 → 跳过剩余写入 → 仍报成功，摘要为空 | 分多次提交形成半成品，去重未验证完整性。相关后续修复有独立验证记录 | 同库交接状态、请求、摘要一次事务提交，或采用能核验并补齐的恢复协议 |
| T22/T34：客户已描述错误/地图问题 | 事实丢失 → 摘要写“尚未记录现象”；T22 还把登录国家 NL 写购买渠道 | 上游事实失效传播到摘要；字段含义映射错误 | 使用当前问题关联的原始材料与有效事实；登录/注册国家不能作为销售渠道 |
| 较晚 T9：先生成摘要，后取得物流事实 | 摘要仍写产品未确认、无故障，索要购买凭证 | 业务模板不匹配，摘要未随同一案件的新事实刷新 | 订单变更摘要包含订单、商品、条件、物流与未完成请求；刷新不混入另一个订单 |

应明确区分：摘要已准备、请求已登记、人工已接单、订单已暂停或退款已完成。当前阶段只能陈述有实际回执支持的事实。

未知故障的准备交接、安全事件和客户主动人工不是同一个触发原因，不能见到 `contact/service` 就套同一种模板。摘要应保留多个症状、已做操作、材料缺失、条件诉求及各自对象。

## 11. J：回复范围与中断恢复

| 案例/场景 | 错误或需要防止的链路 | 根因 / 备注 | 合理处理与验收点 |
|---|---|---|---|
| T35：询问低电回充后是否继续任务 | 正常机制已解释 → 继续扩展电池错误码/操作 → 流式超时，留下半段文本；复测还露出内部证据 ID | 答复范围过大、内部引用直接呈现、失败状态记录不足。该次超时不能证明由某个模型性能不足主导 | 回答机制及必要例外；展示可读出处；失败标为未完成并提供重试，不把半段建议当完成 |
| 网络断开后恢复（构造验收用例） | 客户未收到回复 → 重连后重复提交 → 可能重复业务办理 | 传输断开与业务是否提交是不同状态；不能凭客户端未收到结果判断服务端没做 | 恢复已发布会话状态和事件；同次请求复用原结果，不重复入队或执行 |
| 服务重启发生在业务提交后、会话提交前（构造验收用例） | 会话看似未处理 → 重跑业务动作 | 业务结果和会话状态可能跨提交边界 | 通过请求编号及持久化结果恢复；无法确认时显示结果待核实，不假定成功或失败 |

后两行是需要验证的场景，不是本次测评已经观察到的线上故障。会话记录、流程状态、业务动作结果与材料缺失状态都需要恢复；只保存聊天文本不足以继续正确流程。

## 12. K：数据与评测质量

问题：真实工单不一定能给出唯一答案，知识也可能存在适用范围问题。系统错误、来源冲突、资料缺口和项目标签错误应分别记录。

| 案例/资料 | 已确认情况 | 根因 / 备注 | 合理处理与验收点 |
|---|---|---|---|
| T4：产品名 X10 Pro，SKU/订单对应 E25 | 产品字段不一致 | 有依据的源字段勘误；不是全部订单资料错误 | 物流仍可按订单查；特定型号排障前解决冲突，原始资料不覆盖 |
| T2：客户描述与订单包裹映射/状态不一致 | 来源之间冲突，不能裁定谁错 | 缺乏足够证据证明是客户认错或表格错误 | 分别说明客户反馈与记录，澄清实际商品/运单；物流签收不等于客户收到对应商品 |
| T46 / `bp-0123` | 有问句/操作混排，且包含型号不适用的外接软管检查 | 混排属于系统转换难点；外接软管属于知识适用内容问题，两者分别归责 | 保留原文与来源，规范化层屏蔽已确认不适用内容；命中官方资料不免除适用性审核 |
| T57 / `bp-0164` | “App 5.0 及以上可能有问题”，缺确认时间、平台、版本上限与修复依据 | 时效及适用范围缺口，未证实条目虚假或已失效 | 作为候选线索，结合实际版本及当前厂商证据；不能永久当确诊条件 |
| 项目二次标签 T50/T52/T61/T46 | 分别奖励补否定、错误充电方向、无法启动方案或异响推吸力异常 | 项目标签将猜测或主题相近当成正确，不是主办方给出的唯一标准答案 | 验收原事实、适用条件、合理澄清及任务结果；命中 ID 不能单独判通过 |

缺信息本身是有效客服场景，例如缺订单号、型号未知、只描述情绪。合理澄清可以通过；不能为了得到唯一排障答案而删掉这些样本。知识放在哪个工作表也不能决定产品范围，已有摄像头资料曾被工作表名称误导而漏认。

原始层保留工单及知识，评审层另记冲突、勘误、缺失信息、可接受结果与禁止假定的事实。评分口径应在比较模型或架构前冻结，历史首测不被最好的一次复测覆盖。

## 13. 完整示例：吸奶器异响为什么需要判断对象

### 13.1 真实 T46 与教学变体

真实 T46 原文写的是 `Motor making awful noise`，并说明不到一个月、总共使用约 20 次。客户已经将声音描述为马达异响；这仍不等于已经确诊马达损坏，也没有确认吸力下降。该轮主要错误是知识被转成不合适的交互卡片。

下面改成更宽泛的“我的 S1 Pro 吸奶器有异响，用了大约 20 次”，用于解释整机与部件判断。**后续回答全部为构造示例，不属于官方 T46 已发生的会话。**

| 轮次 | 输入或候选 | 系统应如何理解 | 合理下一步及原因 |
|---|---|---|---|
| 1. 首次求助 | 客户：“我的 S1 Pro 吸奶器有异响，用了大约 20 次。” | 意图是排障；对象是整机；现象是异响；声音来源、时机和吸力变化未知 | 保留事实和未知项，检索适用型号的异响资料 |
| 2. 候选判断 | A：马达异响 `bp-0123`；B：无/弱吸力 `bp-0125` | A 与主题相关，但入口信息待补；B 的核心症状尚未报告。“整机”与 A 的“马达”不同不构成冲突 | 允许 A 继续适用性判断，先问声音持续性、时机及性能变化；不能由“没冲突”跳到“已适用” |
| 3. 事实回答 | 客户：“声音在上面的主机，抽吸过程中持续响，吸力感觉没变。” | 更新声音对象、发生时机和持续性；“吸力没变”是客户观察，不是检测结论 | 进入符合这些条件的噪音分支；不切换到默认无吸力排查，不宣称马达损坏 |
| 4. 材料与操作 | 收集至少 10 秒音视频；提供已审核、适用于该型号的装配检查 | 视频是材料；装配检查是操作；不适用的外接软管内容不能执行 | 用上传入口和操作反馈分别收结果；材料暂缺时仅继续不依赖材料的检查 |
| 5. 操作结果 | 客户：“按要求重新装配了，还是响。” | 记录具体动作、对象及无效结果，而不只保存“未解决”四个字 | 选择剩余适用检查；若需再装配，应明确新增检查点，避免循环重复 |
| 6. 结束或交接 | 适用检查后仍异常，或可靠判断需要人工 | 已知现象、动作及材料都有去向；免费服务资格尚未核实 | 保存完整交接信息，按业务要求核实订单/SN等；不保证免费换货，不把登记交接说成修好了 |

### 13.2 哪些对象判断合理，哪些不合理

| 用户描述 | 候选 | 判断 |
|---|---|---|
| 整机有异响 | 马达异响 | 名称不同本身无冲突；是否适用仍要检查声音对象和条件 |
| 整机有异响 | 无吸力 | 缺少候选核心症状，不能仅凭都是同一产品就开始执行 |
| 充电盒自身充不进电 | 泵在盒子内触点不良 | 故障方向不同；不能将下游方案当作已适用 |
| 左侧泵不能充电 | 右侧泵不能充电 | 虽然都叫 pump，左右对象不同；中心词相同不足以认定一致 |
| 水盘漏水 | 清洁盘密封问题 | 可能是同类部件的不同称呼，需结合型号部件关系；不能单凭 tray 相同下结论 |

因此，“我的吸奶器有异响 → 检查马达”只能作为待核验候选示例。若把它直接写成正确操作，会跳过真正需要说明的适用条件。

## 14. LLM、规则与状态各负责什么

`diagnose/synthesize.py` 负责结合事实与知识候选提出、筛选和排序诊断假设；它不是整个客服系统的唯一决策点。入口理解、业务查询、知识转换、任务推进和状态保存分别影响最终回答。

下表描述合理职责边界，不能作为当前实现全部完成的声明。

| 工作 | LLM 的职责 | 程序/规则的职责 | 必须保存的状态 |
|---|---|---|---|
| 意图与来源 | 理解求助、反问、设备引文和混合表达 | 核验来源片段、明确停止要求和路由约束 | 诉求、来源位置、对象、用户约束 |
| 实体与事实 | 识别整机/部件、方向、肯否、时间和歧义 | 核验有定义的字段、对象归属及已知冲突 | 原话、语义值、实体关系、未知项 |
| 知识选择 | 判断候选入口前提与现象是否匹配 | 校验型号/错误码范围、合法候选和独立证据引用 | 候选、选用/拒绝原因、知识来源 |
| 问题与步骤 | 提出必要追问，解释条件和动作 | 按审核后的节点类型执行，校验答案与分支 | 答案、材料缺失、操作结果、当前节点 |
| 任务与业务动作 | 理解多诉求、条件和请求修订 | 授权检查、任务状态、请求去重、事务和结果核实 | 每项请求的标识、对象、条件与回执 |
| 交接与回复 | 根据事实组织可读表达 | 防止内部 ID 外露、无回执成功话术和失败伪装 | 摘要版本、关联请求、发布/失败状态 |

自然语言理解可以由 LLM 提供结构化结果；程序应校验可证明的约束。反复扩展词表来承担所有语义判断会增加误判，更强模型也不能补出不存在的知识、业务回执或丢失状态。

## 15. 通用回归用例与改进顺序

典型案例应推广成成对测试，避免只修某个 T 编号或固定原句。

| 用例组 | 需要比较的输入 | 必须保持的行为 |
|---|---|---|
| 说话来源 | 设备提示人工 / 客户明确要人工 / 两者混合 | 分段判断；保留真实人工请求 |
| 信息与安全 | 仅表达不满 / 明确故障现象 / 安全风险 | 信息不足时问必要事实；安全路径保持独立，不以一般澄清拖延安全处理 |
| 故障对象 | 追踪号查不到 / 设备离线 / 二者同时 | 物流与故障各自绑定对象，不互相吞掉 |
| 实体关系 | 整机与部件 / 两个部件 / 左右部件 / 输入和输出供电 | 不误拒整机候选，不混淆关系和左右 |
| 同名对象的角色 | 两边都写 charging case，但分别是盒子受电失败和盒子给泵供电失败 | 按充电关系核验，不能仅因主语相同放过方向冲突 |
| 肯否与未知 | 能工作 / 不能工作 / 没说哪侧异常 | 不补否定词，不把明确故障当信息不足 |
| 时间与多症状 | 提前启动 / 未启动 / 提前且缺记录 | 保留方向和每个症状的处理去向 |
| 引文与编号 | 空白差异 / 拼写改写 / 跨段拼接 / 事实编号填入知识字段 | 合法事实不丢失；无效引用可见并修复，不能放弃来源校验 |
| 召回与适用性 | 正确资料已入上下文 / 被裁掉 / 无适用资料 | 使用对应恢复动作；不把所有失败统一转人工 |
| 历史操作 | 已做且无效 / 已做结果未知 / 相似但不同操作 | 等价才跳过；不虚增执行次数 |
| 交互与材料 | 事实问句 / 操作 / 必需材料缺失 / 可选材料缺失 | 载荷及推进条件不同；未知不默认通过 |
| 多诉求结束 | 过保仍有排障 / 无其他请求 / 客户明确停止 | 当前任务与全部任务分别收尾 |
| 请求与交接 | 同请求重试 / 新要求 / 半途失败 / 改查另一订单 | 不吞新要求、不重复登记、不混合摘要归属 |
| 回复恢复 | 正常解释 / 流式失败 / 断网 / 提交后重启 | 范围适当、失败可见、恢复不重复业务动作 |

改进顺序：先确保事实来源、对象和失败原因可见，修正明确的路由及任务遗漏；再统一诊断输入与知识引用，补齐适用性和节点条件；最后根据各层指标评估召回排序、模型选择和知识维护。

必要工作包括来源可追溯、任务归属、引用修复、节点类型与业务提交保证。通用工作流引擎、全量产品本体、可视化流程编辑器和更换整个知识库属于可选复杂度，当前案例不能证明必须采用。
