# 多诉求处理与人工交接方案（以 T9 为回归案例）

## 问题与证据

客户要求查询 Anker008 主机物流；如果主机尚未发货，先暂停并讨论其他产品，同时表达未收到延迟通知的不满。

11:48 复测三个独立会话均识别 order_change 与 logistics_query，但执行路径为 understand → service_context → commit_issue。案件已创建，状态仍 open，只有 order_identified 事件；物流任务 pending，却回复已将请求交给同事。

证据：[本轮测评](../planning/2026-10-09-0828_official-case-evaluation/round2-1146/report.md)、[案件与任务状态](../planning/2026-10-09-0828_official-case-evaluation/round2-1146/verification.json)。

## 第一性原理与完成条件

系统要交付的是每项客户诉求的可验证处理结果。识别意图只表明理解了需求；生成一句话不能证明业务动作已发生。

| 诉求 | 当前能力 | 可接受的处理结果 |
| --- | --- | --- |
| 主机和滤网物流 | 查询官方订单数据 | 回复主机预计 2026-10-20 发货、滤网已送达；附事实来源。预计日期不表述为保证 |
| 若主机未发货，先暂停 | 当前系统不能直接暂停发货 | 保留条件和主机范围，将请求持久化到人工队列，并如实说明暂停尚未确认 |
| 暂停期间讨论其他产品 | 尚无明确偏好，且未授权换成具体商品 | 交接摘要保留该诉求，必要时询问希望改善哪些功能；不擅自改购或编造推荐 |
| 对延迟未通知不满 | 调整回复方式 | 回应不便和沟通缺失，不编造延迟原因或承诺处理时限 |

人工已排队、人工已接单、订单已暂停是三个不同事实。只有收到相应结果后才能陈述该事实。当前功能最多能证明本系统人工队列已登记，不能证明外部订单已暂停。

## 必须成立的约束

1. 每项诉求保留所属订单、对象范围、条件和客户原话。T9 的“if not shipped”不能丢失，也不能把暂停主机改写为取消整张订单。
2. 每项诉求分别记录处理状态。查询成功、等待客户、等待人工、失败不能统一标成业务已解决。
3. 等待人工的影响范围必须明确。只有不依赖人工结论、订单归属明确、且未被安全规则或客户明确要求阻断的查询才能继续；本轮结束时，未完成事项必须有明确等待原因或失败结果。
4. 已完成动作的文案必须依据持久化成功结果生成；失败时说明未提交成功。
5. 同一次交接请求重试不能重复入队。交接成功但会话状态尚未提交时，重放可以恢复原结果。

## 推荐流程

1. 绑定 Anker008，读取已有物流事实。这是判断“如果尚未发货”条件的前置事实，不等于将所有物流查询无条件提高为最高优先级。
2. 将“未发货则暂缓主机发货，并先讨论其他产品”的原始请求交给人工处理。资料显示尚未发货，但仍不能保证仓库此刻已暂停；交接要求人工核实最新状态。
3. 人工队列持久化成功后，将该诉求置为 waiting_human（等待人工），保留案件编号与交接依据。
4. 继续完成物流答复及必要的产品偏好澄清。最终会话可结束本轮，案件仍等待人工，不能显示整体业务已解决。
5. 交接写入失败时，保留真实失败状态，仍可答复已取得的物流信息；同一请求可安全重试。

产品咨询可和暂缓请求一起交接，也可在机器人具备可靠产品信息时继续澄清偏好。不能让偏好澄清阻塞已明确、具有时效性的暂缓请求。

## 最小实现范围

### 人工交接模块

在现有 CaseService 内提供一个业务接口，接收稳定请求编号、案件/任务归属、原始诉求及摘要，返回已持久化的交接结果。该模块内部负责合法状态迁移、review_requested 和 handoff_summary 记录、重复请求检查。

现有 await_human 分三次调用 transition、record_review_request、record_handoff。将这三项写入收敛到一次 store.mutate；PostgresCaseStore.mutate 已提供单事务能力。这样不会出现状态已入队但摘要写入失败的半成品。不同请求不能复用同一幂等编号；相同请求重试应返回原结果。

案件事务与会话 checkpoint 不假定处于同一事务。通过稳定请求编号和重放已有交接结果恢复任务状态，复用已有持久化消息机制。

### 任务推进

在现有 task_queue 上区分 waiting_human 与 done。waiting_human 表示用户诉求尚未解决，不能单凭该状态就继续其他任务。任务推进还须检查依赖、风险、客户停止要求和已有待确认事项。第一阶段只让满足这些条件的独立只读查询继续；不自动恢复受阻的排障、换货、退款或订单变更执行。

由业务处理返回明确结果，并按任务编号及订单归属更新任务，再集中决定继续、等待或结束。不要让每个分支自行发送成功话术并直接结束整轮，也不要仅凭 completed_task_intent 这个字符串隐式推断业务已完成。

service_context 的不可执行诉求分支进入实际交接；交接完成后由任务推进判断能否继续。人工等待状态属于对应任务和案件，后续 consult 不应覆盖它。不能只把当前 return 改成 await_human：现有 await_human 也会直接 commit_issue，物流仍然被丢弃。也不能将 await_human 全部出口无条件改成 advance_tasks，该函数同时被授权失败、执行结果异常和客户请求人工等路径使用。

### 回复与评测

使用查询事实和交接结果渲染回复。成功交接后可说“暂缓主机发货及讨论其他产品的请求已登记，等待人工核实；尚未确认暂停成功”。没有交接结果时不能说已提交。

terminal_of 不再用 passed your request to 作为成功证据。T9 必须同时满足物流事实覆盖、条件诉求完整、案件实际入队、有交接记录、无未解释的 pending 任务，以及没有声称已暂停订单。

## 验收用例

- 原始 T9：两个物流事实正确；暂停主机和产品咨询诉求完整；人工队列可查询到请求；没有误入换货排障。
- 相同语义交换表述顺序，分别让查询或改单成为主意图：结果均覆盖全部诉求。
- 主机已发货：保留客户的条件语义，告知当前状态，不执行“未发货时暂停”的假定分支；交接核实可行处理。
- 没有可靠物流数据：承认状态未知，将条件请求交人工核实，不编造是否满足条件。
- 人工写入失败：不存在已转交成功文案；物流仍可答复；未成功项保留失败/等待信息。
- 同请求重试、案件提交后会话 checkpoint 前中断恢复：一次业务交接，无重复入队，任务状态最终一致。
- 单独改地址、取消/改购等复用分支也遵守相同完成条件；订单与任务归属不能串联。

实现后的回归采用 FakeChatModel、项目内存案件存储及现有 HTTP 测试工具，不调用真实模型。然后按本轮原输入重跑 T9 三次验证实际运行版本；重复运行只能说明样本稳定性，不能代替确定性回归。

## 影响范围与通用性约束

用户补充要求：方案必须通用，不能为 T9 特判。当前仅修改设计文档，尚未实施，不能宣称其他流程已验证无影响。

- 生产逻辑不得依赖 T9 编号、Anker008、固定日期或完整案例文本；这些只能出现在测试资料和断言中。
- 业务规则按任务能力、条件、归属和处理结果生效。改地址、暂缓、取消、改购等需要人工的请求共用真实交接规则；成功话术统一依据持久化结果。
- 保持优先级含义，不为通过 T9 把所有物流查询永久移到首位。只读取条件判断所需事实，再在不阻塞时效性请求的前提下答复独立查询。
- 后台入队和仅准备升级摘要保持区别。未知故障码或安全事件生成 prepared 摘要，不能因共用文案被说成实际人工已接单。
- 安全阻断、等待用户确认、等待人工批准、执行结果未知仍限制对应动作；在另一个分支取得查询结果，不得清除这些限制或恢复执行。
- 用户明确要求停止机器人处理、只接人工时，停止范围覆盖其要求的任务，不为清空队列继续排障。
- 人工批准或驳回只更新关联请求。若批准还需后续动作，继续通过原有授权检查，不把批准自动解释为订单已变更或整体任务已解决。

| 回归场景 | 必须保持的行为 |
| --- | --- |
| 单独查物流或保修 | 正常答复，不凭空建立人工交接 |
| 需要人工处理的请求加独立查询 | 真实登记交接，继续答复允许的查询；未处理事项保留状态 |
| 等待照片、SN 或客户确认的换货 | 对应流程继续等待，不能因处理了查询而跳过材料或确认 |
| 人工审核未通过或尚未完成 | 不执行依赖批准的动作，不误标已解决 |
| 安全风险、未知错误码 | 保持停用/升级规则与实际交接状态，不重新进入受阻排障 |
| 明确只要人工 | 尊重停止机器人处理的要求 |
| 执行失败或执行结果未知 | 不重复提交，不假定动作未发生或已成功；沿原核实路径处理 |
| 多订单、多问题 | 交接、查询、人工决定均绑定各自任务和订单，不能串用 |

通用性验证还应使用非 T9 的组合输入，包括“改地址并查物流”“申请退款并查保修”，以及先后两条消息追加诉求。先跑受影响的确定性回归，再重跑八个原样本和 T1/T9 稳定性样本；只有这些检查完成后才报告实际影响。
